## Overview

- **App Name:** Test Recorder
- **Purpose:** Record interactions on any website and turn them into runnable Playwright tests.
- **Features:**
  - Prompt for a URL, open it in a dedicated browser window, and record every interaction as a test step.
  - Captures clicks, text input (fill), selects, checkboxes, Enter/Escape key presses, and navigation.
  - Pause/resume recording; add assertions (element visible / contains text) by clicking elements in the recorded page.
  - Generates a `@playwright/test` spec on close; stored in a test library.
  - Runs a selected test locally with the bundled Playwright (installs the browser on first run), streaming live output. **Step highlighting during runs:** a custom Playwright reporter (`step-reporter-source.ts` → `step-reporter.mjs` written next to the specs) emits `__GLAZE_STEP__:` JSON markers on stdout for each `pw:api` step begin/end with the spec line number; the runner (`playwright-runner.ts`) builds a line→stepIndex map from the spec, strips the markers from visible output, and pushes `runner:step` events; the recorder store tracks per-step `stepStatus` ("running"/"passed"/"failed") in `RunInfo`; `StepRow` accepts a `runStatus` prop and shows an accent-tinted background + spinner (running), green tint + check (passed), or red tint + X (failed) with a status icon on the right. The failed highlight was enhanced to `bg-support-red/15 ring-1 ring-inset ring-support-red/40` (15% red background + 40% red ring) with red description text and a larger `size-4` X icon so the failed step clearly stands out. `TestDetailView` passes `runInfo.stepStatus[i]` to each row. Only applies to app-generated specs (one step per line); imported scripts have no step map so markers pass through harmlessly.
  - "Edit in Trainer" reopens an existing test's trainer window preloaded with its recorded steps so the user can extend it; stopping regenerates the script from the combined steps and updates the same record (preserves `createdAt`). When a test has manual script edits (`scriptEdited`), the "Edit in Trainer" button opens a confirmation dialog ("Edit in Trainer") with three options: "Save & continue" (primary accent — persists any unsaved script draft, then opens the trainer), "Continue without saving" (left-aligned destructive — opens the trainer, letting later regeneration overwrite the edits), and Cancel. On arrival, all trainer controls stay disabled (status "Loading page…") until the browser window finishes loading its first page (`pageReady` on `RecorderState`); the trainer then just shows the loaded page (the `goto`/navigation) and waits — it does **not** auto-replay the recorded steps (the old auto-`replayAll` on load was removed because it "flew through" the whole test and could wedge the backend). The user replays on demand with **"Replay from current step"** (see the replay bullet below). Row highlighting still uses the `StepRow runStatus` mechanism driven by `recorder:replayStep`. **Status states:** the trainer's top-bar `Status` badge reads "Loading page…" (before `pageReady`), then **"Running"** whenever ANY replay is executing (a store-level `executing` flag covering single-step / from-current replays, OR the streamed `replayRun.running`), else "Paused" / "Editing" / "Recording". While running, ALL step-editing controls are locked (`controlsDisabled = !pageReady || running` gates the replay button, assert menu, Add step, AI steps, pause/resume, every `StepRow` action, and the cursor-gap inserts) — so "Editing" only appears when the user is actually free to record or change steps. **Loading modal + timeout:** while the training browser opens, a full-area loading overlay (spinner + "Opening training browser…" + URL + copy) shows on the main window. The training window is force-shown on the earliest of `ready-to-show` / `dom-ready` / a **creation-relative `SHOW_FALLBACK_MS` (1.5s) timer** — the timer is the key fix for the "first click does nothing on a cold start" bug: on the first recorder window after app launch the WebView subsystem cold-starts and its readiness events lag past 10s, which used to leave the window hidden and falsely trip the timeout. Now the window always appears ~1.5s after creation regardless of those events. `LOAD_TIMEOUT_MS` (15s) only bounds `pageReady` (how long controls stay disabled waiting for the first page), decoupled from window-opening. The load-failure path (`!shown || destroyed`) is now a genuine "couldn't open" case (window destroyed) — it logs a failed `RunRecord` to Stats and shows the "Couldn't open the training browser" dialog ("Try again" / "Check Stats"). **Exit confirmation:** the toolbar button is labeled **"Save Test"** in Training mode (editing an existing test, `state.editing`) or **"Generate Test"** in Creation mode (new test). With no live steps (`liveSteps.length === 0`) it saves/exits directly (no warning). With unsaved steps it opens a two-button `Dialog` — "Save & Exit" (finalize + close) or "Discard Edits" (discard steps + close via `recorder:discardExit`) — showing the step count.
  - **mabl-style Trainer (editable step list):** the live trainer step list is fully mutable — drag to reorder, click a value/text to inline-edit it, delete, and an insert cursor (click the gap between steps) that controls where new captured/added steps land. A "+ Add step" menu inserts manual steps without touching the page: Assertion, Wait (duration or wait-for-element), Go to URL, Press key, Find element, Set viewport. Locator-requiring steps (assertion, wait-for-element, press-on-element, find-element) use the same "Target Element" crosshair picker as the per-step "Refine selector" flow (now grouped under a kebab "Step utilities" dropdown beneath the row, alongside the "Continue on Failure" toggle — see Recent History) — the user picks an element in the training browser and chooses one of its candidate locators (best-first) instead of typing a CSS selector by hand. Assertions expanded from visible/has-text to 13 kinds (visible/hidden/contains-text/exact-text/enabled/disabled/checked/unchecked/value/attribute/count/page-URL/page-title) with a Hard/Soft toggle (`expect.soft`). A per-step ▶ replay previews that one step in the live window (best-effort synthetic events, not a real Playwright run). A **"Replay from current step"** button (formerly "Replay from start") replays SLOWLY from the currently selected step (or index 0 if none is selected) through the END of the list — a settle + pause between steps (`REPLAY_SETTLE_MS`/`REPLAY_STEP_DELAY_MS` in `recorder-service.ts`) so the user can watch — streaming each step's result + verbose logs live to the debug panel's Console tab via a new `recorder:replayLog` push (`{phase:"start"|"step"|"done"}`). A hard failure stops the run; soft failures continue; if/endif honored. Each step's injected script is raced against `REPLAY_STEP_TIMEOUT_MS` (8s) via `execWithTimeout` so a step that triggers a navigation (or hangs) fails cleanly instead of wedging the run with controls disabled. Capture is suppressed during the run (`withCaptureSuspended` — see below), the training window is focused before the first step, and both trainer windows show **Replaying** and lock their controls off the broadcast `RecorderState.replaying` rather than each window's own local flag. The running step is auto-selected so the highlight + Step-details tab follow along, and each step gets an **ephemeral pass/fail outline** as it finishes — `.step-replay-pass`/`.step-replay-fail` in `renderer/styles.css`, a green/red one-shot fade held for `REPLAY_FLASH_MS`(2.5s, matching the per-row replay tint) and driven by the store's `replayFlash` map off the `recorder:replayStep` END event. Same outline mechanism as the AI-added `.step-new` glow and mutually exclusive with it (both draw an `outline`; the flash wins while it lasts). Pinned by `check:step-glow`. An "AI steps" button asks the local LLM for a structured `Step[]` from a natural-language flow and inserts editable steps into the list; the dialog has an optional "Refine selector" picker (same crosshair pick as step rows) that captures an element's locator and passes it to the LLM as context so generation can target the exact element the user pointed at. The AI generates only the steps AFTER navigation — Step 1 ("Navigate to URL") is a test-level setting the user controls in the Step 1 URL editor, so the prompt tells the model not to emit a `goto` step (assume the page is already loaded at the starting URL), and the dialog defensively filters out any `goto` the model still emits before inserting. **Tabbed debug panel (`DebugPanel` in `recording-view.tsx`, h-56):** a `TabsRoot` (controlled `value`) with two tabs. **Console** — the live "test results" stream: each replayed step's pass/fail header + verbose formatted log lines (timestamp · level · message) as the run progresses, a status line (`Running… n/total` / `Done — p/r passed` / `Stopped at step n`) and a **% hit rate** pill (passed÷ran). An **Auto-scroll checkbox (checked by default)** gates the `ScrollArea autoScrollToBottom`; unchecking lets the user scroll manually. The Console auto-selects on "Replay from current step". **Per-step "Debug with AI":** each FAILED step's error block in the Console shows a Sparkles button that opens `StepAiDebugDialog` (`renderer/main/ai-debug-panel.tsx`) — a leaner sibling of the full-run `AiDebugDialog` that streams a focused LLM diagnosis of that single step (step label + Playwright-style locator via `locatorToPrompt` + error + verbose logs) via `buildStepDebugMessages` (`renderer/lib/llm-prompts.ts`). Reuses `useLlmChat`, `ModelPicker`, `CodeBlock`, `parseResponse`, `friendlyError` (exported from `ai-debug-panel.tsx`). No "Apply to script" (these are editable steps, not a script) — just diagnosis + optional corrected-expression snippet + copy. Auto-starts once per unique failed step; Stop/Regenerate buttons. **Step details** — the selected step's element-locator summary + persisted replay diagnostics (the previous per-step panel content) plus the hit-rate pill and a clear (✕) button. Clicking a step row still selects it (accent ring). Per-step diagnostics are persisted per-test in `userData/recorder/debug-logs.json` (via `recorder-debug-store.ts`); the store loads them on session open and listens for `recorder:debugLogs` pushes; the live Console stream is driven separately by `recorder:replayLog` (ephemeral, held in the recorder store's `replayRun`).
  - Script tab supports direct in-app editing (Edit/Save/Cancel) of the generated spec text, independent of the recorded steps. **IDE-style script views:** both the read-only `ScriptView` and the editable `ScriptEditor` (in `renderer/main/script-view.tsx`) render with a line-numbered gutter + regex syntax highlighting (keywords/strings/comments/numbers/decorators) using the design system's `--color-token-*` variables (blue keywords, red strings, gray-italic comments) so they adapt to light/dark. The editor overlays a transparent `<textarea>` on a highlighted `<pre>` (shared font metrics + padding for exact alignment, synced scroll, explicit white caret since `text-transparent` hides the caret in WebKit). Both views use `text-mono font-mono` (13px/18px) — slightly larger than the old `text-small-mono` (11px) for a more legible IDE feel.
  - Import existing Playwright tests: the sidebar + opens a native menu with "Train manually" (the original recorder flow), "Generate from prompt", "Select from files" (pick a local folder), and "From URL" (clone a git repo). Each matched `*.spec.ts`/`*.test.ts` file is parsed into `Step[]` (via `spec-parser.ts`); the verbatim file is kept as the runnable script and the test is `scriptEdited`. Imported tests (`sourceDir` set) are **Script-only** in the detail view — the verbatim file is the source of truth, so the Steps tab is not shown even when steps parsed. Tests created in the app show **both** Steps and Script tabs (Steps primary when there are steps).
  - **Generate test from prompt (phase 3):** the sidebar + menu's "Generate from prompt" opens `GenerateTestDialog` — a separate window where the user describes a test in natural language and the local LLM generates a complete Playwright spec. Pre-selectable common options: test name, starting URL, execution speed (Fast/Medium/Slow, persisted on the `TestRecord`), and browser viewport (Default/Desktop/Laptop/Tablet/Mobile presets — passed into the prompt as a hint). The dialog shows prompt-formatting tips, streams the response with the same formatted rendering as the AI debug panel (prose + fenced code cards), and when the model returns a complete applyable spec (contains `import` and `test(`) a "Create test" button persists it via `tests:createFromPrompt` (creates a `TestRecord` whose `steps` are `parseSpecDetailed`'s reading of the generated source, `scriptEdited: true`, the generated source as the script file) then navigates to it. **The step list is only as good as what the parser can read back**, and a model left to its own devices writes JavaScript, not a step sequence: locators bound to `const`s, `test.step(…)` wrappers, data read out of the page and asserted with `expect(value)`. `GENERATE_SYSTEM_PROMPT` therefore states the round-trippable vocabulary explicitly (see `llm-prompts.ts`) — without it a generated test arrives with a near-empty Steps tab (or none at all: the tab is hidden at zero steps) and an "Edit in Trainer" that offers to regenerate the good script from those two steps.
  - **Visual testing (roadmap complete, Phases 0–5 + post-roadmap):** an optional per-run "Capture screenshots" toggle (default off) next to Run test, plus a "Visual" sidebar tab (grouped with Stats). When the toggle is on, a run of an app-generated test **captures a screenshot after each page action** and persists it under `userData/recorder/artifacts/<testId>/<runId>/<stepIndex>.png` + `manifest.json` + `replay.json` (retained for the newest 10 runs per test). The **Visual tab is a screenshot-replay viewer**: pick a captured run and scrub its steps in a timeline, seeing the screenshot + pass/fail per step with the failure point highlighted (auto-jump + red callout + timeline marker). **Phase 3 adds page-level visual diffing:** each captured step's screenshot is compared against a **pinned baseline** (keyed by `Step.id`; first captured run seeds it, later runs diff against it — never the previous run). A step exceeding a per-test threshold is flagged "visual change detected" (orange badge/callout/timeline marker), with a Current/Baseline/Diff view toggle and a **per-step** "Accept New Baseline" to re-pin an intentional change (the run-level "Accept All & Re-baseline" was deliberately removed on 2026-08-04 — see DECISIONS; `visual:acceptRun` and `api.visual.acceptRun` remain in place, unused by the UI). Diffing is pure-JS (pixelmatch); it degrades to "can't compare" on size mismatch/corrupt images rather than false-flagging. **Phase 4 adds freeform step notes:** any step in the replay timeline can carry one freeform text note (an "Add note" affordance in the step-detail row, editable/clearable), shown inline while scrubbing and marked on the timeline with a message-square icon. **Phase 5 (final)** wired the tab to the real views (done in Phase 2), added a one-path end-to-end regression check (`npm run check:visual-pipeline`), kept retention at 10 (validated against real disk usage), and fixed a retention bug that could delete the pinned baseline. **Post-roadmap additions:** (1) **Ignore/mask regions** — `TestRecord.visualMasks` stores normalized 0–1 rectangles; `diffPngBuffers` paints a solid fill into both images before pixelmatch so masked pixels compare equal. The Visual tab's "Ignore regions" button toggles a `cursor-crosshair` overlay (`MaskLayer` in `visual-view.tsx`) over the screenshot; drag to draw a dashed orange rectangle. A mask with `stepId: null` applies to every step; the "Apply to all steps" switch controls this. The diff badge shows a dashed-square icon when regions were excluded. IPC: `visual:getMasks`/`setMasks`. (2) **Capture-overhead measurement** — the capture fixture times each `page.screenshot()` and writes `captureMs`/`shotCount` into `manifest.json`; the runner stores them on `RunRecord`. Stats shows a "Capture overhead" panel (above the pass/fail chart) with per-run screenshot time, per-screenshot mean, and captured-vs-uncaptured duration. Hidden until at least one instrumented capture run exists. (3) **Age-based artifact retention** — `pruneRuns` takes an optional `maxAgeMs` on top of the count cap; a run survives only if it satisfies both. New setting `artifactRetentionDays` (0 = off, max 365) in Settings → "Delete screenshots older than". Pinned baselines (`baseline/` dir) are excluded from both rules. (4) **Element-scoped (component-level) diffing** — records the acted-on element's bounding box (`elementRect` in `capture-fixture-source.ts`) at capture time; a Page/Element `SegmentedControl` in the step-detail row (only for steps with `step.rect`) toggles between page-wide and element-cropped comparison. The baseline stores its own rect, so each side is cropped by geometry from its own run. IPC: `visual:getElementSteps`/`setElementStep`. Steps whose baseline predates the geometry feature show no toggle; if the user toggles Element on a step whose baseline lacks geometry, the diff reports "the pinned baseline predates element geometry — accept a new baseline to enable it". (5) **Local run notifications** — a macOS notification (`run-notifier.ts` via the SDK `Notification` API) fires when a run fails or flags a visual change; clean runs stay quiet. Gated by Settings → "Notify when a run has problems" (`notifyOnRunIssues`). The macOS notification is local only; external delivery is a SEPARATE, opt-in feature — see the webhook-alerts bullet below (added later; earlier notes calling external alerting "deferred" are stale).
  - **Accessibility checks (axe), gated separately from screenshots:** a per-test **"Check accessibility"** toggle beside "Capture screenshots" (global default `RecorderSettings.defaultA11yChecks`, off) makes the capture fixture inject `axe-core` via `addInitScript` (once per document, resolved from the same `node_modules` the Playwright CLI came from) and run it after each captured action. Gated independently of screenshots because a11y is useful without them and costs far more — `a11yMs`/`a11yChecks` are timed and reported separately from `captureMs` for exactly that reason, and Stats shows the two apart. Violations ride the SAME manifest entries as screenshots (one correlation, in `buildReplay`, so a result can never be attributed to the wrong step), compacted to rule id + impact + help + node targets, capped at 25 violations × 5 nodes. `enrichWithA11y` then diffs them against the test's accepted baseline (`a11y-diff.ts`, pure). **Identity is rule id AND node target** — keying on the rule alone would make accepting one low-contrast label accept every future contrast failure on the page. The baseline lives on the `TestRecord` (`a11yBaseline`), NOT under the artifacts tree, which makes "retention pruned my baseline" structurally impossible rather than a rule to remember; accept-step / accept-run / reset are in `a11y-baseline-ops.ts`. **Reported, never fatal** — nothing here touches `runStatus`, pinned by a source-level assertion in `a11y-diff.test.ts`. **Four surfaces, in decreasing order of how much the user has to go looking:** (1) an **"Accessibility" tab on the test itself** (`a11y-panel.tsx`, last tab, after Heals; hidden for imported tests like Variables/Heals), badged with the unaccepted-step count — it describes the most recent run that CHECKED (`latestA11yRun`), NOT the most recent run, so a later run with the toggle off can't blank the results and read as "fixed"; it carries per-step and whole-run Accept, a **dismiss** on the "not accepted yet" banner, plus **"Reset accepted"**, which is the only UI that has ever reached `a11y:resetBaseline`. The dismiss writes the SAME `RunReplay.dismissedNotices` flag the Visual view's banner uses, because both panels read the same run's replay and "I have seen this run's accessibility findings" is one fact — two flags would let the user dismiss it here and still be nagged about the identical finding one screen over. Only the orange banner is dismissible: the red "completed none" one reports a BROKEN CHECK rather than a finding about the page, and letting that be waved off is how a silently broken axe fixture hides for another few months. All four states of that banner slot centre their copy, since they swap as a run's verdict changes and centring one would look like the banner jumping alignment on its own. (2) A `describeA11yOutcome` line in the run's Output panel. (3) An orange `Accessibility` marker on any run in the Visual run LIST with unaccepted violations. (4) The per-step badge + violation list + Accept in the Visual view itself. **Both (1) and (2) state the number of COMPLETED checks**, because zero of them is a fault and must never read as a clean page (see DECISIONS 2026-08-06). The violation rendering (`a11y-violations.tsx`: `A11yBadge`, `A11yViolationList`, `IMPACT_COLOR`) is shared by the tab and the Visual view — two hand-written copies would eventually disagree about which issues matter. Coverage: `a11y-diff.test.ts`, `a11y-format.test.ts`, `a11y-panel.test.tsx` (one test per situation it must tell apart), `capture-fixture-a11y.dom.test.ts` (the shipped axe callback, evaluated the way Playwright evaluates it), the a11y section of `check:visual-pipeline`, and the tab/run-list markers in `test-detail-view.test.tsx` / `visual-view.test.tsx`.
  - Right-click a test in the sidebar for a context menu: "Reveal in Finder" (highlights the spec file), "Remove from Sidebar" (hides the test from the sidebar view WITHOUT deleting its record or script file — `hidden: true` on the `TestRecord`; the file stays on disk for later restoration), "Duplicate Test" (see the next bullet), and "Adjust Test Speed" submenu with a 3-stop Slow/Medium/Fast slider that sets a Playwright `slowMo` delay for that test's runs (0/400/1200ms).
  - **Duplicate a test** (sidebar right-click → "Duplicate Test"): a new `TestRecord` and a new spec file carrying everything that describes the test — steps (with their ids), variables, datasets, tags, flow flags, visual masks/thresholds/element-scoped steps, and every run preference (speed, browser, headless, timeout, capture/a11y/logs toggles) — and **none of its history**: no runs, screenshots, pinned visual baselines, step notes, Auto-Heal journal or AI debug sessions (all of those live in their own stores keyed by test id, so a fresh id starts empty without anything being deleted), and no `a11yBaseline` (accepted violations describe the ORIGINAL's runs; a copy carrying them would report a clean page it has never been run against). Named `<original> [n]` with the lowest free n from 2 up, counting **hidden** tests so a collision can't be invisible. **Stored secret VALUES are copied** (backend-only, via `testSecretsStore.copyTest`) so the copy actually runs — the handler then refreshes the redaction snapshot, or the copy's password is a value redaction was never told about. A generated spec is regenerated so its `test("…")` carries the new name; a hand-edited or imported one is copied word for word (same trade-off `tests:rename` already makes), and an imported test's whole `scripts/imported/<id>/` sandbox comes across so its relative imports still resolve. **The record is REBUILT from `DUPLICATED_FIELDS`, never spread** — same reasoning as `normalizeRawStep`; `check:duplicate-test` fails while any `TestRecord` field is absent from both that list and `DROPPED_FIELDS`. A warning dialog appears **only when something runner/trainer-related is active** (variables, stored secrets, cookie/capture/`runFlow` steps, datasets, being a flow, hand-edited or imported) — a prompt that always appears is one nobody reads. Files: `main/services/duplicate-test.ts`, `renderer/lib/duplicate-warnings.ts`, `renderer/main/duplicate-test-dialog.tsx`.
  - **Auto-Heal (resilient replay):** during "Replay from current step", when a step's locator fails to resolve, a backend Auto-Heal engine probes the live page for alternative locator candidates using all available context — the step's action/text, freshly generated candidate locators, and hints from past runs' debug logs — retrying per the user's settings. If a candidate makes the step pass, it's auto-applied to the step (marked with a green "Healed ✓" badge in the Console); otherwise the ranked candidates surface in the Console as a menu where the user can pick any suggested target to apply to the step. Settings (in the app Settings window) control retry count and per-attempt timeout, and let the user disable Auto-Heal.
  - **Refine Selector (per-step element picker):** each editable trainer step row that has a locator shows a crosshair "Refine selector" icon (between the ▶ Run/replay and ✕ Delete icons). Clicking it pauses the session and enters a pick mode in the training browser — hovering draws a blue bounding box over components and clicks are intercepted (page doesn't respond). Clicking a component captures its locator candidates (test-id / role / label / placeholder / text / CSS / XPath, best-first), computed CSS, and attributes; a "Refine Selector" review dialog (showing which step is being refined) lets the user pick the best locator and **update that step's locator** (Update selector), then resumes recording. Operates at the step level — it refines an existing step rather than inserting a new one.
  - **Right-click test-tools menu in the training browser:** right-clicking in the recorder window pops a native macOS menu (the window loads an external page we don't own, so the menu is a backend `Menu.popup` from `@glaze/core/backend`, not in-page React). The element under the cursor is resolved via `PICK_AT_POINT_SCRIPT` (`elementFromPoint` + inlined `DOM_HELPERS` → `buildPicked` + the element's current text/value), so menu items are **pre-targeted at that element**. Menu layout: a disabled header showing the target (e.g. `button#submit`) or "No element here"; **Assert element ▸** (visible/hidden/contains-text/exact-text/enabled/disabled/checked/unchecked/value/attribute/count — text/value kinds prefill the element's current text); **Assert page ▸** (URL is… / title is…); **Wait ▸** (for element visible / for element hidden / for duration…); **Refine selector for this element**; **Add step ▸** (Go to URL / Press key / Set viewport / Find element). Picking an item pushes a `recorder:contextAction` event to the main window (`ContextAction` payload: kind + assert?/waitMode? + picked + prefillText/prefillValue), which opens the existing Add-step dialog **prefilled** (locator from the picked element, assert kind / wait mode / text / value seeded) so the user can tweak before inserting at the cursor. Fully additive — the "+ Add step" menu and assert-mode toolbar stay. Coordinate mapping: context-menu `x/y` are DIP; `elementFromPoint` uses CSS client coords, adjusted by `wc.getZoomFactor()` when not 1.
  - **Trainer window URL bar setting:** the recording/editing window's native title bar shows the current page's live URL by default ("Recording — https://…", updated on every navigation) as a stand-in address bar. A Settings toggle ("Show URL bar in training window") lets the user turn this off, reverting to a static title; persisted in `recorder-settings.json`, applied per-session at `recorder:start`.
  - **Default run speed (New Recording dialog + Settings):** the New Recording dialog has a "Run speed" `SegmentedControl` (Slow/Medium/Fast) that reads and writes a persisted `defaultRunSpeed` on `RecorderSettings` (`recorder-settings.json`, **slow by default**). New recordings seed their per-test `speed` from this default in `recorder-service.finalize()`, so the sidebar "Adjust Test Speed" override still works per-test. Settings shows the same control under "Default run speed" so the choice is visible and changeable there too. Same `SegmentedControl` idiom as `GenerateTestDialog`'s execution-speed picker.
  - **Window size preset (New Recording dialog + Settings):** the New Recording dialog has a "Window size" `Select` (Default / Desktop 1280×800 / Laptop 1440×900 / Tablet 768×1024 / Mobile 390×844, from `renderer/lib/viewport-presets.ts`) that reads and writes a persisted `defaultWindowSize` on `RecorderSettings`, mirrored in Settings under "Default window size". The preset does two things at once, and both are needed: the training window OPENS at that PAGE size (`useContentSize`), and the size is recorded as the session's first `viewport` step so the generated spec calls `setViewportSize` BEFORE `goto` and the test REPLAYS at the size it was recorded at. Sizing only the window would make the preset cosmetic — a test recorded at 390×844 would run at Playwright's own 1280×720 and meet a desktop layout it never saw. Re-opening a test in the trainer takes its size from `recordedViewport(steps)` instead of the dialog, and adds no second viewport step.
  - **Window resize as a test step (`viewport`):** a resize can be inserted anywhere in a test, not only at the start. Both "+ Add step → Set viewport" pickers (the trainer's `add-step-dialog.tsx` and the detail view's `edit-steps-view.tsx`) offer the shared presets plus **Custom…** width/height, clamped by `clampViewportAxis` to the same 200–4000 range `normalizeViewport` enforces on the backend, so a typed size is never silently rewritten. A resize row is inline-editable as one `WIDTHxHEIGHT` field (`parseSizeDraft` in `step-row.tsx` accepts `x`, `×` or `,`; an unparseable draft commits NOTHING, because a resize with only a width is not a smaller edit but a broken step) and is **replayable on its own** — the one exclusion from the per-step ▶ that was dropped. - `main/services/step-replayer.ts` — `buildReplayScript(step)` builds an injected IIFE (reusing `DOM_HELPERS`) that resolves the step's locator (getByRole/TestId/Label/Placeholder/Text via attribute/role/text scans; css via querySelector; xpath via `document.evaluate`) and performs the action or evaluates the assertion, returning `{ok,error?,met?,logs}` where `logs` is an ordered `DebugLogLine[]` (timestamp · level · message) with verbose detail: locator kind/value + match count, resolved element tag/id/class, action taken, assertion actual-vs-expected, errors/thrown. - `main/services/batch-runner.ts` — **batch (suite) runs**. `createBatchRunner(deps)` returns `{start, stop, getState}`; `batchRunner` is the app singleton. `start({testIds, captureArtifacts?, runHeadless?, browser?, concurrency?})` queues the tests and runs them **one at a time by default** (`concurrency` absent or 1 — the pre-existing behaviour), or up to `concurrency` at once, awaiting each via `playwrightRunner.waitFor(runId)`, emitting `batch:progress` per transition and `batch:done` at the end. Edge cases it pins: a test deleted after queueing is **skipped** (not fatal); a test already running (`waitFor` → null) is **skipped**, not reported as a bogus failure; a failing test never aborts the batch; `stop()` kills **every** running test and skips the rest while keeping earlier results; only one batch runs at a time (a second `start` returns `{alreadyRunning: true}` with the in-flight id). `summarize(state, now)` is pure (an all-skipped batch is NOT `ok`). **Parallelism is lane-based.** `buildLanes(queue)` partitions the expanded queue into one lane per distinct `testId`; lanes run concurrently up to the limit, entries WITHIN a lane stay sequential. That is not a nicety: the runner keys a live run by `testId` (`runId === testId`), so two entries for one test in flight together make `start()` decline the second with `alreadyRunning` and the row is reported **skipped** — i.e. a dataset sweep would silently run one row instead of all of them. `buildQueue` dedupes the selection so a test's entries are always contiguous, which is what makes flattened lane order identical to queue order and therefore makes `concurrency: 1` the same execution as the old sequential loop. **Two things now multiply a test's entries** — dataset rows and the per-row engine multi-select (`perTest`, validated in the `batch:run` handler by rebuilding each element and filtering `browsers` through `RUN_BROWSERS`, which validates/dedupes/orders in one pass). Both expand *engine-major inside the test*, never across tests, so contiguity — and therefore the lane invariant — survives; the cost is that one test on three engines runs them serially. A test absent from `perTest` falls back to the batch-wide `browser`/`runHeadless`, which is the MCP path. `BatchTestResult.browser` (optional, so `batch-history.json` needs no migration) is what makes three results for one test distinguishable. `clampBatchConcurrency(requested, lanes)` (in `main/recorder/types.ts`) bounds the request by the lane count and `MAX_BATCH_CONCURRENCY` (16); it is applied in the `batch:run` handler AND the runner. `currentIndex` is now **derived** as the lowest-index running entry (-1 idle) rather than assigned by the loop, because it is persisted and pre-parallel `BatchRecord`s are still read back. On completion it fires TWO things through injected seams: `alert` (the opt-in outgoing webhook, failures only) and `notify` (a local macOS notification via `run-notifier`, gated on `notifyOnBatchDone`, default ON, and firing on **success too** — a batch is a job you walk away from). The per-run notification is correspondingly suppressed for batched runs via `shouldNotifyRun`, so a batch with eight failures posts one notification rather than eight. **Deps are injected (`BatchDeps`)** purely so `check:batch-runner` can drive the queue against a fake runner — including asserting runs never overlap, that a swept test's rows never overlap *each other*, and that `stop()` kills all of them — with no browsers or child processes.

- `main/services/input-service.ts` — The native half of a `state` step: moves the training window's REAL pointer via `webContents.sendInputEvent` so `:hover`/`:active` genuinely apply in the trainer preview. Same shape and same reason as `resize-service.ts` — a page can no more move the OS pointer than resize its own window, and `:hover` is a function of pointer position, not an event, so a synthetic `mouseover` applies no style at all. Split by who can answer: the injected replayer resolves the locator and returns the element's centre `point`; this converts it through `getZoomFactor()` and sends the event. Holds the only genuinely stateful thing here — the last pointer position and whether the button is down — because the OS has exactly one of each. - `main/services/resize-service.ts` — applies a `viewport` step during trainer replay by resizing the training window, and reports what it became. `applyViewportStep(win, step, evaluate)` normalizes the size through `normalizeViewport` (the same path the session-open preset takes, so a step and a preset can never resolve to different sizes), calls `setContentSize` (CONTENT, not frame — the recorded number is the page size), reads back `getContentSize()` plus `window.innerWidth/innerHeight` via `PAGE_METRICS_SCRIPT`, and returns the same `{ok,error?,logs}` shape the injected replayer does. `formatResizeLog` prints all THREE sizes because they disagree meaningfully: requested (what the step asked for), window (what the OS granted — it clamps to the display), page (what the document sees — the scrollbar's width is what actually flips a breakpoint). - `main/services/cookie-service.ts` — live cookies + cookie-step application, over `webContents.session.cookies`.   - `shared/metrics-query.mjs` — the curated queries: `stepHealth`, `stepDurationTrend`, `suiteCost`, `browserMatrix`, `failureClusters`, `runEvidence`, `siblingRuns`, `stepDurations` (p50/p95 over two windows), `stepBrowserMatrix` (per STEP, where `browserMatrix` is per test — "step 7 fails on WebKit" sends you to one locator, "this test fails on WebKit" sends you to read the whole test), plus `counts`/`isPopulated`. `stepDurations` computes its percentiles in JS rather than SQL, deliberately: the `LIMIT 1 OFFSET <expression over aggregates>` form SQLite accepted for p95 and rejected for p50 with "datatype mismatch", and because `all()` swallows a throw by contract the broken half came back as `null` and read exactly like "this step was never timed". **No SQL escapes this file** — not into a tool body, a React component or an emitter. That is what makes the plan's "strictly local, per-machine" decision reversible, and why the MCP exposes curated tools instead of a SQL escape hatch. Every function tolerates a null handle, because metrics are unavailable on a runtime without `node:sqlite` and "no data" has to be an ordinary answer.

Kept out of `metrics-query.mjs` because that file has one job and one rule, and out of both callers because the app's panel and the MCP's tool must not be able to disagree about what "diverges" means. `divergentSteps`'s vocabulary deliberately matches `triage.mjs`'s cross-run signals — the same question asked of a whole history rather than one run. **`insufficient` is not `clean`**: 255 of 305 steps on the development machine have only ever run on one engine, and rendering those as clean would give a single-engine suite a clean bill of cross-browser health.
  - `shared/triage.mjs` — `triageRun`, site problem or runner problem, plus the `TRIAGE_COHORT` sibling window both callers must share (or the same run answers differently from the app and from the MCP). Takes a bundle somebody else has read — `runEvidence()`'s run + steps, `siblingRuns()`, and the failing step's `stepHealth()` row — and returns `{ verdict, confidence, evidence, limits, suggestedNext }`. **Evidence is the product; the verdict is a summary of it.** Four rules it is built to: `unknown` is first-class (a run with no artifacts must say so, not reason from pass/fail); it never throws and never touches a run's status, pinned at source level by `check:triage`; anything argued from an ABSENCE is withdrawn when `console_dropped`/`network_dropped` say the absence isn't real; and `limits` costs confidence per entry, so three blind spots are not priced as one. Weighted signals, not booleans — a 5xx on the failing step and a changed screenshot are both site-ward and are not the same claim.

- `main/services/import-service.ts` — Imports existing Playwright tests. `importFromFiles()` opens a native directory picker (`dialog.showOpenDialog`), scans for `*.spec.ts`/`*.test.ts` (skips node_modules/.git/etc, depth+file caps). `importFromGit(url)` shallow-clones (`git clone --depth 1` via `execFile`, validates URL scheme, ENOENT→friendly "git not installed") to an `os.tmpdir()` temp dir, scans, cleans up. - `main/services/spec-parser.ts` — `parseSpec(source) → Step[]`: best-effort reverse of `script-generator.ts`, now round-tripping its **full** vocabulary (not just a subset): `page.goto`/`page.waitForTimeout`/`page.setViewportSize`/`page.keyboard.press`, `<locator>.click|.fill|.selectOption|.check|.uncheck|.press|.waitFor` with `getByTestId/getByRole/getByLabel/getByPlaceholder/getByText/locator(...)` locators, and `expect(...)`/`expect.soft(...)` for all 16 assert kinds (incl. page-level `toHaveURL`/`toHaveTitle`, `.not.toBeChecked`, and `toHaveCSS` — whose second argument selects the match mode, with the `new RegExp(...)` arm checked FIRST so a `contains` assert isn't downgraded to an `is` against a regex source). `.hover()`/`.focus()` parse to `state` steps (they used to count as skips, permanently flagging any imported test that hovered) and `page.mouse.down()`/`.up()` to `press`/`release`. `parseSpecDetailed(source) → {steps, skipped}` (which `parseSpec` wraps) also counts statements that look like actions/assertions but can't be classified — used by the `tests:updateScript` handler to set `TestRecord.stepsDiverged` instead of silently undercounting. Also round-trips conditional blocks: `parseCondition(raw)` reverses `conditionExpr` (element + page conditions, incl. negated `unchecked` and count-based `exists`), a recognized `if (…) {` becomes an `if` step (`ifDepth` counter) and its matching `}` an `endif`; an unrecognized/foreign `if` skips the whole `{…}` block (via `matchBrace`) so no half-parsed `if` is emitted without its `endif`. Conditional waits round-trip too: `stripComments` PRESERVES the generator's trailing `// wait until` marker (the second such exception, alongside `// disabled — skipped:`), and a marked `expect` becomes a `wait` step instead of an `assert` — without it every conditional wait would silently come back as an assertion, since the two compile to the same call. `.waitFor({ state })` now carries its state back as a `waitUntil` (a wait-for-hidden used to parse as a bare wait and regenerate as wait-for-VISIBLE); `state: "detached"` has no counterpart in the model and is counted as unclassified rather than inverted. **Also reads the shapes a MODEL writes, which the generator never emits:** a locator bound to a `const` and used later (`const submit = page.getByRole(…)` … `await submit.click()`) resolves through a per-body variable map, and `expect(submit)` resolves the same way — both halves used to disappear, the declaration as a skip and the *use* as nothing at all, which is how a prompt-generated spec arrived with its `goto` and no actions. A REFINED chain (`.first()`, `.filter()`, `.or()`) is deliberately left unregistered and counted, because storing the base locator would regenerate a selector matching the wrong element; likewise `expect(<jsValue>)` has no step and is now counted rather than ignored. `extractTestBodies` skips `test.step` alongside `test.describe`/`test.beforeEach`: its body runs steps, but it sits INSIDE an already-extracted `test(...)` body that the scan walks through anyway, so matching it emitted every statement twice. `locatorActionStep()` is the single place a `<locator>.<action>(…)` becomes a step, shared by the inline and variable branches so a method added to one can't be missing from the other. Regression coverage: `main/services/__tests__/spec-parser.check.ts` (sections 5–6 cover if/endif, 7–9 cover conditional waits, 18–20 cover `test.step`, locator variables, and what is counted rather than swallowed). **Sandbox note:** `npm run check:spec-parser` (tsx) fails under the agent sandbox with `listen EPERM` (unix socket); run it via `npx esbuild main/services/__tests__/spec-parser.check.ts --bundle --platform=node --format=esm --outfile=$TMPDIR/check.mjs && node $TMPDIR/check.mjs` instead.

- `main/services/playwright-runner.ts` — Resolves `@playwright/test` CLI by scanning candidate node_modules roots; spawns `cli.js test <spec> --config <playwright.config.ts> --headed --browser=<engine> --reporter=line`; installs the chosen engine first if missing; streams output. **Browser selection:** `start({browser?})` resolves explicit → `TestRecord.runBrowser` → `RecorderSettings.defaultRunBrowser`. `isBrowserInstalled(engine)` matches directories by the `<engine>-` prefix, NOT a bare `startsWith` — Playwright also unpacks `chromium_headless_shell-*`, which is not a usable headed browser, so the old `startsWith("chromium")` reported a shell-only install as complete and the run failed at launch. **Awaiting a run:** `start` is fire-and-forget, and the `runs` map can't be used to await one (it holds an entry only while the child process is alive — empty during browser install and after exit but before the `RunRecord` is written), so a separate `inFlight` map holds a per-run promise resolving to the exit code, exposed as `waitFor(runId)` (null when not in flight). This is what batch runs sequence on. `ensureConfig()` writes `playwright.config.ts` next to the specs from `playwright-config-source.ts` since the CLI has no `--slow-mo` flag; **every `ensure*` writer now goes through `writeIfChanged` (compare, then temp-file + atomic rename)** — these are files SHARED by every run, rewritten on every run, while other runs' Playwright processes may be reading them, and truncate-then-write is not atomic. Content is fixed per app build, so after the first run of a session they write nothing at all. **Concurrent browser install** is serialized through an `installs` map keyed by engine: several parallel runs can discover the same missing engine at once, and N `playwright install` processes unpacking into one directory produces a half-written browser that then fails to launch for every later run; the first caller installs and the rest await the same promise (and are told so, since the install's output streams to a different run's Output panel). **`PW_OUTPUT_DIR`** gives each run its own Playwright scratch dir (`<scriptsDir>/test-results/<recordId>`, removed in the `finally`) — the default is derived from the SPEC's path, so two concurrent runs of one spec would share and clean the same folder; the speed→delay table and the per-test timeout rule now live in `run-pacing.ts` and are passed via the `PW_SLOWMO_MS` env var and `--timeout` per run. **Crawl speed:** a `crawl` run of an app-generated test also joins `captureArtifacts || healing || a11y || recordLogs` as a reason to redirect the spec's `@playwright/test` import to the capture fixture, writes `glaze-settle.mjs`, and sets `GLAZE_SETTLE=1` (see `settle-fixture-source.ts`). Settling alone does NOT make the run an artifact run — `artifactRun` gates the prune/`ensureRunDir`/`writeSteps` bookkeeping separately, so a crawl run with healing off doesn't prune the artifact history to create an empty dir. An imported test can't be redirected at all, so it gets the step delay and an explicit "page-settling is skipped for imported tests" line rather than silently slower-but-identical behaviour. **Run persistence:** accumulates visible output per run in `logBuffers` (via `emitOutput`) and on `finally` calls `runHistoryStore.append(...)` (status = exitCode===0?passed:failed) then pushes `runs:changed` before `runner:done`. **Visual-testing capture (Phase 1):** mints a fresh `recordId` uuid per run (used for BOTH the artifacts dir and the `RunRecord` id, so a test's runs stop overwriting each other); when `captureArtifacts && !rec.sourceDir`, calls `ensureCaptureFixture` + `prepareCaptureSpec` (temp `<recordId>.capture.spec.ts` with line-1 `@playwright/test`→`./glaze-capture.mjs`), prunes old run dirs, creates the run dir, and runs the temp spec with env `GLAZE_ARTIFACT_DIR`/`GLAZE_TEST_ID`/`GLAZE_RUN_ID` (`GLAZE_CAPTURE_ARTIFACTS`=1); deletes the temp spec in `finally`; step line map built from the spec actually run. `buildStepLineMap` unchanged (line-preserving redirect). **Phase 2:** accumulates per-step pass/fail in `stepStatusMaps` (via `emitStep`, keyed by the reporter's step index) and, in `finally` when capturing, writes `replay.json` via `buildReplay(...)` — the single place that correlates the reporter statuses + the capture manifest against `Step[]`. **Reporter-attribution gotcha:** the capture fixture WRAPS action methods, so Playwright attributes wrapped actions' step location to `glaze-capture.mjs` and the step-reporter's file guard drops them → wrapped actions (goto/click/fill/…) get NO reporter status on a capture run. So `buildReplay` combines two signals: reporter statuses are authoritative for asserts/waits/page-level steps; a screenshot's presence ⇒ that action ran and passed; and the failing step is the first reported failure, else (for a failed run) the first uncaptured non-control step after the last screenshot. `captureMethod(step)` mirrors the fixture's PAGE_ACTIONS/LOCATOR_ACTIONS to match manifest entries to steps by method (so a misclassification can't cascade-desync the timeline).
- `main/services/capture-fixture-source.ts` — `captureFixtureSource`: the `glaze-capture.mjs` fixture as a raw JS string (bare `"` inside the template literal — escaped quotes trip `no-useless-escape`). - `main/services/page-actions.ts` — `PAGE_ACTIONS` (`goto`/`goBack`/`goForward`/`reload`/`setViewportSize`/`setContent`) and `LOCATOR_ACTIONS` (`click`/`fill`/`check`/`selectOption`/…): the canonical set of page-mutating Playwright methods, plus `actionsLiteral()` to embed them in a fixture source string. **Two** fixtures patch these now (capture screenshots after each; settle waits after each), and they are separate source strings — a second hand-maintained copy would drift the first time an action was added to one, and the failure is silent (the step still runs and still screenshots, it just never settles). - `main/services/settle-fixture-source.ts` — `settleFixtureSource`: the `glaze-settle.mjs` fixture as a raw JS string, written next to the specs like the capture and heal fixtures. `installSettle(page)` patches the `page-actions.ts` methods so that after each action resolves — and **before control returns to the spec** — it awaits `waitForLoadState("load")` (15s cap), `waitForLoadState("networkidle")` (5s cap, expected to time out on a page with an open connection; reported once per run, not per step), then `document.fonts.ready` + a double `requestAnimationFrame` (2s cap). Env-gated on `GLAZE_SETTLE`, set by the runner only for a `crawl`-speed run of an app-generated test. **Never fails a test:** every wait is individually bounded and swallowed, and `withTimeout` attaches a terminal `.catch` — an abandoned wait whose page later navigates would otherwise become an unhandled rejection and fail an otherwise-fine run. Why a fixture and not generated code: a spec is generated once and lives on disk while speed is changed afterwards from the sidebar slider, so emitted `waitForLoadState` calls would silently disagree with the setting.
- `main/services/run-pacing.ts` — pure run-pacing policy, split out of `playwright-runner.ts` so a timeout rule can be tested without bundling the visual pipeline. `SLOW_MO_MS` maps `TestRecord.speed` (`crawl`/`slow`/`medium`/`fast`) → `2500`/`1200`/`400`/`0` ms. `resolveTestTimeoutMs(perTest, settingsDefault, speed)` resolves explicit per-test → Settings default → 60s, then raises a `crawl` run to a `CRAWL_MIN_TEST_TIMEOUT_MS` (5 min) **floor**, returning `{timeoutMs, raised}`. The floor exists because crawl multiplies run time: against the 60s default, choosing the resilient speed would make tests fail. It is a floor, not an override — a longer timeout is left alone — and `raised` is what lets the runner say so in the output rather than changing a timeout silently.

Its own two failure modes are pinned: a scanner that goes blind (harvest floors + one named channel per parsing path) and a send it cannot resolve (which fails rather than being skipped). It skips a balanced `<…>` before the call parens because `api.on<{ status: "begin" | "end" }>("recorder:replayStep", …)` otherwise parses `begin` as the channel.

- `main/services/ui-scale.ts` — the "Font size" setting, implemented as **proportional zoom** rather than a type scale. `attachUiScale(win)` is called once per APP window at creation (`main/index.ts`, `windows/settings-window.ts`, `windows/trainer-panel-window.ts`): it sets `webContents.setZoomFactor` from `RecorderSettings.uiScale` and re-applies on `did-finish-load`, because Chromium resets the factor across a navigation and a window that reloads would otherwise snap back to 100% silently. `applyUiScaleToAllWindows()` is called from the `recorder:setSettings` handler so the change lands while the user is looking at it; it names the three windows rather than enumerating them, and the settings window is in that list explicitly because it is NOT an aux window and is the one window the setting is changed in. **Zoom and not a `--gl-font-scale` multiplier** because the theme is tuned in whole pixels (108 `font-size` declarations, 9.5px labels inside 24px controls inside a 34px strip) — growing the text inside fixed-height chrome clips rather than helps, and zoom re-lays the page out so text and boxes grow together. **The training PAGE is deliberately excluded**, which is the load-bearing property (the training browser's own URL strip IS scaled — it is app chrome, and `recorder-service.ts` is a fourth caller applying `uiScale()` to that view and nothing else): it renders the arbitrary site under test, so scaling it would change what a responsive site serves, what a click lands on and what a visual baseline captures. The module never imports `BrowserWindow`, so there is no `getAllWindows` to reach for; `ui-scale.test.ts` pins that structurally alongside the reload and destroyed-window behaviour. Validation lives in the store, not here — `uiScale` is membership in `UI_SCALES`, never a clamp, because a `0` or `1e9` would draw the Settings window (the only way back) unreadable. **It also owns window SIZING**: `scaled(cssPixels)` converts a layout measurement into points, and `attachUiScale(win, {width, height})` records a window's floor in CSS pixels so it can be re-applied on every change — a floor left in points is a smaller viewport than it was measured for (960 points is 768 CSS px at 125%, under the ~928 the widest toolbar needs). `setMinimumSize` does not resize an already-smaller window on macOS, so a window found under its new floor is grown; one above it is never shrunk. The trainer panel deliberately passes NO floor: its minimum is its docked width, latched for the session in `trainer-panel-window.ts`, because the dock, the follower and `computeUndock` must all agree on one number. Covered by `ui-scale.test.ts` and `e2e/ui-scale.spec.ts` — and the e2e asserts on the renderer's `clientWidth`/`scrollWidth`, never a screenshot, because Playwright captures a zoomed Electron window as a crop at the pre-zoom device scale and a correct viewport photographs as a clipped one.
- `main/services/panel-dock.ts` — **Pure** dock geometry for the trainer panel. `computeDock` (dock-time: splits the browser's footprint into browser + panel, total-preserving, `null` when the display can't hold both at their minimums — unless `DockOptions.preserveBrowserWidth`, for a session recording at a **window-size preset**, where the browser's width is the size the test replays at rather than a footprint the user dragged: the pair's total grows instead of splitting, `BROWSER_MIN_WIDTH` does not apply because a 390-wide mobile preset is deliberately below it, and not fitting the display returns `null` so the panel opens undocked rather than resizing a browser it was told not to), `computePanelFollow` (every move/resize thereafter: places the panel against the browser's edge and does NOT touch the browser — flips to the other side when the preferred one runs out of display, `null` when neither fits so the caller undocks), `computeParkedPanel` (where the panel opens when `computeDock` said no: flush beside the browser if a whole panel fits there, else against the work-area edge that covers LESS of the browser — because "undocked" still has to be a rectangle somebody chose, and a window created with no coordinates is centred on the display, i.e. over the page under test), `computeUndock`, `boundsEqual`, `isDuplicateApply`. The two operations must stay separate: one function serving both re-splits an already-split footprint on every drag, walking the browser a panel-width narrower each time. Pure for the same reason as `recorder-navigation.ts` — display edges, negative-origin monitors and too-narrow screens are all one call here and unreachable by hand.
- `renderer/recorder-chrome/` — the training browser's **URL bar** (`index.tsx` → `recorder-chrome.html`, the fourth Vite entry; `url-bar.tsx` + tests). Renders into `chromeView`, a `WebContentsView` pinned to the top 36pt of the recorder window, above the untrusted page. Shows the live URL with the origin dimmed and the path bright, a copy button, and an **Assert URL** menu (native `Menu.popup` — a React popover would be clipped to the strip's height) that opens a prefilled URL assertion through `recorder:assertUrl`. NOT named `*-window.html`, because it is not a window. Drawn in the `--gl-*` theme layer since 2026-08-12 (`.gl-chrome-strip*` in `screens.css`); reviewable at `?view=chrome` in the browser preview. Its CSP is tighter than the three windows' — this is the app's only owned pixel inside a window whose other occupant is an arbitrary site, and it loads no remote anything.
- `shared/url-assert.mjs` — `urlAssertPrefill(kind, url)`: what a URL assertion's "Expected" field is seeded with. `urlIs` gets the absolute URL (it generates an exact whole-URL match, so anything shorter can never pass); `url`/`urlEndsWith` get the path + query + fragment, because the origin is what differs between environments and asserting it is why those kinds exist. A site root falls back to the HOST rather than suggesting `/`, which as a contains-assertion passes against every URL on every host — a green assertion that tests nothing. Returns `""` for unparseable or non-http URLs rather than something plausible. In `shared/` because four callers on both sides of the IPC boundary need the identical answer: the training browser's URL strip and its right-click menu (backend), and the assert menus in `recording-view.tsx` and `trainer-panel-view.tsx` (renderer).
- `main/services/panel-dock.ts` — pure dock geometry. `computePanelSpan(browser, workArea)` decides the panel's vertical placement for both `computePanelFollow` and `computeParkedPanel`: the panel is pinned to the browser's TOP edge and shrinks to whatever is left above the work area's bottom, down to `PANEL_MIN_HEIGHT`. It replaced "full browser height, then clamp `y`", which was safe and wrong — a default 820pt browser on an ~870pt work area gave the panel about fifty points of vertical travel, after which it stopped following while the browser kept going. Being flush is what *docked* means, so height is the negotiable part. `computeDock` still clamps, correctly: it MOVES the browser too, so it places the pair rather than chasing it.
- `main/windows/trainer-panel-window.ts` — Panel lifecycle (modeled on `settings-window.ts`) + the follower. `openTrainerPanel`/`closeTrainerPanel`/`dock`/`undock`/`isTrainerPanelOpen`/`isTrainerPanelDocked`/`getTrainerPanelDockState`, and `FOLLOW_EVENTS`. `openTrainerPanel(recWindow, {fixedBrowserWidth})` latches a session-long `preserveBrowserWidth` (set by `recorder-service` when the session has a window-size preset) that EVERY later dock reads — the user can undock and re-dock, and a re-dock that forgot it would shrink the browser the first dock left alone. It also suppresses two things that would then be wrong: `undock` skips giving back width the dock never took (that would push the browser past its preset), and `viewportNarrowed` isn't sent, because nothing narrowed (`move`/`moved`/`resize`/`resized`, attached by iteration). **Reentrancy is the whole risk**: docking resizes the browser → `resize` fires → the panel moves → `move` fires. Three defences, all required — every bounds write goes through `applyBounds` (raises an `applying` flag, records the rectangle), `isDuplicateApply` rejects an event echoing a write we just made (the flag alone loses to an event delivered a tick late), and the follower listens to the BROWSER only, never the panel. mabl shipped this loop; it is silent (nothing throws, the app wedges). Degraded paths: full-screen → auto-undock (re-dock on leave), minimize → hide, no room on the display → the panel opens at `computeParkedPanel`'s rectangle + `trainerPanel:undocked` push. The panel's opening x/y are never left off: an omitted coordinate is centred by the window layer, which is on top of the page. That first state can only be FETCHED (`trainerPanel:getState`) — the push announcing it is emitted while the panel is still loading its page, so a panel that opened undocked never hears it.

Both halves are needed and neither is obvious: Chromium pushes a document's title up to the window whenever it changes, so `title: ""` survives only until something in the renderer assigns `document.title` (which the entry point did, from the build-time `__APP_DISPLAY_NAME__`), and an empty `<title>` in `main-window.html` survives only until a library sets one. Any `state` other than `loaded`/`not-loaded` leaves `loaded` unset rather than guessing. **Authentication:** LM Studio's server can be configured to require a bearer token, and when it is, EVERY route 401s — so `localAuthHeaders(provider)` stamps `Authorization: Bearer <token>` on all three LM Studio calls (`/v1/models`, `/api/v0/models`, `/v1/chat/completions`); no stored token means no header, which is the correct request for the default unauthenticated setup. - **Issue tracker** (`main/services/issue-tracker/`) — sending a defect to Linear. Phase 1 is the CONNECTION only: prove a key works and choose where issues will go. Creating issues, uploading images and commenting arrive with the compose dialog and are deliberately absent from the interface, so it cannot be half-implemented and look finished.
  - `types.ts` — the `IssueProvider` contract and the `IssueProviderError` class; re-exports the wire shapes from `renderer/lib/issue-types.ts`. The interface is designed against **two** APIs rather than one, because an interface derived from a single example becomes that example renamed: every decision is one that survives Linear (GraphQL, UUID + human identifier, labels as node ids, team → project, upload-then-reference) **and** GitHub Issues (REST, repo-scoped integers, labels as strings, repo → milestone, markdown-embedded assets). Hence: methods express intent never a route; containers are named by the provider (`ProviderVocabulary`) not by this file; containers nest exactly two levels; and providers are **stateless with respect to the credential** — the key is a parameter, so no provider instance holds a decrypted key for the life of the process. Only Linear is implemented; GitHub exists as the adversary that keeps the shape honest, and an escape hatch through this interface is the signal the abstraction was premature.
  - `linear-provider.ts` — `verify` / `listContainers` / `listSubContainers` over Linear's GraphQL API, with an injectable `fetch` for tests. **No error may carry the key**: a raw fetch rejection can carry the request and a raw body is written by a remote server, so every throw is an `IssueProviderError` built from a status code plus at most a scrubbed, flattened, 300-char GraphQL message. Personal API keys go in `Authorization` **raw, with no `Bearer` prefix** (OAuth tokens use it) — getting that wrong produces a 400 that reads as "your key is bad" and sends people off to regenerate a working key. Linear reports a bad key as a **200 with an `errors` array**, so a status-code check alone misreports it as a parse failure. Remote lists are rebuilt, not trusted; a project is attributed to a team only when it belongs to exactly one, since a Linear project may span teams.
  - `issue-tracker-service.ts` — what the IPC handlers call. The judgement it encodes: **"a key is saved" and "the key works" are different claims and the UI must make both**. `status()` is local and never touches the network; `verify()` is the only thing that does; the verified account is cached **in process and never persisted**, because a claim about right now read off disk at launch is how a revoked key keeps saying Connected. `connect()` **saves before it verifies and does not roll back on failure** — a good key pasted on a dead network should not have to be pasted again. `disconnect()` clears the defaults with the key, since a team id is only meaningful inside the workspace that key opened.
  - `provider-registry.ts` — provider → `{provider, key store}`. A table rather than a direct import so callers already ask "which provider?".
  - `linear-token-store.ts` — the Linear key over `encrypted-secret-store`, same write-only contract as the three above. One key means one workspace, by decision; the filename is provider-specific, so a second provider is a second store rather than a migration.
  - `payload.ts` — **PURE, and the single place the outgoing body is decided.** Pure for the reason `buildAlertPayload` is: it makes the guarantee checkable, and `check:issue-payload` constructs hostile inputs by hand and asserts against the returned object. Four properties are pinned independently: the raw Playwright log NEVER appears (only `errorSignature`'s reduction of its first line); console lines appear for a FAILURE only and only the errors the loader already narrowed to; network entries appear for a failure only and **only when the run had its headers filtered**; header values never appear at all, filtered or not — `FailureRequest` has nowhere to put them, which is stronger than remembering to strip them. `line()` also neutralises backticks, which covers two escapes at once: closing a code span to open a link, and ending the fence the error signature is rendered in.
  - `defect-loader.ts` — the impure half: reads the evidence off disk and hands the builder plain data. Owns two rules that fail silently if forgotten. The RAW RUN LOG never leaves this file — `readLog` is called for exactly one purpose and only the failure LINE continues onward. And network entries are dropped **whole** when `RunLogs.headersFiltered` is false, rather than narrowed: a run captured with `GLAZE_RECORD_ALL_HEADERS=1` holds real Authorization and Cookie values, and not reading them is stronger than filtering them. `readImages` re-reads approved images by filename at send time, bounded twice — `readShot` refuses a traversing name, and this refuses a name the draft never offered.
  - `issue-link-store.ts` — which defects already have issues, keyed **without the run id**. That is the design: a visual difference or an a11y violation reappears every run, so a run-keyed link would report "not filed" every time and produce one duplicate per run. `stepId` is stable across runs. `kind` and `ruleId` are in the key because one step can carry a visual change AND several a11y violations at once. **One derivation (`keyFor`) serves both the writer and the reader** — it had two, they used separators that rendered identically and were not equal, and the symptom was a link that saved fine and could never be found again.
  - `issue-config-store.ts` — default container/sub-container **per provider** (`userData/recorder/issue-tracker-config.json`), mirroring `llm-config-store`. Keyed by provider because a Linear team id means nothing to GitHub. NOT in `RecorderSettings`: these are opaque ids minted by a remote API that stop meaning anything when the key is removed, and a settings key that silently means nothing lies in the "differs from default" count. Values are **rebuilt** on read (bounded, string-only) for the same reason `normalizeRawStep` is — this is JSON on disk that a later feature sends back out in a create request. `undefined` leaves a field alone, `null` clears it; collapsing the two makes clearing impossible to express.
- `shared/deep-link.mjs` (+ hand-written `.d.mts`) — `goodlooks://` parsing, and **the whole validation surface**. In `shared/` because the Electron shell receives the URL and the renderer routes it, and a transcribed copy of the rule is right the day it is written. A deep link is UNTRUSTED INPUT in the same sense as a branch name from a PR head ref: it sits in a Linear issue anyone can edit and is clicked by whoever opens it. It SELECTS A VIEW and nothing else — never runs, writes or deletes. **Dot segments are rejected on the RAW STRING, before `new URL()`**, because the URL parser RESOLVES `..` rather than preserving it (`goodlooks://test/t/run/..` parses to `/t/`): a validator inspecting parsed segments can never see a traversal, because by then it has been applied and silently changed which target the link resolves to. Guarded by `check:deep-link`.
- `main/shell/deep-link.ts` — protocol registration and `open-url`. In `main/shell/` because it imports `electron`. Registered at MODULE SCOPE: on macOS the `open-url` that launched the app fires before `whenReady`, so a listener attached later misses the click that started everything and a cold start opens on the home screen. ### Settings window

Redesigned 2026-08-07 from one flat scroll into a sidebar of eight panes with search. See DECISIONS.md for why this shape.

- `renderer/lib/settings-schema.ts` — the window's shape **as data**, pure and DOM-free so it runs in the node project. `PANES` (id/title/subtitle/group) and `paneSegments()`, which returns RUNS of consecutive panes sharing a group rather than one bucket per group — two separate stretches are ungrouped (Appearance at the top, Diagnostics + Experiments at the bottom), and bucketing by value would render the developer panes directly under Appearance. `SETTING_INDEX` maps every row to its pane, its label, its search keywords and the `RecorderSettings` key it writes (absent for credential-backed and action rows, which is what keeps "reset section" away from the API key and the webhook URL). `searchSettings(query)` is case-insensitive substring over label + keywords + the owning pane's title, every term required — substring rather than fuzzy, because a settings search that returns near-misses is worse than one that returns nothing. `SETTINGS_DEFAULTS` mirrors `recorder-settings-store.ts` (which stays the authority) so the window can say "3 settings differ from the default" without asking the backend; `modifiedKeys`/`resetPatch` build on it, with a `sameValue` that compares arrays and `{width,height}` structurally — reference equality would report an untouched `disabledAestheticEnhancements` as modified on every load. Also the five **clamps** (`clampTestTimeoutSec`, `clampRetainedRuns`, `clampRetentionDays`, `clampHealRetries`, `clampHealTimeoutMs`), lifted out of the old async handlers where the only way to test "9999 runs is refused" was to render a window and fire a change event, plus `formatBytes`. Covered by `settings-schema.test.ts` (118 tests), whose load-bearing assertion is that **every persisted default is surfaced in exactly one pane** — a key in the store with no row is unreachable, a key claimed by two panes shows two different modified-counts for one value, and both are invisible on screen.
- `renderer/settings/settings-controller.tsx` — every piece of state and every handler, lifted wholesale out of the old view. One controller rather than per-pane state because two loads have side effects that must fire when the WINDOW opens, not when a section is looked at: the LLM auto-probe rewrites the configured model when the stored one is no longer installed, and the settings load feeds every pane's modified-count. The ~20 `useState`s for `RecorderSettings` fields collapse into one object plus `save(patch)`; the patch shape is unchanged (one key per `recorder:setSettings` call, merged backend-side), so nothing crossing IPC moved. `save` is **optimistic and does not roll back** on failure — the toast reports it, and a rollback would fight the user's next keystroke. Each load goes through a local `load()` helper whose `try` matters as much as its `.catch`: the calls are made synchronously inside the effect, so a surface that THROWS (a preload that didn't expose it) would abort the effect and skip every load after it. A **resolved** `null` from `recorder:getSettings` is coerced to `{}` for the same reason — it doesn't reach the catch, and the first pane to read a key off null took the whole window down. `SettingsControllerProvider` is the test seam.
- `renderer/settings/settings-view.tsx` — the shell only: `SplitView` + nav + the active pane, search wiring, the reset footer, Escape-to-close (unchanged — a field's own Escape and a Select's must win over closing the window). A search that empties the selected pane moves to the first pane that still has a hit; staying put would show an empty pane beside a sidebar advertising matches elsewhere.
- `renderer/settings/settings-nav.tsx` — the sidebar, **drawn as the `Rail`** since B4 (2026-08-10): the same components the main window's library is built from, so a user who opens Settings recognises the strip down the left as the same object (REDESIGN §B4 asks for "the rail becomes the settings nav"; Settings is its own window here, so there is nothing to swap — recognition is what the sentence actually buys). The search field goes in the rail's pinned `search` slot rather than into the scroller. The row accessory does double duty: match count while searching, modified count otherwise. Panes with no match **leave the list** rather than greying, because greying keeps the list the same length and hides that search narrowed anything. Two behaviour changes came with the swap: rows activate on **click** (`SidebarListItem` fired on `mouseDown` — the documented trap where `fireEvent.click` reports "0 calls"), and selection is announced by `RailRow`'s own `aria-current="true"` rather than a hand-passed `"page"`. The modified-count accessory is a neutral `.gl-chip`, not a blue `Badge` — colour means outcome in this palette, and a coloured count beside a pane name claims something about a result.

### Build, test and preview tooling
- `scripts/bootstrap-worktree.mjs` — `npm run bootstrap`. Symlinks a git worktree's `node_modules` at the main checkout's, so a fresh worktree can run lint/type-check/`test:all` immediately instead of paying a multi-minute install (or, as was the case before this, running none of them: a fresh worktree has no dependency tree at all). **Refuses when the two `package-lock.json` files differ** — a shared tree across branches with different dependencies means an install on one silently rewrites the other's, which surfaces days later as an unexplained version error on a branch nobody touched. `.gitignore` spells `node_modules` without a trailing slash so the symlinked form is still ignored. **The link is not sufficient for `npm run package`**, even when the lockfiles match — see `scripts/verify-package.mjs` for what electron-builder does with it and why that is a silent failure rather than a loud one.
- `scripts/verify-package.mjs` — the two guards around `npm run package`, wired into the script itself (`--preflight` before the build, `--verify` after electron-builder) and re-run by CI on the bundle it packages. **The preflight refuses when `node_modules` is a symlink**, which is what `npm run bootstrap` leaves behind: electron-builder collects dependencies by reading `node_modules` directly, and through a link it finds the direct dependencies and nothing below them — it prints `cannot find path for dependency` naming ~80 of them and then **exits 0**, leaving 175 packages out of the bundle. The `--verify` half is the load-bearing one: it computes the runtime dependency closure from `package.json` + the installed tree and asks the finished `.app` whether each package is *resolvable* from the directory that needs it, using Node's own walk-up rule. Resolving rather than comparing directory listings is deliberate — npm hoists some packages and nests others, both layouts are correct, and a listing comparison calls the nested case a failure. It follows `dependencies` only: `devDependencies` are not shipped and `optionalDependencies` may legitimately be pruned. A short `RUNTIME_CRITICAL` list (`@playwright/test`, `playwright`, `playwright-core`, `axe-core`) is asserted on top, so the error names the consequence — these are resolved *by path* by `playwright-runner.ts`, which is exactly why no bundler can vouch for them. Guarded by `check:package-integrity`, whose fixture bundles every direct dependency and no transitive one, because that is the shape of the real bug and a weaker check goes green on it.
- `scripts/dev-app-bundle.mjs` (+ hand-written `.d.mts`) — what makes `npm run dev` **look like this app**. In development the app is not its own macOS bundle: `electron .` runs `node_modules/electron/dist/Electron.app`, and macOS takes the Dock icon and the first menu bar title from the bundle that is running — so dev showed the Electron atom under an "Electron" menu however the app named itself at runtime. `app.setName()` is not the fix, and calling it would be actively harmful here: it renames `app.getPath("userData")`, which is precisely the redirection `main/shell/user-data.ts` exists to undo. So this clones Electron.app once into `node_modules/.cache/dev-app`, rewrites `CFBundleName`, `CFBundleDisplayName`, `CFBundleExecutable` and the identifier, drops `build-icon.icns` over the bundle's icon, and re-signs; `scripts/dev.mjs` launches that binary instead of `npx electron`. **Renaming the executable is not cosmetic** — macOS falls back to `CFBundleExecutable` for the process name, so a bundle with the right `CFBundleName` and the stock executable still says "Electron" (measured, not assumed). **Re-signing is not optional**: editing `Info.plist` invalidates Electron's ad-hoc signature and Apple Silicon refuses to run the result. It costs ~0.15s and ~0 bytes because `cp -Rc` is an APFS clone, and a stamp file (Electron version + the icon's size and mtime) means it is rebuilt only when one of those changes. **Every failure returns null** and dev falls back to plain Electron — a wrong-looking icon must never be the reason the app won't start. Runs standalone (`node scripts/dev-app-bundle.mjs --force`). A packaged build needs none of this: electron-builder writes both fields from `build.productName` / `build.mac.icon`. Guarded by `check:app-identity`, which builds the real bundle and reads the plist back.
- `scripts/switch-branch.mjs` — the build half of the in-app **branch switcher**. `--repo <primary checkout> --branch <name> --out <builds root>` fetches the ref, checks it out **detached** into its own git worktree under the app's data directory, gives it a `node_modules` (symlink when the lockfiles match, `npm ci` when they don't — bootstrap-worktree *refuses* at that point, but there is no human at a prompt here), runs **the branch's own `npm run build`**, and prints `{ok, appPath}`. `--in-place` builds a directory that is already checked out, which is how "return to my checkout" recovers a checkout that has never been built. Structured events on stdout behind a `##gl-switch##` sentinel; child output on stderr, which the app renders as a live build log. Runs standalone on purpose — a build reachable only by clicking a button in the app is one nobody can debug. **A worktree, never `git checkout` in place**: switching the user's own checkout would discard or block on uncommitted work, rewrite the files of the running app, and leave no way back if the branch fails to build. It refuses to report success unless `build/main/index.js` and `build/main-window.html` both exist — an `npm run build` that exits 0 without them launches a blank window and a clean log.
- **`shell/electron` branch** — the de-Glazed tree: stock Electron + Vite + esbuild, nothing outside `node_modules`, so `npm ci && lint && type-check && test:all && build` all run on a hosted CI runner, which this branch structurally cannot do. Branched from `a61598c` (the port's real merge base, established by comparing all 199 shared source files against each candidate), so `git diff main..shell/electron` is the port itself and the 12 commits of drift arrive by cherry-pick. It carries `.github/workflows/gate.yml` (the real gate on ubuntu; end-to-end + `electron-builder` on macOS) and an `e2e/` suite that drives the actual app through Playwright's `_electron` support. Its browser preview (`renderer/dev/`) has since been ported to `main` — see the next bullet. See `docs/plans/testing-pipeline-and-preview-environments.md` for the phased plan and `docs/DECISIONS.md` (2026-08-07) for why.
- **The browser preview** — `npm run dev:web` runs the whole renderer in an ordinary browser tab against a fake backend, with no native shell and no build slot to take turns over. Four pieces: `preview.html` (the entry — its name is load-bearing, since the renderer build globs `*-window.html` and would otherwise ship it as a fourth window), `renderer/dev/preview-boot.ts` (installs the bridge BEFORE the app entry is imported, mounts the "fixture data, no backend" banner, and honours `?view=` / `?test=` — plus two views mounted INSTEAD OF the app: `?view=specimen` for the primitives, and `?view=settings` for the **Settings window**, which is a separate `BrowserWindow` reachable only through `window:openSettings` and therefore had no browser answer at all before B4. Since 2026-08-12, **`?view=trainer-panel`** and **`?view=chrome`** mount the docked trainer panel and the training browser's URL strip the same way, for the same reason and one step further: the panel is a `BrowserWindow` the backend opens when a session starts and the strip is a `WebContentsView` inside the recorder window, so neither was reachable from a tab at all — which is how both stayed on the component library's stock classes long after every screen they mirror had moved to the theme. The panel preview is boxed to 360px on purpose: a tool row that wraps at 360 and not at 1400 is exactly what it is opened to check. That one re-creates the providers from `renderer/settings/index.tsx` rather than importing it — that module is an entry point and would `createRoot` a second copy — and pulls in `styles.css`, without which the window renders as an unstyled column of buttons), `renderer/dev/preview-bridge.ts` (a `window.glazeAPI` over ~50 typed handlers, **plus `?view=recorder` since B6, and `?view=recorder-editing` since 2026-08-10 for a session CONTINUING an existing test — the only state in which the insert cursor is mid-list and therefore the only one that shows the labelled cursor,** — `RootShell` swaps the outlet for `RecordingView` only while `state.recording`, and nothing in a browser tab can make that true, so the trainer had no address at all; the flag reports a live session over a fixture test's steps, with `pageReady: true` because the view renders a "Loading page…" chip and disables every control until it is. **A push bus and a scripted run since B5a** — `on` was a no-op, which quietly bounded the preview to whatever a view renders before anything happens to it. Everything in this app with a *result* arrives by push, so "Run test" started a run that could never finish and the run panel was only ever reachable in its Running state: the failed console path could not be reviewed at all. `startFakeRun` emits `runner:output` / `runner:step` / `runner:done` on a timer so steps land one at a time, and takes its OUTCOME FROM THE FIXTURE rather than a coin flip — `t-login`'s stored run failed, so `?test=t-login` is a stable address for "show me the failed path". Steps after the failing one are left unreported, as Playwright would leave them. Two signature details are load-bearing and both were bugs first: listeners are called `(event, payload)` because `api.on` reads `args[1]`, and the payload key is `id`, not `testId`. **`startFakeChat` since 2026-08-10** answers `llm:chat` with a canned diagnosis streamed in chunks, and that reply ENDS IN A `glaze-request` BLOCK on purpose: the panel's most intricate surface is everything that happens after the model asks for more data — the card, the fetch, the review, the two-step send — and none of it is reachable without a reply that actually contains the block. Every other way to see it needs a local model installed and cooperating, which no agent and no non-Mac reviewer has) and `renderer/dev/preview-fixtures.ts` — which since B8 carries a **captured run** (`REPLAY`), because `artifacts:list` returning `[]` meant the Visual screen, the largest file in the renderer, only ever rendered its empty state. It has one step of each diff state (match, changed, new-baseline, unable, uncaptured), since a fixture where everything matches exercises one branch of the viewer and hides four; the frames are generated SVG data URIs, because a real PNG is a binary blob nobody can diff in review and a remote image is an egress path `check:renderer-egress` bans outright. Since §6.6's drift strip it also carries `REPLAY_HISTORY` — eight earlier runs of the same test, cloned from `REPLAY` so a step added above cannot go missing from its own history — because drift is a statement about a SERIES and a fixture with one run in it renders nothing at all, the same trap as `artifacts:list` returning `[]`, one level up. It is built by `vite.config.ts` under `--mode preview`, which swaps the three window entries for `preview.html`, sends the output to `build-preview/` so it can never overwrite the packaged renderer, switches `base` from `./` (file://) to `/` (served over http, deep paths), and adds an SPA fallback so any path serves `preview.html`. Under Glaze this was a second standalone config, because the SDK owned the app's build and this project had none of its own; the port gave the app a real Vite config, and a mode is all the difference that was left. **The router uses `createMemoryHistory()`**, so a URL path can never select a view; `?view=stats` / `?test=<id>` ask the router directly instead. Two things the native WebView provides that a tab does not are declared in `preview.html`: `color-scheme` (the app's `Text` resolves to `text-inherit`, so without it every label renders black on black) and an opaque backstop on `html` — behind body, never by overriding `--color-window-bg`, because every `bg-panel` surface depends on that compositing. Guarded by `preview-bridge.test.ts`. `npm run build:preview` emits a static bundle to `build-preview/`.

### Theme layer — `renderer/theme/` (the indie redesign, Phase A)

The bespoke design layer the redesign is built on. See `docs/REDESIGN.md` for the
plan it implements. A2 (tokens, fonts, atmosphere) and A3 (the primitives) landed
2026-08-08 with **nothing consuming them**, deliberately — the app was unchanged
on screen, so a regression in Phase B had exactly one candidate cause. **A4
(2026-08-10) is where that stops being true**: the shell mounts `Atmosphere`,
draws the top strip and the rail out of this layer, and retires the light theme.
The nine screens inside the shell are still the old chrome until Phase B.

- `renderer/theme/tokens.css` — the `--gl-*` custom properties, declared on
  `:root`. Real declarations, not Tailwind theme keys or borrowed SDK names, and
  that is the whole point: this repo has shipped `bg-muted` and the entire
  `border-token-*` family emitting **no CSS at all** for months (DECISIONS
  2026-08-06), because a class that does not exist and one that does are
  indistinguishable in a `.tsx`. A name we declare ourselves is a name
  `check:theme-tokens` can check. Dark only, and the absence of a `.light` block
  is the decision rather than an omission. Carries two rules that are load-bearing
  rather than cosmetic: **colour means outcome** (so selection is neutral white at
  low alpha — `--gl-sel-bg`/`--gl-sel-ring` — never a status hue it would compete
  with), and **AI is a treatment, not a colour** (`--gl-holo`, on borders and
  small marks only, never a text fill). `--gl-status-w: 78px` is a layout
  contract, not styling: it is why a column of status chips has one edge.
- `renderer/theme/fonts.css` + `fonts/` — self-hosted Space Mono and Space
  Grotesk, latin + latin-ext woff2, 92KB for all six files, SIL OFL 1.1 text
  beside them. **No network `src` fallback**: the mockup pulls from
  fonts.googleapis.com, which in a packaged app is an outbound request on every
  launch against an egress posture of one opt-in webhook (DECISIONS 2026-08-04),
  plus a blank-until-loaded flash and a hard failure offline. A missing file
  falls through to the system font instead — legible, obviously wrong to a
  designer, and sends nothing. **The 500 → 400 / 600 → 700 weight mapping lives
  in the `font-weight` RANGE descriptors**, not at the call sites: Space Mono
  ships only 400 and 700, the design leans on 500 and 600, and leaving the
  browser to synthesise means the Glaze WebView and a browser preview disagree
  about what the app looks like. Declaring the 400 file as `100 500` and the 700
  file as `600 900` makes every request match a real face, so no synthesis
  happens at all. Space Grotesk is a genuine variable font (`fvar`/`gvar`/`avar`
  verified in the woff2) and needs none of that. `@font-face` is a declaration,
  not a fetch — nothing loads until a screen actually uses it.
- `renderer/theme/atmosphere.css` + `atmosphere.tsx` — the three global fixed
  layers (grain, vignette, scanlines) and the motion floor. **Motion that reports
  something is not decoration**: a running step must still pulse under `calm`,
  so the two kinds are separated by `data-gl-motion="ambient"` rather than by
  animation name (CSS cannot select on animation-name, and threading a flag
  through every animation string gets missed on the one element nobody
  re-tested). `!important` throughout because the redesign applies animation
  shorthand inline, and a motion setting that loses to the thing it turns off is
  worse than none. **`prefers-reduced-motion: reduce` forces `calm` as a FLOOR** —
  the rule the mockup omits — clamped one-directionally so `still` survives it.
  `resolveAtmo()` is the mechanism (via `useSyncExternalStore`, so the *first*
  paint is already right — with an effect, the one frame a motion-sensitive user
  sees is the animated one); the `@media` rule in the CSS is the backstop for the
  window before React mounts. The layers are **portalled to `document.body`**,
  because a `position: fixed` element inside an ancestor carrying `transform` or
  `filter` positions against that ancestor — not hypothetical in a design built
  on both. Grain is an inline `feTurbulence` data URI (~400 bytes) standing in
  for the mockup's 4.2MB PNG plate; it was always going to look like noise at 3%
  opacity, and this *is* noise.
- The three stylesheets come in through `renderer/styles.css`, which all three
  windows import — **above the `@source` lines**, because `@import` must precede
  every other at-rule and the SDK's build prepends its own two framework imports
  to that file. Below `@source` they would be dropped by any pipeline that does
  not inline them first, which is a stylesheet that silently loses the theme.
- `renderer/theme/tokens.ts` — the narrow set of tokens that a `var()` genuinely
  cannot express, and deliberately small because every value in it is a second
  copy. Three reasons a value qualifies: it gets **concatenated** (`StatusChip`
  draws `tone + "55"` over `tone + "12"`, and CSS cannot append to the result of
  `var()`), it gets **interpolated** (`Temp` mixes along a ramp, which is
  arithmetic on a colour and belongs in a function a test can call), or it is a
  **layout contract a check has to name** (`STATUS_W`). `toneSurface()` and
  `insetRail()` are the only places those two derivations happen — `Btn tone="go"`
  and `StatusChip` share them rather than each writing the hex out.
  `check:theme-tokens` pins every value against its `tokens.css` declaration in
  both directions, and separately pins that **no status hex is ever written into
  a stylesheet**, which is what keeps that single route honest.
- `renderer/theme/primitives/` + `primitives.css` — the fourteen presentational
  components (`Atmosphere` is the fifteenth, from A2), each with its own test
  file. The split between the two is not taste: everything identical on every
  instance is a named class, and only per-instance derived values are inline,
  because **an inline style is invisible to the source-level checks** and
  anything they police needs a rule with a name to point at. The ones carrying a
  real argument rather than a shape: `Temp` (the deviation ramp, §3.4 — dead
  inside ±10%, and it falls to `off` rather than fabricating a median);
  `StatusChip` (fixed width **plus `flex-shrink: 0`**, added in B7 — a width a
  flex row can take back is not a fixed width, and the run-history table's
  status cell proved it by squeezing the chip to nothing beside a "healed" chip,
  so the row reported the heal and silently dropped the outcome; `running` takes
  the holo treatment because running is the *absence* of an outcome, not one of
  them); `StepRow` (status as
  an inset `box-shadow` rail that COMPOSES with the selection ring, so a row can
  be selected and failing at once); `MenuItem` (the consequence line renders
  unconditionally — the honest description of concurrency 8 is a failure mode
  that looks like a flaky suite); `SiteIcon` (monogram by default, favicon
  opt-in, because the mockup's per-row icon lookup is an egress path);
  `CRT` (content never treated, z-610 above the overlays).
- `renderer/main/step-composer.tsx` — **the inline step composer, C §6.2, 2026-08-12.** Was `add-step-dialog.tsx`. Composing a step by hand now happens IN THE LIST, at the insert cursor, in both the main window (`recording-view.tsx`) and the trainer panel (`trainer-panel-view.tsx`). The cursor was added so a step could be placed somewhere other than the end, and the control for placing it then covered up the answer to "where is it going?" — composing in place makes the position part of what you are looking at while you fill the fields in. Both call sites render it through a `composerAt(index)` helper rather than hoisting one element out of the tree, because "between step 3 and step 4" is a position in the list's map, not a place in the component tree; it renders at most once, since `state.cursor` is a single index, and it has a home in the EMPTY list too (the only way to put a step into a session that has captured nothing). **The ten kind forms are unchanged and so are their tests** — the plan's "removes 1,170 lines" does not survive contact and should not: those lines are ten step kinds times their fields, each with behaviour behind it, and deleting them to hit a number would be deleting the feature. What changed is the frame, which had to grow back three things Radix was providing: **Escape** bound on the panel (without it the only way out of a half-filled composer is the mouse); **Add disabled until `build()` returns steps** (a modal can afford an always-enabled confirm that does nothing, because it stays open and "nothing happened" reads as "I have not finished" — a panel in the list cannot, and a button that silently declines is indistinguishable from a broken one); and a **max-width on the body**, since the panel inherits the step list's width where the dialog was `size="large"`. It also exposed a latent bug: the reset effect cleared `locator`, which `TargetElementPicker` — a child — had just seeded from the picked element, and a child's effects run before its parent's. The reset is gone; both call sites `key` the composer on the kind and the picked element, so every open and re-target is a fresh mount and `useState(null)` is the reset. Covered by `step-composer.test.tsx` (the ten forms, plus a `describe` for the panel frame) and by the context-action tests in `trainer-panel-view.test.tsx`, which now query `[data-gl="step-composer"]` rather than `role="dialog"`.
- **Baseline provenance — C §6.6, 2026-08-12.** `renderer/lib/baseline-provenance.ts`, rendered into `CRT`'s `caption` by `useBaselineCaption` in `visual-view.tsx`. The screen asked the user to judge a frame against a baseline and said nothing about the baseline; "these two differ" means something entirely different depending on whether it was pinned yesterday from the same engine or months ago from another. **Three of the plan's six fields do not exist in this app and were not invented**: no COMMIT (nothing reads the user's repository), no WHO ACCEPTED (single-user, no identity), no VIEWPORT (not on `RunRecord`, and a test can resize mid-run so there is no single one to report). What ships is the run, the age, the engine, headed/headless, element-scoped, and **whether the run still exists** — retention prunes run history while a baseline outlives it, so a baseline can be valid and untraceable, which bounds how far the comparison can be trusted. An absent `runBrowser` reads as chromium for a run that EXISTS (history, not a default) and as `null` for one that is gone; the line says "run since pruned" rather than dropping a field, since a provenance line with a hole reads as a rendering bug. Shown only where the baseline is on screen — under the current frame or the diff map it would attribute one frame's history to another, and in Blink it appears only on the baseline half. Stale (30 days) marks amber and only the line, not the frame: an old baseline is not a fault, it is a prompt to look. Covered by `baseline-provenance.test.ts` (the sentence itself, not the DOM) and a `describe` in `visual-view.test.tsx`.
- **The weekly read — C §6.5, 2026-08-12.** `renderer/lib/weekly-digest.ts` (pure) + `renderer/main/digest-panel.tsx`, rendered ABOVE the Stats scroller and outside it. **A READ, NOT THE MOCKUP'S DIGEST PREVIEW**: that sat beside the delivery channels §7.3 removed, and with delivery gone a preview previews nothing. What survived is the question — six panels on that screen are tables and breakdowns answering things the reader already knew they wanted, and none said how the week went. **A quiet week is not a good week**: with no runs it says "Nothing ran this week", never "0 failed" or "all passed", which are true of an empty set, read as good news, and describe the failure mode the app exists against. The week-on-week comparison is what makes it weekly and is OMITTED for a first week rather than compared against zero (which reads as explosive growth and is really a statement about the app being new). Failures are counted per TEST — one test failing three times is one problem, three tests failing once is three — with two named and the rest counted, since a list of five names is a table written in prose and the real table is further down. Flake reuses §6.4's `flakeRuns` rather than adding a second definition; **that function wants ONE test's history, OLDEST FIRST**, and sorted the other way it silently finds nothing (`cost-model`'s own `realRuns` re-sorts for the same reason). The panel renders nothing with no history at all, but a suite whose history is all older than a week still gets it — "nothing ran this week" is the most useful thing it can say about a suite that has gone quiet. Covered by `weekly-digest.test.ts` and `digest-panel.test.tsx`.
- **Stats → Report, the Export panel — C §6.5, 2026-08-12.** `main/services/report-emitter.ts` (gather, redact, save), the `report:emit` IPC channel, and `renderer/main/report-panel.tsx` under Cost in Stats. The panel renders `shared/emitters.mjs`'s own `EMITTERS` array rather than a copy, so an emitter added to the module cannot be forgotten in the UI. **THE RENDERER NEVER HOLDS THE EMITTED TEXT, and that is the shape of the feature rather than an implementation detail**: `redactWithSnapshot` reads an encrypted store that cannot leave the main process, so a channel returning bytes would move the un-redacted payload across the IPC boundary first and leave the redaction applied to a copy. The channel is therefore a VERB — it answers with a path, a byte count and a row count. `check:emit-redaction` pins all three halves: every emitter call in the service passes `redact: redactWithSnapshot`, none reaches for `NO_REDACTION` (the escape hatch that exists for the MCP and for tests, and which would satisfy the first check while defeating it), and no `report:` channel returns text; it strips comments before that second scan, because the first version went red on the service's own comment explaining the rule — a guard that fires on the sentence documenting it teaches people to delete the documentation. `listLive` rather than `list`, because a run whose test was deleted has its name dropped and a report row reading "undefined" is worse than one fewer row. A cancelled save is an ANSWER and raises no toast; "last written" is keyed per emitter, since one shared slot would make a second export look like it replaced the first. The mockup's PDF and "public link" chips and its channel toggles are not built — see §6.5. Covered by `report-panel.test.tsx` and `check:emit-redaction`; the preview bridge answers `report:emit` with the CANCEL the real dialog reports, because a browser tab has no filesystem and a fake success would put a path on screen naming a file nobody can open.
- **The emitters — C §6.5 / §7.3 (MCP Phase 5), 2026-08-12.** `shared/emitters.mjs` + hand-written `.d.mts`, tested from `main/services/emitters.test.ts`. Five formats: JUnit XML, GitHub Actions annotations, ticket markdown, OTLP JSON trace, and NDJSON/CSV of `step_metrics`. **EMIT, NOT SEND, AND THE MODULE IS WHERE THAT IS ENFORCED** — every function returns a STRING, so there is nowhere in it to open a socket, store a credential or know a hostname; that is REDESIGN §10's open question 3 answered by construction rather than by policy. Redaction is passed IN as a parameter because `redactWithSnapshot` reads an encrypted store and must stay app-side; importing it would make the module impure and untestable at once. In `shared/` because the app and the standalone MCP both emit and §7.3 says to build them once — hence `.mjs` + `.d.mts`, since the app is bundled TypeScript and the MCP is plain ESM with no build step. The test lives under `main/` for the reason `branch-paths.test.ts` gives: vitest's node project globs `main/**/*.test.ts`, so a test beside the module would match NEITHER project and pass by never running. `EMITTERS` is exported as DATA and the panel will render it, so an emitter cannot be added to the module and forgotten in the UI; `risk` is set on the three that carry more than outcomes (OTLP's span attributes include the URL under test; NDJSON/CSV are unaggregated per-step rows) and stated per-emitter rather than once at the top, since a general warning about "exports" is not read as being about the row under the cursor. The mockup's PDF and "public link" chips and its channel toggles are NOT built — see §6.5. **Not yet wired to any surface**: the Export panel and the weekly digest are the remaining halves of §6.5.
- **The job ticker — C §6.8, 2026-08-12.** `renderer/lib/job-ticker.ts` (the reading, pure) + `renderer/main/job-ticker.tsx` (the subscription and markup), filling the second of the two slots `top-strip.tsx` shipped empty in A4. **Its data source is `recorder-store`** — REDESIGN §10's open question 2, answered from the codebase: that store already owns the live run map and is the one provider mounted for the whole session, and its own `runs:changed` comment argues that a subscription on a ROUTE component is not listening on any other route. **Which made the batch half a bug fix:** `batch:progress` had exactly one subscriber, `batch-view`, so a batch you started and walked away from was invisible everywhere else, and the `batch:done` cache invalidation only fired if you happened to be looking at that screen. Both moved onto the store; the view keeps its own `batch`, which answers a different question ("the record I am displaying", possibly a historical one). Five readings: one run (named — with one job the name IS the information), several (counted — five names do not fit and a truncated list lies about which five), batch (which outranks its own member runs, since they are in the run map too), a held failure, and idle, which renders **nothing** — an "idle" chip is a permanent word in the chrome that is true and useless, and the ticker's PRESENCE is the signal. Every label leads with its state because the strip truncates: the first version put the verb last and FAILED was the first thing cut. `RunInfo` gained `finishedAt` for the hold — measured from `startedAt`, a run longer than the window is expired before it finishes, which kills the one notice the feature exists to give. - **The region breakdown ("what moved") — C §6.6, 2026-08-12.** Backend clustering in `main/services/visual-diff.ts`, wording in `renderer/lib/diff-regions.ts`, boxes and the ranked list in `visual-view.tsx`. A diff map lights every changed pixel with equal weight, so a paragraph of font smoothing and a button that moved 40px look identical; this turns the same pixels into measured boxes, ranked by how much of the change each holds. **A COARSE GRID, NOT PER-PIXEL CONNECTED COMPONENTS** — per-pixel components on a 1280×3000 screenshot produce hundreds of antialiasing specks, which is the noise the feature exists to see past, reproduced in a new shape and ranked above real change; snapping to a grid first merges a paragraph's smoothing into one region and keeps a moved button its own, at 40×95 cells rather than 3.8M pixels. The changed-pixel mask is read back off the overlay pixelmatch already drew — it writes unchanged pixels as GREYSCALE and changed ones in a marker colour, so "r, g and b are not all equal" identifies them exactly; both marker colours are passed explicitly rather than defaulted, because that invariant is the only thing making it safe. - **Baseline drift — C §6.6, 2026-08-12.** `renderer/lib/baseline-drift.ts`, rendered by `StepDrift` in `visual-view.tsx` as a 20px strip under the step row. Every other mode on this screen answers "did this frame change?" for ONE run; nothing in the app could answer the one that follows — is it changing *repeatedly*? Those have different fixes: a frame that changed once is a change to look at, a frame over threshold in six of the last ten runs is a baseline nobody re-pinned, and reading it one run at a time makes one standing problem look like six small ones. **A run with no reading is a gap, never a zero** — a skipped step, capture off, a run predating the step or an `unable` comparison measured nothing, and a zero-height bar says the frame was identical, which is a claim nobody made. That distinction is pure geometry inside a 20px strip and **it shipped collapsed once already**, with `MIN_BAR` flooring a bar at one pixel — indistinguishable from the dash meaning no reading; `check:drift-gap` now pins both halves of the fix (a floor thick enough to read as a bar, and a gap marker lifted clear of the baseline bars stand on), because jsdom has no layout engine and the `dom` project runs with `css: false`. **A single change is never drift**, which falls out of `MIN_RUNS_FOR_DRIFT` and `DRIFT_SHARE` together rather than out of a branch — one edit, one moved frame, one re-pin is the ordinary case and the thing this most easily cries wolf about — so a test pins it across the whole window range. Only `drifting` takes a colour, in the amber the changed bars already use. - **The three metrics panels** (Phase 4), rendered by `stats-view.tsx` below Stability, each from its own `metrics:*` handler and its own react-query key so they fail and refresh independently. `step-health-panel.tsx` — the join table, one row per step across all history, client-sortable over rows the query already ordered worst-first and paged 25 at a time (sort first, then page — the other order ranks only what's on screen); every count travels with its denominator ("4 heals" means different things across 5 runs and across 400), and a null duration renders as a dash, never a 0 that would sort to the top of "fastest". `suite-cost-panel.tsx` — what the instrumentation costs (capture and a11y, both MEASURED; the speed setting is reported separately because it is derivable but not recorded as a total, and an estimate beside two measurements reads as a third measurement) plus the steps whose median grew; when no step has two full windows it says *why* the trend is empty rather than reporting "no slowdowns", which on a young history reads as a clean bill of health. `divergence-panel.tsx` — only the steps that disagree across engines, with `insufficient` summarised as a count; the "no step disagrees" reassurance is withheld entirely unless at least one step was actually compared. Covered by `metrics-panels.test.tsx`.
- `RunTriage` (`run-triage.tsx`) — one line under the Output panel's header, for a finished FAILED run with a `recordId`, over `runs:triage` → `shared/triage.mjs`. Shows the verdict, its confidence, and **the strongest piece of evidence unconditionally** — a verdict word on its own is an assertion people either believe or ignore. The rest of the evidence and all of `limits` sit behind one disclosure, together: the limits are why a verdict is soft, and separating them invites the verdict to be read without them. An `unknown` verdict **renders** rather than hiding, because an uncaptured failure is exactly the case where the user can act (turn capture on, run again); only a null result — metrics unavailable, or no rows for this run — renders nothing. Not a `Tooltip`: Radix tooltips can't be opened under jsdom, and this is the part of the feature where being wrong is quiet. Stale responses are dropped by a `current` flag, or a slow verdict for the previous run paints onto the next one. **On the `Verdict` primitive since B5a**, and TWO OF THE FOUR VERDICTS CARRY NO TONE: `site` is amber (caution, go and look there) and `runner` is red (the failure is in the test you wrote), but `mixed` and `unknown` are the classifier declining to call it, and colouring either would have the component assert what the reasoning behind it refused to — so `Verdict`'s `tone` became optional with a neutral dot, the same contract `StatusChip` already had. Never phos: the run has already failed, and a green dot anywhere on this panel reads as a pass whatever the sentence beside it says. Covered by `run-triage.test.tsx`, plus a pair in `ai-debug-icons.test.tsx` pinning that the line cannot disturb the sparkle beside it.
- `RunSummaryPanel` (`run-summary-panel.tsx`) + `summariseRun` (`renderer/lib/run-summary.ts`) — **C §6.1, 2026-08-12.** The five panels a run that did NOT fail deserves. The detail view used to be shaped around failure — a verdict chip, a triage line and a log — which is right for the run you arrived at because something broke and wrong for every other one: a passed run's panel was a green word over eight lines of Playwright's own chatter, answering nothing anybody came to ask. Each state now answers its own question: `never` what pressing Run would do, `running` how far in (a determinate bar over `stepStatus`, plus an elapsed clock the view ticks itself — a run WAITING streams no log, and those are exactly the runs somebody is watching the clock on), `passed` what held (duration as a `Temp` against the median of this test's previous PASSED runs, steps, capture, and any unaccepted a11y violations), `healed` what Auto-Heal substituted and how much of it nobody has reviewed, `retry` what was different between the failure and the pass. `failed` renders nothing here — `RunTriage` is that state's panel, and a summary above it would put a description of the failure over the explanation of it. **The decision and the arithmetic are pure and separate from the markup**, which is what lets the claims that would be silent if wrong be tested directly: healed beats retry, an absent `healFailedSteps` is null and never 0, an absent `speed` is Unknown and never fast, one run is not a median. Two states carry AMBER despite the run passing (`healed`, and a `retry` where nothing differed) — a mis-heal usually succeeds, so a healed pass is the run most worth distrusting and the one that looks most trustworthy. Fed from `["runs"]` and `["heals", id]`, both of which `test-detail-view.tsx` already holds for its tab badges, so the summary costs nothing extra. Covered by `run-summary.test.ts` (the state table) and `run-summary-panel.test.tsx` (the rendering and the tones); all six states are visible at `?view=specimen`, because the preview's fixtures only ever reach one of them.
- `RunOutput` (`run-output.tsx`) — **reskinned in B5a**. The verdict is a `StatusChip` (one shape, one width, the palette's tones) rather than an SDK `Status` badge, and `running` takes the holo treatment instead of a hue: running is the ABSENCE of an outcome, and a colour there makes a run still in flight look like one that finished and reported. The log is `.gl-console` on `--gl-black` — the only true #000 in the palette, reserved for this and the backing behind a captured frame, because Playwright's output is evidence and should not look like our chrome. **The log expands.** The panel is a 224px strip, about eight lines: enough to see that something failed and never enough to read the stack, so anyone diagnosing a failure was scrolling a viewport the size of a business card while the step list above sat idle. Expanding hands it the whole pane (`flex: 1 1 auto`, so it takes what the window has rather than a number written in the stylesheet); it is a drawer rather than a modal because the verdict, the triage line and the log are one thought. Not persisted — a panel that stayed expanded would hide the step list on the next test opened, for a run nobody had looked at. Icon-only "Copy output" (Copy/Check toggle) copies via `window.glazeAPI.clipboard.writeText`; when the run failed (`code !== 0`) a "Debug with AI" (`Sparkles`) button opens `AiDebugDialog` (owned by `test-detail-view.tsx`, which has the test/script context `RunOutput` doesn't). **Extended in C §6.1:** the panel is rendered ALWAYS, not only once something has run in this session — opening a test cold said nothing about it at all, not even that it had never run — and it drops the log (there is none) rather than the panel. The chip reports the six states via `chipFor`, not pass/fail. Without a log the panel is `flex: 0 0 auto`; the summary's own cap is `40vh` and NOT a percentage, because the panel's height is then content-driven and indefinite, against which a percentage `max-height` resolves to `none` and silently does nothing — the symptom is a panel that renders correctly and is cut off at the window edge, with the scrollbar that would have revealed the rest never appearing.
- `AiDebugDialog` uses `Dialog` in props mode with no `onConfirm` (so no auto footer) — dismissible only via Esc/outside-click, per the documented Dialog pitfall; body renders its own Stop/Regenerate/Apply-to-script/Copy action row plus a `ScrollArea` that renders parsed segments (prose `<p>` + `CodeBlock` cards) via `renderer/lib/parse-llm-response.ts`. `AlertDialog` confirms the script overwrite before applying.
- `CustomContextMenu`/`...Sub`/`...SubContent` (sidebar row right-click) — used instead of native `ContextMenu` specifically because the "Adjust Test Speed" submenu embeds a `Slider` (arbitrary React content); native `ContextMenu` is NSMenu-backed and can't host custom widgets. `CustomContextMenuTrigger asChild` wraps a plain (non-forwardRef) `SidebarListItem` fine — Radix's `asChild`/`cloneElement` only needs the child to spread `...props` onto its DOM node, no ref required.
- `Callout` (`color="yellow"`, `icon={<TriangleAlert/>}`, `<Callout.Text>`) in `test-detail-view.tsx` — shown above the Steps/Script tabs when `test.stepsDiverged` is true (script has statements the parser couldn't map back to steps after an edit) AND `stepsDivergedDismissed` is not set. **Dismissible** (`tests:dismissDiverged`), and the dismissal is persisted on the record: `stepsDiverged` stays true, so everything else reading it — the run comparison, the MCP — keeps saying so, and only the banner is silenced. The backend re-arms it whenever divergence is established AFRESH (a `tests:updateScript` re-parse that skips statements, or a `tests:updateSteps` save left out of the script), so an old acknowledgement can never hide a new problem.

### Data & storage
- `userData/recorder/tests.json` — array of `TestRecord`.
- `userData/recorder/scripts/<id>.spec.ts` — generated specs. A `node_modules` symlink → app node_modules is created here so specs resolve `@playwright/test`. **`ensureModuleResolution` REPAIRS that link, it does not merely create a missing one.** The scripts dir outlives the build that made the link: adopting a legacy Glaze store (`main/shell/user-data.ts`) inherits the old install's link, still pointing into the SDK tree, and the spec then resolves a *second* copy of `@playwright/test` while the CLI runs from ours — which fails every run at collection with "Playwright Test did not expect test() to be called here". It `lstat`s rather than `existsSync`, because `existsSync` follows symlinks and so answers `false` for a dangling one, which is exactly the case that has to be repaired. A real directory is left alone. Covered by `main/services/module-resolution.test.ts`.
- `userData/recorder/browsers/` — Playwright browser install (`PLAYWRIGHT_BROWSERS_PATH`).
- `userData/recorder/run-history.json` — array of `RunRecord` (run stats index; capped 1000). `userData/recorder/logs/<runId>.log` — raw console output per run. These two are deleted independently (see the Stats feature): reset-stats keeps the `.log` files. `RunRecord.id` is now minted at run START by the runner (passed into `append`) so it equals the artifacts `runId`.
- `userData/recorder/artifacts/<testId>/<runId>/` — **visual-testing screenshots (Phase 1)**: `<stepIndex>.png` (0-based page-action order) + `manifest.json` (`{testId,runId,title,status,startedAt,finishedAt,steps:[{index,action,target,value,ok,ts}]}`). `runId` === `RunRecord.id`. Written by the `glaze-capture.mjs` fixture inside the Playwright worker; NOT inlined into tests.json (binary blobs kept out of the JSON store). Retention: newest 10 run dirs per test (`artifact-store.ts`). Deleted with the test via `tests:delete`. **Phase 2:** the run dir also holds `replay.json` — the canonical per-step replay model (`{testId,runId,testName,url,status,startedAt,finishedAt,failedIndex,visualThreshold?,steps:[{index,stepId,label,type,status,screenshot,diff?}]}`, aligned to `Step[]` index, `screenshot` a filename or null). Written by the runner (`buildReplay`), read by the Visual tab. Runs captured before Phase 2 lack `replay.json` so they don't appear in the replay list. **Phase 3 (visual diffing):** each `ReplayStep` also carries `diff?: {state:"new-baseline"|"match"|"changed"|"unable", ratio?, threshold?, reason?, diffFile?}` and the run dir holds `<stepIndex>.diff.png` overlays for `changed` steps. **Pinned baselines** live at `userData/recorder/artifacts/<testId>/baseline/<stepId>.png` + `baseline.json` (`{testId,updatedAt,steps:{[stepId]:{stepId,runId,at,label}}}`) — keyed by `Step.id` (NOT URL: a test is a deterministic script and Step.id survives reorder/insert; only screenshot-producing steps get a baseline). Managed by `baseline-store.ts`; deleted with the test via `tests:delete`. The first captured run seeds baselines; later runs diff against the PINNED baseline (never the previous run). Diffing is pure-JS (`visual-diff.ts` → pixelmatch + pngjs, no native bindings); size mismatch (viewport/responsive change) or a decode error degrades to `state:"unable"`, never a false flag. Per-test threshold on `TestRecord.visualThreshold` (percent of pixels, default `DEFAULT_VISUAL_THRESHOLD` = 0.1 in `recorder/types.ts`).

Written **write-through** by the batch runner after every per-test transition, and by the MCP server's `run_batch` in the same shape — so a batch driven from an MCP client appears in the app's Batch view. Joined to individual runs by `RunRecord.batchId`.

Deliberately its own index file (mirrors `tests.json`'s pattern) rather than embedded in `replay.json`, since `replay.json` is a runner-owned model fully regenerated every run — annotations must survive that regeneration and outlive artifact retention pruning. ### IPC channels
- Invoke: `recorder:start {url,name,testId?,viewport?}` (testId seeds the session from an existing `TestRecord` — its steps/url/name/createdAt win over the passed url/name, and so does its recorded viewport; `viewport` is the New Recording dialog's window-size preset, normalized by `normalizeViewport` and recorded as the session's first `viewport` step) / `recorder:pause` / `recorder:resume` / `recorder:setAssert {mode,soft?}` / `recorder:deleteStep {stepId}` / `recorder:insertStep {step,index?}` / `recorder:reorderStep {stepId,toIndex}` / `recorder:updateStep {stepId,patch}` / `recorder:setCursor {index}` / `recorder:replayStep {stepId}` → `{ok,error?}` / `recorder:startRefine` / `recorder:endRefine` (Refine Selector picker: startRefine pauses + enters pick mode, endRefine resumes; both take no args — the target step is tracked renderer-side in `refiningStepId`, and a pick updates that step's locator rather than inserting a new step) / `recorder:stop` / `recorder:getState` → `RecorderState` (now includes `editing`, `assertSoft`, `cursor`, `refineMode`). Push: `recorder:steps` (full `Step[]`, after every mutation — replaces the old per-step `recorder:step`) and `recorder:picked` (`PickedElement` — an element captured via Refine Selector).
- Invoke: `trainerPanel:dock` / `trainerPanel:undock` → `{docked}`. Push: `trainerPanel:docked {width}` / `trainerPanel:undocked {reason}` / `trainerPanel:viewportNarrowed {width}`. Dock state lives in the BACKEND (it moves real windows) and the panel's button follows the push rather than flipping optimistically — a dock can legitimately be refused on a display too small to hold both windows, and an inverted label makes the control look dead. `viewportNarrowed` fires once per session because docking shrinks the training browser, so a responsive site may render a layout the user did not choose.
- Invoke: `recorder:getSteps` → `Step[]` — the session's current steps, for a window that opened AFTER the initial `recorder:steps` push (that push fires inside `recorder:start`, so the docked panel never sees it). The store calls this on mount alongside `getState` and sets `stepsLoaded`; both trainers gate `controlsDisabled` on it, because acting on a step list you have not received yet inserts at the wrong position. The insert cursor opens at `initialCursor(editing, stepCount)` — index 1 when continuing an existing test, since opening a session executes only the initial navigation. **A replay moves it too** (`cursorPastReplayed`, 2026-08-10): the cursor marks where the BROWSER is, and a replay executes more than the navigation. Without that half, replaying to reach a state and then recording wrote the new step in BEFORE the steps that reach it — the same silent wrong-order failure the initial cursor was added to stop. Pinned by `check:insert-cursor`.
- Invoke: `recorder:getSettings` → `RecorderSettings` (includes `defaultTestTimeoutMs`, default 60000) / `recorder:setSettings {…}` → `RecorderSettings`, backed by `recorder-settings-store.ts`. Snapshotted into the session at `recorder:start` (a mid-session toggle doesn't affect an already-open trainer window; it takes effect next time a trainer window opens). Per-test Playwright timeout override: `tests:setTestTimeout {id, testTimeoutMs: number|null}` (null clears); runner resolves override → Settings default → 60s and passes `--timeout=` + `PW_TEST_TIMEOUT_MS`.
- Invoke (Auto-Heal): `recorder:applyHeal {stepId, locator}` → applies a chosen heal candidate's `Locator` to the step (thin wrapper over `updateStep`, then broadcasts `recorder:steps`). Heals reach the renderer on the `recorder:replayLog` `step` event's `heal` field, which the Console renders as candidates/badge. **There is no `recorder:healSuggestion` push** — it existed until 2026-08-09 and nothing ever subscribed to it. Note the consequence, because it is a real gap rather than a tidy-up: only `replayFromCurrent` forwards its `HealResult` onto `replayLog`; the other three callers of `tryHeal` (single-step preview, `replayAll`, `replayFromStart`) keep `okWithHeal` and drop the candidates, so for those paths the candidates exist only in the journal (the Heals view) and nowhere on screen. **Auto-Heal replay flow (`tryHeal` + `healAndRetry` in `recorder-service.ts`):** Auto-Heal runs in **all four** replay paths — `replayStep` (single-step preview), `replayFromStart`, `replayAll` (Edit-in-Trainer auto-run), and `replayFromCurrent`. It was originally wired into `replayFromCurrent` only; the shared re-run wiring now lives in `healAndRetry(wc, step, index, error)`, which every path calls, and structural `if` steps are excluded in the loop paths (no healable target). Guarded by `check:auto-heal-wiring`. When a step fails with an element-not-found error AND `autoHealEnabled`, it runs `healStep`, and if candidates are found it re-runs the step with the best candidate; on success it sets `heal.ok=true`, `heal.autoApplied=true`, `heal.appliedLocator`, auto-applies the locator to the step, and treats the step as passed. Otherwise the (un-applied) candidates stream to the Console for the user to pick manually.
- Invoke: `tests:list` / `tests:get {id}` / `tests:getScript {id}` / `tests:delete {id}` / `tests:rename {id,name}` (skips script regen if `scriptEdited`) / `tests:updateScript {id,source}` (writes the spec file, sets `scriptEdited: true`; for non-imported tests also resyncs `steps` via `parseSpecDetailed` and sets `stepsDiverged` when any statement couldn't be classified — surfaced as a `Callout` in `test-detail-view.tsx`) / `tests:setSpeed {id,speed}` → `TestRecord` (`speed` is `"slow"|"medium"|"fast"`, validated in the handler) / `tests:setHidden {id,hidden}` → `TestRecord | null` (toggles sidebar visibility; no file deletion).

- Invoke: `tests:duplicate {id}` → `TestRecord` (the new copy). Runs `duplicateTest` (record + spec + imported sandbox), then `testSecretsStore.copyTest` + `refreshSecretSnapshot()`. Throws on an unknown id, and on a hand-edited/imported test whose spec file has gone missing — there is nothing to rebuild it from.
- Invoke: `tests:setTags {id, tags}` → `TestRecord`. `tags` is typed `unknown` and passed through `normalizeTags` (trim, collapse inner whitespace, dedupe case-insensitively with first spelling winning, sort, cap 20 tags × 32 chars) — it sits directly behind IPC, so a non-array or non-string entries normalize to `[]` rather than throwing or persisting junk into `tests.json`. Idempotent, so repeated saves don't churn the record.
- Invoke: `tests:deleteTag {tag}` → `{tag, removed}`. Removes the tag from every record carrying it (case-insensitive, hidden tests included). `tag` is typed `unknown` and goes through `normalizeTags` too, so canonical form has exactly one definition; anything that normalizes away throws "A tag is required" rather than touching the library. `removed` is the true count and can exceed what the renderer previewed, since `tests:list` excludes hidden tests.

- Invoke (branch switcher): `branches:status` → `BranchStatus` (`{available, reason?, checkout?, appPath?, repo?, current?, switched, hasToken}` — **never throws**; the library sidebar gates its "Branches" row on `available`, and the browser preview's fake bridge answers it `available: false` explicitly rather than letting `defaultFor` return null) / `branches:listPulls` → `PullRequestSummary[]` / `branches:listBranches {refresh}` → `BranchSummary[]` / `branches:switch {branch}` → `{appPath}` (resolves as the relaunch is scheduled — the process is gone a moment later, so the caller should expect the window to disappear rather than render a success state) / `branches:home` → `{appPath}` / `branches:setToken {token}` → `{hasToken:true}` / `branches:clearToken` → `{hasToken:false}`. ### Conventions & constraints
- **External Claude Code collaboration:** `CLAUDE.md` (repo root, tracked in git) is a handoff doc for a Claude Code CLI session run directly in this folder — architecture, directory map, hard constraints (forbidden imports, protected dirs, npmrc rules), SDK reference paths, and npm commands. External sessions can edit + `npm run lint`/`type-check`/`build`, but can't launch or live-preview the native app — that still requires the Glaze app. Both share the same local-only git repo (no remote); commits from either show up interleaved in `git log`.
- **Sidebar `actions` cannot host a React dropdown menu.** `Sidebar` runs `applyButtonDefaults` over its `actions`, which breaks any `*DropdownMenuTrigger asChild` wrapper — both the native `DropdownMenu` and `CustomDropdownMenu` render an empty actions wrapper (no trigger button, no error thrown). Verified: only the plain `<Button>` renders there. For a header action menu, keep a plain `<Button>` in `actions` and open a native menu from its `onClick` via `window.glazeAPI.Menu.popup({ items, x, y, coordinateSpace: "view" })` (already exposed in `preload.ts`), switching on the returned `commandId`. Anchor with the button's `getBoundingClientRect()` (left/bottom); leave `positioningItem` unset (a harmless "ignoring invalid positioningItem" debug warning is logged). **`coordinateSpace: "view"` is required** — `Menu.popup`'s `x`/`y` are documented as absolute screen-space coordinates, but `getBoundingClientRect()` gives coordinates relative to the window's content view. Without `coordinateSpace: "view"`, those small view-local numbers get treated as virtual-desktop coordinates and the menu always opens near the primary display's origin (i.e. on the laptop screen) even when the app window is on a different display. All four renderer popup call sites (`recording-view.tsx` ×2, `library-sidebar.tsx`, `stats-view.tsx`) now pass it. The backend context menu in `recorder-service.ts` (`menu.popup({ window: recWindow, ... })`) is unaffected — it passes an explicit `window`, which anchors it correctly regardless of coordinate space.
- **Glaze `webContents.executeJavaScript` runs each call in a fresh ephemeral content world** — JS globals do NOT persist between calls, and the backend `console-message` event does NOT fire for page logs. The recorder therefore stores all state + the step queue on shared `<html>` DOM attributes (which persist for the document lifetime and are readable from any world) and the backend polls to drain them. Do not switch back to console/global-based capture.
- Recording window loads the external URL directly with `titleBarStyle: "default"` and NO app preload (external/untrusted page). Popups are denied and loaded in-place via `setWindowOpenHandler`.
- **No custom in-window address bar is possible:** the recorder window's content IS the externally-loaded page (no app-owned HTML wrapper, no `<webview>`/`WebContentsView` embedding in this SDK), so a real editable URL bar can't be overlaid on the page. The "URL bar" is the native title bar instead — `recorder-service.ts`'s `updateTitle()` sets `recWindow.setTitle("Recording/Editing — <current URL>")` on every `did-navigate` when `session.showUrlBar` is true (the global default), so it tracks navigation live; when the setting is off, the title is left at its static initial value (set once at window creation) and never updated.
- **All navigation stays in the trainer window (3 layers):** Glaze routes navigations out to the system browser in ways that broke recording. Fixes, in `recorder-service.ts` `start()` + capture script:
  1. **Plain cross-origin `<a href>` links (the main culprit):** Glaze hands cross-origin main-frame navigations to the default browser. `wc.on("will-navigate")` calls `details.preventDefault()` then `loadNavInWindow(url)` (re-issues via `loadURL`) for main-frame, non-same-document http(s) navigations. A `selfLoad` guard prevents the programmatic `loadURL` from being re-intercepted (loop). `did-navigate` no longer needs to be prevented.
  2. **`target="_blank"` anchors:** capture script `keepInWindow()` rewrites the clicked anchor/form `target` to `_self` in the capture-phase click/keydown, plus injects `<base target="_self">`.
  3. **`window.open`:** `setWindowOpenHandler` returns `{action:"deny"}` and calls `loadNavInWindow`; `did-create-window` closes any stray child as a backstop.
  - NOTE: an external browser window is NOT a Glaze window, so it never appears in `LiveAppInspectionStatus`. Verify in-window navigation by reading the recorder window's own `location.href`, not by counting app windows.
- The navigating click is caught by draining on `will-navigate`/`did-navigate` in addition to the 250ms poll.
- Runner spawns with `process.execPath` + `ELECTRON_RUN_AS_NODE=1`, `cwd` = scripts dir, `NODE_PATH` = app node_modules.
- Built backend runs from `.glaze/build/main`, so runtime deps must be resolved against `.glaze-sources/node_modules` (see `resolvePlaywright` candidate scan).
- **`Slider`'s `onValueCommit` is unreliable for a plain click (no drag) — commit on `onValueChange` instead.** `TestSpeedSlider` in `library-sidebar.tsx` originally persisted on `onValueCommit`; the thumb's local value visibly updated on click but the backend write never happened (no `tests:setSpeed` call, no `testStore.save` log line) because a single click never produces the drag gesture Radix's slide-end/pointerup handling expects. Fixed by calling the commit logic directly from `onValueChange`, guarded by a `useRef` so repeated same-value events don't re-fire — fine for a low-cardinality (3-stop) slider; a continuous-value slider would need a debounce instead.
- App logs (`~/Library/Logs/app.glaze.macos.<appId>/glaze-*.log`, tail the most-recently-modified one) are the fastest way to confirm an IPC handler actually ran — `testStore.save()` logs `"Saved test record"` (not the channel name), so grep the log message text, not the IPC channel/handler name.

## The Electron shell (`main/shell/`) — added by the port off Glaze

The only directory permitted to import `electron`. Everything else in `main/`
goes through `@shell/backend`; `eslint.config.js` enforces it. See
[../PORTING.md](../PORTING.md) for the migration record.

### `main/shell/backend.ts`
The adapter that replaced `@glaze/core/backend`. Re-exports Electron's `app`,
`BrowserWindow`, `Menu`, `Notification`, `dialog`, `ipcMain`, `safeStorage`,
`screen`, `globalShortcut`, and supplies the four things Electron has no direct
equivalent for: the `logger`, a `BrowserWindow` wrapper that strips Glaze's
`windowKey` option (so window-creation code was not rewritten), a no-op
`initDevToolsButtonState`, and the `WebContentsNavigationEvent` type the
recorder's navigation guards are written against. The wrapper is a function
returning an instance rather than a subclass — Electron's `BrowserWindow` is
native-backed and cannot be `extend`ed.

### `main/shell/user-data.ts`
Decides where the app's data lives, and must run as the **first statement** in
`main/index.ts` — before `applyRetention()`, which sweeps at module scope and
would otherwise prune the wrong directory. (Imports are hoisted, so "first"
means first in the body.)

Under Glaze the host supplied `userData`; stock Electron derives it from
`productName`, so the port silently began reading an empty `Good Looks!/`
directory while the real 1.4 GB store sat beside it under
`app.glaze.macos.<id>-local/`. The app looked wiped rather than misdirected.

Resolution order: the `GOOD_LOOKS_USERDATA` override; then the current
directory if it already holds a recorder store; then the newest legacy Glaze
store, **adopted in place** (no copy, so a Glaze build keeps working and there
is no half-migrated state); then Electron's default. Adoption fires only when
the current directory has no store of its own, which makes it one-shot and
means it can never redirect an install that has real data.

`metrics.db` deliberately does **not** count as "has a store" — it is a derived
shadow and the port writes an empty one on first launch, so counting it would
stop adoption from ever firing. Covered by `user-data.test.ts` (18 cases),
including that one.

### `main/shell/logger.ts`
`logger.info(scope, message, meta?)`, matching the SDK's shape so ~40 call
sites were untouched. Console plus an append-only file under
`userData/logs/main.log`, because a packaged app has no terminal attached.
File writes are best-effort and never throw.

### `main/shell/host-handlers.ts`
The IPC handlers the Glaze runtime used to register automatically, backing
`window.glazeAPI.{dialog,shell,clipboard,nativeTheme,Menu}`. Under Electron
nobody registers them unless we do, and a missing one surfaces as "No handler
registered" the first time a menu or copy button is used — so the set is the
full surface the renderer actually calls, enumerated by grep rather than guessed.
`Menu:popup` is the important one: it converts the renderer's plain-data menu
template into a real macOS menu and answers with the picked `commandId`, which
is what keeps `Select` and `DropdownMenu` native. Also exports
`forwardRendererConsole`, which pipes renderer errors into the main log — the
port's first failure was a blank window with a completely clean log.
`shell:openExternal` is the one handler with a validator in front of it; see
below.

### `main/shell/external-url.ts`
The allowlist deciding which URLs may be handed to the OS, and the whole of the
`shell:openExternal` boundary. `shell.openExternal` launches whatever Launch
Services has registered for a scheme — `file://` opens a document, a custom
scheme starts another application — and the URL this app passes is a PR's
`html_url` out of a GitHub API response, so it is network input. `checkExternalUrl`
accepts https on `github.com` (or a subdomain) and **returns the parsed href**,
which the handler opens instead of its argument: validating a parsed URL and
then opening the caller's raw string means two values that merely usually agree.
Guarded by `check:open-external` (hostile hosts, schemes, userinfo, normalisation)
and by `check:recorder-navigation`, whose blanket ban on `openExternal` in `main/`
is now a one-file allowlist — that check also pins the fact the exception rests
on, that the **training window has no preload** and so an untrusted page has no
`glazeAPI` with which to invoke any host channel.

### `main/shell/app-protocol.ts`
Serves the built renderer over a custom `app://` scheme. Vite emits module
scripts, which under `file://` get a null origin and are blocked by CORS; the
symptom is a blank window. Registering a real scheme also gives the pages'
CSP a meaningful `'self'`. Path containment is judged on the **real** path
against the **real** build root, the same rule the import sandbox applies, so
neither `..` in a URL nor a symlink inside the bundle can read the rest of
the disk.
