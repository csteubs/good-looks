## Overview

- **App Name:** Test Recorder
- **Purpose:** Record interactions on any website and turn them into runnable Playwright tests.
- **Features:**
  - Prompt for a URL, open it in a dedicated browser window, and record every interaction as a test step.
  - Captures clicks, text input (fill), selects, checkboxes, Enter/Escape key presses, and navigation.
  - Pause/resume recording; add assertions (element visible / contains text) by clicking elements in the recorded page.
  - Generates a `@playwright/test` spec on close; stored in a test library.
  - Runs a selected test locally with the bundled Playwright (installs the browser on first run), streaming live output. **Step highlighting during runs:** a custom Playwright reporter (`step-reporter-source.ts` → `step-reporter.mjs` written next to the specs) emits `__GLAZE_STEP__:` JSON markers on stdout for each `pw:api` step begin/end with the spec line number; the runner (`playwright-runner.ts`) builds a line→stepIndex map from the spec, strips the markers from visible output, and pushes `runner:step` events; the recorder store tracks per-step `stepStatus` ("running"/"passed"/"failed") in `RunInfo`; `StepRow` accepts a `runStatus` prop and shows an accent-tinted background + spinner (running), green tint + check (passed), or red tint + X (failed) with a status icon on the right. The failed highlight was enhanced to `bg-support-red/15 ring-1 ring-inset ring-support-red/40` (15% red background + 40% red ring) with red description text and a larger `size-4` X icon so the failed step clearly stands out. `TestDetailView` passes `runInfo.stepStatus[i]` to each row. Only applies to app-generated specs (one step per line); imported scripts have no step map so markers pass through harmlessly.
  - "Edit in Trainer" reopens an existing test's trainer window preloaded with its recorded steps so the user can extend it; stopping regenerates the script from the combined steps and updates the same record (preserves `createdAt`). When a test has manual script edits (`scriptEdited`), the "Edit in Trainer" button opens a confirmation dialog ("Edit in Trainer") with three options: "Save & continue" (primary accent — persists any unsaved script draft, then opens the trainer), "Continue without saving" (left-aligned destructive — opens the trainer, letting later regeneration overwrite the edits), and Cancel. On arrival, all trainer controls stay disabled (status "Loading page…") until the browser window finishes loading its first page (`pageReady` on `RecorderState`); the trainer then just shows the loaded page (the `goto`/navigation) and waits — it does **not** auto-replay the recorded steps (the old auto-`replayAll` on load was removed because it "flew through" the whole test and could wedge the backend). The user replays on demand with **"Replay from current step"** (see the replay bullet below). Row highlighting still uses the `StepRow runStatus` mechanism driven by `recorder:replayStep`. **Status states:** the trainer's top-bar `Status` badge reads "Loading page…" (before `pageReady`), then **"Running"** whenever ANY replay is executing (a store-level `executing` flag covering single-step / from-current replays, OR the streamed `replayRun.running`), else "Paused" / "Editing" / "Recording". While running, ALL step-editing controls are locked (`controlsDisabled = !pageReady || running` gates the replay button, assert menu, Add step, AI steps, pause/resume, every `StepRow` action, and the cursor-gap inserts) — so "Editing" only appears when the user is actually free to record or change steps. **Loading modal + timeout:** while the training browser opens, a full-area loading overlay (spinner + "Opening training browser…" + URL + copy) shows on the main window. The training window is force-shown on the earliest of `ready-to-show` / `dom-ready` / a **creation-relative `SHOW_FALLBACK_MS` (1.5s) timer** — the timer is the key fix for the "first click does nothing on a cold start" bug: on the first recorder window after app launch the WebView subsystem cold-starts and its readiness events lag past 10s, which used to leave the window hidden and falsely trip the timeout. Now the window always appears ~1.5s after creation regardless of those events. `LOAD_TIMEOUT_MS` (15s) only bounds `pageReady` (how long controls stay disabled waiting for the first page), decoupled from window-opening. The load-failure path (`!shown || destroyed`) is now a genuine "couldn't open" case (window destroyed) — it logs a failed `RunRecord` to Stats and shows the "Couldn't open the training browser" dialog ("Try again" / "Check Stats"). **Exit confirmation:** the toolbar button is labeled **"Save Test"** in Training mode (editing an existing test, `state.editing`) or **"Generate Test"** in Creation mode (new test). With no live steps (`liveSteps.length === 0`) it saves/exits directly (no warning). With unsaved steps it opens a two-button `Dialog` — "Save & Exit" (finalize + close) or "Discard Edits" (discard steps + close via `recorder:discardExit`) — showing the step count.
  - **mabl-style Trainer (editable step list):** the live trainer step list is fully mutable — drag to reorder, click a value/text to inline-edit it, delete, and an insert cursor (click the gap between steps) that controls where new captured/added steps land. A "+ Add step" menu inserts manual steps without touching the page: Assertion, Wait (duration or wait-for-element), Go to URL, Press key, Find element, Set viewport. Locator-requiring steps (assertion, wait-for-element, press-on-element, find-element) use the same "Target Element" crosshair picker as the per-step "Refine selector" flow (now grouped under a kebab "Step utilities" dropdown beneath the row, alongside the "Continue on Failure" toggle — see Recent History) — the user picks an element in the training browser and chooses one of its candidate locators (best-first) instead of typing a CSS selector by hand. Assertions expanded from visible/has-text to 13 kinds (visible/hidden/contains-text/exact-text/enabled/disabled/checked/unchecked/value/attribute/count/page-URL/page-title) with a Hard/Soft toggle (`expect.soft`). A per-step ▶ replay previews that one step in the live window (best-effort synthetic events, not a real Playwright run). A **"Replay from current step"** button (formerly "Replay from start") replays SLOWLY from the currently selected step (or index 0 if none is selected) through the END of the list — a settle + pause between steps (`REPLAY_SETTLE_MS`/`REPLAY_STEP_DELAY_MS` in `recorder-service.ts`) so the user can watch — streaming each step's result + verbose logs live to the debug panel's Console tab via a new `recorder:replayLog` push (`{phase:"start"|"step"|"done"}`). A hard failure stops the run; soft failures continue; if/endif honored. Each step's injected script is raced against `REPLAY_STEP_TIMEOUT_MS` (8s) via `execWithTimeout` so a step that triggers a navigation (or hangs) fails cleanly instead of wedging the run with controls disabled. Capture is suppressed during the run (`withCaptureSuspended` — see below), the training window is focused before the first step, and both trainer windows show **Replaying** and lock their controls off the broadcast `RecorderState.replaying` rather than each window's own local flag. The running step is auto-selected so the highlight + Step-details tab follow along, and each step gets an **ephemeral pass/fail outline** as it finishes — `.step-replay-pass`/`.step-replay-fail` in `renderer/styles.css`, a green/red one-shot fade held for `REPLAY_FLASH_MS`(2.5s, matching the per-row replay tint) and driven by the store's `replayFlash` map off the `recorder:replayStep` END event. Same outline mechanism as the AI-added `.step-new` glow and mutually exclusive with it (both draw an `outline`; the flash wins while it lasts). Pinned by `check:step-glow`. An "AI steps" button asks the local LLM for a structured `Step[]` from a natural-language flow and inserts editable steps into the list; the dialog has an optional "Refine selector" picker (same crosshair pick as step rows) that captures an element's locator and passes it to the LLM as context so generation can target the exact element the user pointed at. The AI generates only the steps AFTER navigation — Step 1 ("Navigate to URL") is a test-level setting the user controls in the Step 1 URL editor, so the prompt tells the model not to emit a `goto` step (assume the page is already loaded at the starting URL), and the dialog defensively filters out any `goto` the model still emits before inserting. **Tabbed debug panel (`DebugPanel` in `recording-view.tsx`, h-56):** a `TabsRoot` (controlled `value`) with two tabs. **Console** — the live "test results" stream: each replayed step's pass/fail header + verbose formatted log lines (timestamp · level · message) as the run progresses, a status line (`Running… n/total` / `Done — p/r passed` / `Stopped at step n`) and a **% hit rate** pill (passed÷ran). An **Auto-scroll checkbox (checked by default)** gates the `ScrollArea autoScrollToBottom`; unchecking lets the user scroll manually. The Console auto-selects on "Replay from current step". **Per-step "Debug with AI":** each FAILED step's error block in the Console shows a Sparkles button that opens `StepAiDebugDialog` (`renderer/main/ai-debug-panel.tsx`) — a leaner sibling of the full-run `AiDebugDialog` that streams a focused LLM diagnosis of that single step (step label + Playwright-style locator via `locatorToPrompt` + error + verbose logs) via `buildStepDebugMessages` (`renderer/lib/llm-prompts.ts`). Reuses `useLlmChat`, `ModelPicker`, `CodeBlock`, `parseResponse`, `friendlyError` (exported from `ai-debug-panel.tsx`). No "Apply to script" (these are editable steps, not a script) — just diagnosis + optional corrected-expression snippet + copy. Auto-starts once per unique failed step; Stop/Regenerate buttons. **Step details** — the selected step's element-locator summary + persisted replay diagnostics (the previous per-step panel content) plus the hit-rate pill and a clear (✕) button. Clicking a step row still selects it (accent ring). Per-step diagnostics are persisted per-test in `userData/recorder/debug-logs.json` (via `recorder-debug-store.ts`); the store loads them on session open and listens for `recorder:debugLogs` pushes; the live Console stream is driven separately by `recorder:replayLog` (ephemeral, held in the recorder store's `replayRun`).
  - Script tab supports direct in-app editing (Edit/Save/Cancel) of the generated spec text, independent of the recorded steps. **IDE-style script views:** both the read-only `ScriptView` and the editable `ScriptEditor` (in `renderer/main/script-view.tsx`) render with a line-numbered gutter + regex syntax highlighting (keywords/strings/comments/numbers/decorators) using the design system's `--color-token-*` variables (blue keywords, red strings, gray-italic comments) so they adapt to light/dark. The editor overlays a transparent `<textarea>` on a highlighted `<pre>` (shared font metrics + padding for exact alignment, synced scroll, explicit white caret since `text-transparent` hides the caret in WebKit). Both views use `text-mono font-mono` (13px/18px) — slightly larger than the old `text-small-mono` (11px) for a more legible IDE feel.
  - Import existing Playwright tests: the sidebar + opens a native menu with "Train manually" (the original recorder flow), "Generate from prompt", "Select from files" (pick a local folder), and "From URL" (clone a git repo). Each matched `*.spec.ts`/`*.test.ts` file is parsed into `Step[]` (via `spec-parser.ts`); the verbatim file is kept as the runnable script and the test is `scriptEdited`. Imported tests (`sourceDir` set) are **Script-only** in the detail view — the verbatim file is the source of truth, so the Steps tab is not shown even when steps parsed. Tests created in the app show **both** Steps and Script tabs (Steps primary when there are steps).
  - **Generate test from prompt (phase 3):** the sidebar + menu's "Generate from prompt" opens `GenerateTestDialog` — a separate window where the user describes a test in natural language and the local LLM generates a complete Playwright spec. Pre-selectable common options: test name, starting URL, execution speed (Fast/Medium/Slow, persisted on the `TestRecord`), and browser viewport (Default/Desktop/Laptop/Tablet/Mobile presets — passed into the prompt as a hint). The dialog shows prompt-formatting tips, streams the response with the same formatted rendering as the AI debug panel (prose + fenced code cards), and when the model returns a complete applyable spec (contains `import` and `test(`) a "Create test" button persists it via `tests:createFromPrompt` (creates a `TestRecord` with empty `steps`, `scriptEdited: true`, the generated source as the script file) then navigates to it.
  - **Visual testing (roadmap complete, Phases 0–5 + post-roadmap):** an optional per-run "Capture screenshots" toggle (default off) next to Run test, plus a "Visual" sidebar tab (grouped with Stats). When the toggle is on, a run of an app-generated test **captures a screenshot after each page action** and persists it under `userData/recorder/artifacts/<testId>/<runId>/<stepIndex>.png` + `manifest.json` + `replay.json` (retained for the newest 10 runs per test). The **Visual tab is a screenshot-replay viewer**: pick a captured run and scrub its steps in a timeline, seeing the screenshot + pass/fail per step with the failure point highlighted (auto-jump + red callout + timeline marker). **Phase 3 adds page-level visual diffing:** each captured step's screenshot is compared against a **pinned baseline** (keyed by `Step.id`; first captured run seeds it, later runs diff against it — never the previous run). A step exceeding a per-test threshold is flagged "visual change detected" (orange badge/callout/timeline marker), with a Current/Baseline/Diff view toggle and "Accept as baseline" (per-step and per-run) to re-pin an intentional change. Diffing is pure-JS (pixelmatch); it degrades to "can't compare" on size mismatch/corrupt images rather than false-flagging. **Phase 4 adds freeform step notes:** any step in the replay timeline can carry one freeform text note (an "Add note" affordance in the step-detail row, editable/clearable), shown inline while scrubbing and marked on the timeline with a message-square icon. **Phase 5 (final)** wired the tab to the real views (done in Phase 2), added a one-path end-to-end regression check (`npm run check:visual-pipeline`), kept retention at 10 (validated against real disk usage), and fixed a retention bug that could delete the pinned baseline. **Post-roadmap additions:** (1) **Ignore/mask regions** — `TestRecord.visualMasks` stores normalized 0–1 rectangles; `diffPngBuffers` paints a solid fill into both images before pixelmatch so masked pixels compare equal. The Visual tab's "Ignore regions" button toggles a `cursor-crosshair` overlay (`MaskLayer` in `visual-view.tsx`) over the screenshot; drag to draw a dashed orange rectangle. A mask with `stepId: null` applies to every step; the "Apply to all steps" switch controls this. The diff badge shows a dashed-square icon when regions were excluded. IPC: `visual:getMasks`/`setMasks`. (2) **Capture-overhead measurement** — the capture fixture times each `page.screenshot()` and writes `captureMs`/`shotCount` into `manifest.json`; the runner stores them on `RunRecord`. Stats shows a "Capture overhead" panel (above the pass/fail chart) with per-run screenshot time, per-screenshot mean, and captured-vs-uncaptured duration. Hidden until at least one instrumented capture run exists. (3) **Age-based artifact retention** — `pruneRuns` takes an optional `maxAgeMs` on top of the count cap; a run survives only if it satisfies both. New setting `artifactRetentionDays` (0 = off, max 365) in Settings → "Delete screenshots older than". Pinned baselines (`baseline/` dir) are excluded from both rules. (4) **Element-scoped (component-level) diffing** — records the acted-on element's bounding box (`elementRect` in `capture-fixture-source.ts`) at capture time; a Page/Element `SegmentedControl` in the step-detail row (only for steps with `step.rect`) toggles between page-wide and element-cropped comparison. The baseline stores its own rect, so each side is cropped by geometry from its own run. IPC: `visual:getElementSteps`/`setElementStep`. Steps whose baseline predates the geometry feature show no toggle; if the user toggles Element on a step whose baseline lacks geometry, the diff reports "the pinned baseline predates element geometry — accept a new baseline to enable it". (5) **Local run notifications** — a macOS notification (`run-notifier.ts` via the SDK `Notification` API) fires when a run fails or flags a visual change; clean runs stay quiet. Gated by Settings → "Notify when a run has problems" (`notifyOnRunIssues`). The macOS notification is local only; external delivery is a SEPARATE, opt-in feature — see the webhook-alerts bullet below (added later; earlier notes calling external alerting "deferred" are stale).
  - **Accessibility checks (axe), gated separately from screenshots:** a per-test **"Check accessibility"** toggle beside "Capture screenshots" (global default `RecorderSettings.defaultA11yChecks`, off) makes the capture fixture inject `axe-core` via `addInitScript` (once per document, resolved from the same `node_modules` the Playwright CLI came from) and run it after each captured action. Gated independently of screenshots because a11y is useful without them and costs far more — `a11yMs`/`a11yChecks` are timed and reported separately from `captureMs` for exactly that reason, and Stats shows the two apart. Violations ride the SAME manifest entries as screenshots (one correlation, in `buildReplay`, so a result can never be attributed to the wrong step), compacted to rule id + impact + help + node targets, capped at 25 violations × 5 nodes. `enrichWithA11y` then diffs them against the test's accepted baseline (`a11y-diff.ts`, pure). **Identity is rule id AND node target** — keying on the rule alone would make accepting one low-contrast label accept every future contrast failure on the page. The baseline lives on the `TestRecord` (`a11yBaseline`), NOT under the artifacts tree, which makes "retention pruned my baseline" structurally impossible rather than a rule to remember; accept-step / accept-run / reset are in `a11y-baseline-ops.ts`. **Reported, never fatal** — nothing here touches `runStatus`, pinned by a source-level assertion in `a11y-diff.test.ts`. **Four surfaces, in decreasing order of how much the user has to go looking:** (1) an **"Accessibility" tab on the test itself** (`a11y-panel.tsx`, last tab, after Heals; hidden for imported tests like Variables/Heals), badged with the unaccepted-step count — it describes the most recent run that CHECKED (`latestA11yRun`), NOT the most recent run, so a later run with the toggle off can't blank the results and read as "fixed"; it carries per-step and whole-run Accept plus **"Reset accepted"**, which is the only UI that has ever reached `a11y:resetBaseline`. (2) A `describeA11yOutcome` line in the run's Output panel. (3) An orange `Accessibility` marker on any run in the Visual run LIST with unaccepted violations. (4) The per-step badge + violation list + Accept in the Visual view itself. **Both (1) and (2) state the number of COMPLETED checks**, because zero of them is a fault and must never read as a clean page (see DECISIONS 2026-08-06). The violation rendering (`a11y-violations.tsx`: `A11yBadge`, `A11yViolationList`, `IMPACT_COLOR`) is shared by the tab and the Visual view — two hand-written copies would eventually disagree about which issues matter. Coverage: `a11y-diff.test.ts`, `a11y-format.test.ts`, `a11y-panel.test.tsx` (one test per situation it must tell apart), `capture-fixture-a11y.dom.test.ts` (the shipped axe callback, evaluated the way Playwright evaluates it), the a11y section of `check:visual-pipeline`, and the tab/run-list markers in `test-detail-view.test.tsx` / `visual-view.test.tsx`.
  - Right-click a test in the sidebar for a context menu: "Reveal in Finder" (highlights the spec file), "Remove from Sidebar" (hides the test from the sidebar view WITHOUT deleting its record or script file — `hidden: true` on the `TestRecord`; the file stays on disk for later restoration), and "Adjust Test Speed" submenu with a 3-stop Slow/Medium/Fast slider that sets a Playwright `slowMo` delay for that test's runs (0/400/1200ms).
  - **Auto-Heal (resilient replay):** during "Replay from current step", when a step's locator fails to resolve, a backend Auto-Heal engine probes the live page for alternative locator candidates using all available context — the step's action/text, freshly generated candidate locators, and hints from past runs' debug logs — retrying per the user's settings. If a candidate makes the step pass, it's auto-applied to the step (marked with a green "Healed ✓" badge in the Console); otherwise the ranked candidates surface in the Console as a menu where the user can pick any suggested target to apply to the step. Settings (in the app Settings window) control retry count and per-attempt timeout, and let the user disable Auto-Heal.
  - **Refine Selector (per-step element picker):** each editable trainer step row that has a locator shows a crosshair "Refine selector" icon (between the ▶ Run/replay and ✕ Delete icons). Clicking it pauses the session and enters a pick mode in the training browser — hovering draws a blue bounding box over components and clicks are intercepted (page doesn't respond). Clicking a component captures its locator candidates (test-id / role / label / placeholder / text / CSS / XPath, best-first), computed CSS, and attributes; a "Refine Selector" review dialog (showing which step is being refined) lets the user pick the best locator and **update that step's locator** (Update selector), then resumes recording. Operates at the step level — it refines an existing step rather than inserting a new one.
  - **Right-click test-tools menu in the training browser:** right-clicking in the recorder window pops a native macOS menu (the window loads an external page we don't own, so the menu is a backend `Menu.popup` from `@glaze/core/backend`, not in-page React). The element under the cursor is resolved via `PICK_AT_POINT_SCRIPT` (`elementFromPoint` + inlined `DOM_HELPERS` → `buildPicked` + the element's current text/value), so menu items are **pre-targeted at that element**. Menu layout: a disabled header showing the target (e.g. `button#submit`) or "No element here"; **Assert element ▸** (visible/hidden/contains-text/exact-text/enabled/disabled/checked/unchecked/value/attribute/count — text/value kinds prefill the element's current text); **Assert page ▸** (URL is… / title is…); **Wait ▸** (for element visible / for element hidden / for duration…); **Refine selector for this element**; **Add step ▸** (Go to URL / Press key / Set viewport / Find element). Picking an item pushes a `recorder:contextAction` event to the main window (`ContextAction` payload: kind + assert?/waitMode? + picked + prefillText/prefillValue), which opens the existing Add-step dialog **prefilled** (locator from the picked element, assert kind / wait mode / text / value seeded) so the user can tweak before inserting at the cursor. Fully additive — the "+ Add step" menu and assert-mode toolbar stay. Coordinate mapping: context-menu `x/y` are DIP; `elementFromPoint` uses CSS client coords, adjusted by `wc.getZoomFactor()` when not 1.
  - **Trainer window URL bar setting:** the recording/editing window's native title bar shows the current page's live URL by default ("Recording — https://…", updated on every navigation) as a stand-in address bar. A Settings toggle ("Show URL bar in training window") lets the user turn this off, reverting to a static title; persisted in `recorder-settings.json`, applied per-session at `recorder:start`.
  - **Default run speed (New Recording dialog + Settings):** the New Recording dialog has a "Run speed" `SegmentedControl` (Slow/Medium/Fast) that reads and writes a persisted `defaultRunSpeed` on `RecorderSettings` (`recorder-settings.json`, **slow by default**). New recordings seed their per-test `speed` from this default in `recorder-service.finalize()`, so the sidebar "Adjust Test Speed" override still works per-test. Settings shows the same control under "Default run speed" so the choice is visible and changeable there too. Same `SegmentedControl` idiom as `GenerateTestDialog`'s execution-speed picker.
  - **Window size preset (New Recording dialog + Settings):** the New Recording dialog has a "Window size" `Select` (Default / Desktop 1280×800 / Laptop 1440×900 / Tablet 768×1024 / Mobile 390×844, from `renderer/lib/viewport-presets.ts`) that reads and writes a persisted `defaultWindowSize` on `RecorderSettings`, mirrored in Settings under "Default window size". The preset does two things at once, and both are needed: the training window OPENS at that PAGE size (`useContentSize`), and the size is recorded as the session's first `viewport` step so the generated spec calls `setViewportSize` BEFORE `goto` and the test REPLAYS at the size it was recorded at. Sizing only the window would make the preset cosmetic — a test recorded at 390×844 would run at Playwright's own 1280×720 and meet a desktop layout it never saw. Re-opening a test in the trainer takes its size from `recordedViewport(steps)` instead of the dialog, and adds no second viewport step.
  - **Window resize as a test step (`viewport`):** a resize can be inserted anywhere in a test, not only at the start. Both "+ Add step → Set viewport" pickers (the trainer's `add-step-dialog.tsx` and the detail view's `edit-steps-view.tsx`) offer the shared presets plus **Custom…** width/height, clamped by `clampViewportAxis` to the same 200–4000 range `normalizeViewport` enforces on the backend, so a typed size is never silently rewritten. A resize row is inline-editable as one `WIDTHxHEIGHT` field (`parseSizeDraft` in `step-row.tsx` accepts `x`, `×` or `,`; an unparseable draft commits NOTHING, because a resize with only a width is not a smaller edit but a broken step) and is **replayable on its own** — the one exclusion from the per-step ▶ that was dropped. It composes with the rest of the step model like any other step: disabled, continue-on-failure, inside an `if` block, inlined through a `runFlow`, reordered by drag, round-tripped by `spec-parser.ts`. **Trainer replay actually resizes the window** (`resize-service.ts`, dispatched from `runStep` alongside `cookie` steps) rather than reporting "not previewable" — see DECISIONS 2026-08-06. **Every executed resize logs its dimensions:** the generated spec emits a `console.log` after `setViewportSize` reporting the requested size and what `page.viewportSize()` actually returned (so it lands in the run's `.log`), the trainer streams requested/window/page sizes into the Console tab, and a manual drag-resize of the training window logs its settled page size (`resized`, not `resize` — one line per deliberate change, not one per drag frame).
  - **Local LLM integration (phase 1 — backend foundation):** connect to a local Ollama or LM Studio server (loopback, private, no API key). Settings has an "AI provider" section to pick the provider, run a "Test connection" (reports Online/Offline + available models), and choose a default model. The server URL is **editable** (an `Input` pre-filled with the saved override or the provider default; saved on blur via `setConfig({ baseUrls: { [provider]: override } })`, clearing the override when it matches the default). Available models **auto-populate** based on the selected provider + URL — a `useEffect` on `[provider, baseUrl]` calls `llm.status` and renders the model list + Online/Offline badge without a manual "Test connection" click; the button remains as a manual refresh.
  - **Debug with AI (phase 2):** when a run fails, a "Debug with AI" button appears in the run Output panel. Opens a dialog that auto-sends the test's script + failing run output to the configured local LLM and streams back a diagnosis + suggested fix, with Regenerate/Stop/Copy response controls. Generating test steps in the trainer is **also built** (`generate-steps-dialog.tsx` + `buildGenerateStepsMessages`, behind the trainer's "AI steps" button) — earlier notes calling it deferred are stale.
  - **Cross-browser runs:** test runs can execute on **Chromium, Firefox, or WebKit**. Resolution order is explicit choice → the test's saved `TestRecord.runBrowser` → the global `RecorderSettings.defaultRunBrowser` (default `chromium`). Picked per-test from a `Select` in the test detail toolbar (persisted via `tests:setBrowser`) and globally in Settings. The Playwright CLI's `--browser=<engine>` flag selects it (the generated `playwright.config.ts` defines no `projects`, so `--browser` is honored rather than overridden). Each engine downloads on its own first use. **Trainer is unaffected** — it records in the app's own WebView. `RunRecord.runBrowser` records which engine a run used (absent on runs predating this — they all ran on Chromium).
  - **Batch (suite) runs:** a **Batch** view (sidebar → Views) runs many tests back to back. Pick any subset of the library, set batch-level headless/capture/browser options, and watch per-test progress plus a pass/fail summary. Tests run **strictly sequentially** — the runner is keyed by testId so it *would* run several at once, but each run spawns its own Playwright process and browser (parallel would contend for CPU and make headed runs fight over the screen), and sequential keeps the per-run event stream (`runner:output`/`step`/`done`, keyed by `runId === testId`) unambiguous for a renderer that shows one live run. Each test still writes its own `RunRecord`, so a batch shows up in Stats as ordinary runs — the batch is a driver, not a new kind of history.   - **Empty-response diagnosis (streams that end with no answer):** a stream can finish cleanly having emitted zero tokens. The old message guessed — "It may have hit a token limit, or the prompt may have been too long for its context window" — which made a COMPLETED request look like a dropped connection, and was simply wrong for a prompt that measured ~780 tokens. `runChat` now records evidence while streaming (`eventCount`, the last `finish_reason`, and the set of delta fields that carried a value) and `describeEmptyResponse` (`main/services/llm/provider-errors.ts`) turns it into a specific message: `finish_reason: "length"` → token limit + raise the context length; zero events → "sent no data at all"; events but no text → "ended its turn… the request completed normally, so this is not a connection or timeout problem", pointing at a chat-template mismatch. Every message names the model, the provider, and the prompt size (`approxTokens`, ~4 chars/token) so it can be compared against a context-length setting. The high-value branch is **unknown delta fields**: a model streaming its answer under a key we don't read (`KNOWN_DELTA_FIELDS` = content/reasoning_content/reasoning/role) is otherwise indistinguishable from a model that said nothing, so that case is reported as OUR bug, naming the fields. The facts are also `logger.warn`'d. Covered end-to-end in `llm-service.test.ts` (real SSE lines through `runChat`) plus unit tests in `provider-errors.test.ts`.
  - **ANSI stripping on run output:** Playwright's `line` reporter redraws with cursor-up/erase-line (`ESC[1A ESC[2K`) and colours failures. Those bytes reached three consumers: the Output panel rendered them as visible mojibake, the log file kept them, and they were sent VERBATIM to the model in the Debug-with-AI prompt, spending context on cursor movements. `stripAnsi` is applied in `emitOutput` (`playwright-runner.ts`) — the same single choke point where secret redaction happens, and for the same reason: per-consumer stripping means getting it right in three places forever. Marker extraction (`__GLAZE_STEP__:`) happens upstream of `emitOutput`, so it is unaffected. The regex is built with `String.fromCharCode(27)` because `no-control-regex` rejects an inline ESC literal and blanket-disabling that rule would cover future additions too. Checked by `main/services/strip-ansi.test.ts` (including that `[chromium]`/`[1/1]`/array syntax survive — a regex that ate a leading `[` would silently corrupt every log line).
  - **Model list is fetched once per provider, not per dialog open:** `useModelPicker` used to call `llm:status` every time an AI dialog opened, which after minimize/restore put a `GET /v1/models` on the wire on each restore — noise that appears in the provider's log right beside an in-flight completion and reads like reopening the window is interfering with the stream. It now refetches only when the configured provider actually changes.

  - **Readable LLM provider errors:** a non-2xx chat response used to reach the AI panel as `Chat request failed (HTTP 400). {"error":"Failed to load model \"…\". Error: LM Link connection closed"}` — the one sentence that mattered buried in a status code and JSON escaping, with no hint what to do. `main/services/llm/provider-errors.ts` (pure) decodes it: `extractProviderMessage` handles the shapes these providers actually send (`{error: string}` for Ollama/LM Studio, `{error:{message}}` for OpenAI-compatible/Anthropic, `{message}`, `{detail}`, plain text), returning null for JSON with no message field so the caller falls back to the status rather than dumping an object, and clamping an HTML error page to 300 chars. `describeHttpFailure` leads with the actionable sentence and keeps the provider's own words after it. The **model-unavailable** case is called out specifically because it's the commonest local-provider failure — the model picker lists every model the server knows about, but a local server only serves what it can load — with a per-provider fix (`ollama pull <model>` / "Load it in LM Studio"). Errors are thrown as a **`ProviderError`** so `llm-service`'s catch distinguishes a decoded provider failure from a TRANSPORT failure **by type, not by text**: a decoded message quotes the provider verbatim, so a body mentioning e.g. a "network error while fetching weights" would match the `abort|timeout|econnrefused|fetch failed|network` patterns and get replaced with "Make sure LM Studio is running" — sending the user after a server that is up and answering. `renderer/lib/llm-errors.ts` adds the model-picker hint and checks that branch BEFORE the connection branches for the same reason. Covered by `main/services/llm/provider-errors.test.ts` + `renderer/lib/llm-errors.test.ts`.

  - **Minimizable AI debug sessions:** any "Debug with AI" job — the full-run `AiDebugDialog` and the trainer's per-step `StepAiDebugDialog` — can be **minimized** back into its icon and picked up later. A session is keyed (`run:<testId>` / `step:<testId>:<stepIndex>`) and lives in a global `AiDebugProvider` (`renderer/main/ai-debug-store.tsx`) mounted in `RootView` ABOVE the router, because `TestDetailView` is a route component and `RootView` swaps the whole outlet for `RecordingView` while recording — a session owned by a dialog died on navigation, and its backend request was left running with nobody holding the `requestId` to cancel it (billed tokens on the Claude provider). **Icon colour is the status** (`renderer/lib/ai-debug-status.ts`, the single mapping): blue = ready for input (`idle`/`cancelled`/`interrupted`), orange + pulse = model thinking, green = finished and ready for review, red = failed. Each state also carries a distinct `title`/`aria-label` — colour alone isn't accessible and isn't assertable in jsdom. Coloured icons appear in the run Output panel (`run-output.tsx`, now shown whenever a session exists — it used to render only for a FAILED run, so a minimized job vanished the moment the test was re-run and passed), on each failed trainer Console step, and on a **global chip** (`ai-debug-chip.tsx`, bottom-right) which is the only affordance that survives navigation and the trainer; it shows the aggregate status by ATTENTION priority (error > done > streaming > interrupted > cancelled > idle — a finished answer must never hide behind a still-running job) and lists sessions when there are several. `AiDebugHost` (in `ai-debug-panel.tsx`) renders whichever session is expanded, so restoring works from anywhere; dialog dismissal (Esc / close / outside click) MINIMIZES, and discarding is a separate explicit button that cancels the request. **Persistence:** sessions are stored in `userData/recorder/ai-debug-sessions.json` (`main/services/ai-debug-store.ts`, versioned envelope, atomic tmp+rename, capped at 20 newest-first, corrupt/unknown-version reads as empty) — but only the OUTPUT survives a restart, never the job: `llm-service`'s in-flight map dies with the process, so `reconcileInterrupted()` at startup (`main/index.ts`, mirroring `batch-history-store`) rewrites a session left as `streaming` into `interrupted` rather than restoring a permanently-orange icon. A RENDERER-only reload is different — the backend request is still alive — so hydration re-adopts a `streaming` session after confirming it with the new `llm:isActive` IPC. The prompt `messages` are deliberately NOT persisted (they embed the script and run output verbatim; they're rebuildable from live data via `buildDebugMessages`); the answer is, so Stats → "Manage data" gained **"Delete AI debug history…"**. Writes are throttled (2s while streaming, always flushed on a terminal transition and on minimize) and streamed chunks are coalesced at 60ms, with **two separate contexts** (metadata vs. content) so a token doesn't re-render every icon in the app. **Concurrency:** at most `MAX_ACTIVE_STREAMS` (2) concurrent streams — local providers serialize requests, so a third would sit "thinking" without progressing and the colour would be lying; the refusal offers "Stop the oldest and send". Restarting a session cancels its own previous request and never counts against its own cap. `scriptHash` (FNV-1a) is stamped at SEND time — NOT on open, which would erase the signal — so reopening a session whose script was edited while minimized shows a **stale-script warning** above the diff, and the diff always recomputes against the CURRENT script. Pure rules live in `renderer/lib/ai-debug-sessions.ts` (keys, hashing, staleness, capacity, aggregate status, pruning that never evicts a live session); coverage is `ai-debug-status.test.ts`, `ai-debug-sessions.test.ts`, `ai-debug-store.test.tsx`, `ai-debug-chip.test.tsx`, `ai-debug-integration.test.tsx`, `run-output.test.tsx`, plus `npm run check:ai-debug-store`. Views wrap in the provider via `renderer/__tests__/ai-debug-harness.tsx`.

  - **Stats view + run-history log database:** a separate "Stats" sidebar nav item (top of the sidebar, above the test list) routes to `/stats` (`StatsView`). Every completed run is persisted to a **log database**: `playwright-runner.ts` accumulates the visible console output per run and, on `runner:done`, appends a `RunRecord` (metadata: testId/testName/url/status/exitCode/startedAt/finishedAt/durationMs) to `userData/recorder/run-history.json` and writes the raw output to `userData/recorder/logs/<runId>.log` (via `run-history-store.ts`), then pushes `runs:changed`. The Stats view shows: summary cards (total/pass rate/passed/failed), a dependency-free **pass/fail-over-time** stacked bar chart (green passed / red failed, bucketed by day, fixed to the last 7 calendar days inclusive of today — days with no runs show as a zero bar rather than being skipped), a **run-history table** (Table component; row click opens a raw-log inspector Dialog with copy — columns Test / Status / **Browser** / Started / Tags / Duration / Log, where Browser is an icon-only `BrowserIcon` and baseline rows show a dash; the Tags badge alongside it carries the mode icon plus the engine's glyph with NO engine name, since the column now owns that fact and the name in both places was pure duplication), and a **raw-log search** box (debounced `runs:searchLogs` — case-insensitive across all `.log` files, returns match count + snippet; clicking a result opens its log). Cleanup via a "Manage data" native menu: **Reset stats (keep logs)** clears `run-history.json` but keeps the `.log` files on disk, **Delete stats & logs** removes both, **Delete logs by date…** opens a Dialog with two `NativeDatePicker` (From/To) → `runs:deleteRange` deletes records + logs whose run started in the inclusive range, and **Reveal logs folder in Finder**. Design note: "stats" = the RunRecord index (charts/table); "logs" = the raw `.log` files — deleted independently by design.

- `main/services/batch-runner.ts` — **batch (suite) runs**. `createBatchRunner(deps)` returns `{start, stop, getState}`; `batchRunner` is the app singleton. `start({testIds, captureArtifacts?, runHeadless?, browser?, concurrency?})` queues the tests and runs them **one at a time by default** (`concurrency` absent or 1 — the pre-existing behaviour), or up to `concurrency` at once, awaiting each via `playwrightRunner.waitFor(runId)`, emitting `batch:progress` per transition and `batch:done` at the end. Edge cases it pins: a test deleted after queueing is **skipped** (not fatal); a test already running (`waitFor` → null) is **skipped**, not reported as a bogus failure; a failing test never aborts the batch; `stop()` kills **every** running test and skips the rest while keeping earlier results; only one batch runs at a time (a second `start` returns `{alreadyRunning: true}` with the in-flight id). `summarize(state, now)` is pure (an all-skipped batch is NOT `ok`). **Parallelism is lane-based.** `buildLanes(queue)` partitions the expanded queue into one lane per distinct `testId`; lanes run concurrently up to the limit, entries WITHIN a lane stay sequential. Deliberately kept out of `stats-view.tsx` so `check:run-filters` can exercise it without React or the design system. Subtlety it encodes: **baseline-update rows** carry an incidental `status` of "passed", so they are reachable ONLY via status `baseline` and are excluded by every tag filter.
- `renderer/lib/browser-icons.tsx` — the one place that decides what Chromium/Firefox/WebKit look like. Two maps, because the app draws browsers on two surfaces that cannot share a renderer: `BROWSER_ICONS` (lucide `Chrome`/`Flame`/`Compass`) for the DOM, and `BROWSER_SF_SYMBOLS` (`globe`/`flame`/`safari`) for the SDK's native `Select`, whose options are drawn by AppKit and never enter the DOM — a React node passed as a `SelectItem` child icon there is silently dropped. `<BrowserIcon browser labelled>` renders the DOM glyph with `role="img"` + `aria-label` + `<title>` by default (icon-only usages need both the accessible name and the hover), and `labelled={false}` where the same row already names the engine — the Stats tag badge, whose row has a Browser column, where a labelled icon would have a screen reader announce "Firefox Firefox". Guarded by `browser-icons.test.tsx`, which pins that both maps are TOTAL over `RUN_BROWSERS` and that no two engines share a glyph — a missing entry renders `undefined` as a component and throws at runtime, in whichever view happened to show that engine first.

- `main/services/import-service.ts` — Imports existing Playwright tests. `importFromFiles()` opens a native directory picker (`dialog.showOpenDialog`), scans for `*.spec.ts`/`*.test.ts` (skips node_modules/.git/etc, depth+file caps). `importFromGit(url)` shallow-clones (`git clone --depth 1` via `execFile`, validates URL scheme, ENOENT→friendly "git not installed") to an `os.tmpdir()` temp dir, scans, cleans up. Each file → a `TestRecord` (file content is the script, `steps` parsed via `spec-parser.ts`, `scriptEdited: true`, name from first `test("…")` or filename, url from first `page.goto("…")`, `sourceDir` = the spec's original folder). `copyRelativeImports()` copies the spec's `./`/`../` sibling modules (recursively, ext/index probing, 5MB cap) into the scripts dir at import time so the spec runs standalone; `repairImports(id)` re-copies from `sourceDir` (exposed as `tests:repairImports`).
- `main/services/spec-parser.ts` — `parseSpec(source) → Step[]`: best-effort reverse of `script-generator.ts`, now round-tripping its **full** vocabulary (not just a subset): `page.goto`/`page.waitForTimeout`/`page.setViewportSize`/`page.keyboard.press`, `<locator>.click|.fill|.selectOption|.check|.uncheck|.press|.waitFor` with `getByTestId/getByRole/getByLabel/getByPlaceholder/getByText/locator(...)` locators, and `expect(...)`/`expect.soft(...)` for all 16 assert kinds (incl. page-level `toHaveURL`/`toHaveTitle`, `.not.toBeChecked`, and `toHaveCSS` — whose second argument selects the match mode, with the `new RegExp(...)` arm checked FIRST so a `contains` assert isn't downgraded to an `is` against a regex source). `.hover()`/`.focus()` parse to `state` steps (they used to count as skips, permanently flagging any imported test that hovered) and `page.mouse.down()`/`.up()` to `press`/`release`. `parseSpecDetailed(source) → {steps, skipped}` (which `parseSpec` wraps) also counts statements that look like actions/assertions but can't be classified — used by the `tests:updateScript` handler to set `TestRecord.stepsDiverged` instead of silently undercounting. Also round-trips conditional blocks: `parseCondition(raw)` reverses `conditionExpr` (element + page conditions, incl. negated `unchecked` and count-based `exists`), a recognized `if (…) {` becomes an `if` step (`ifDepth` counter) and its matching `}` an `endif`; an unrecognized/foreign `if` skips the whole `{…}` block (via `matchBrace`) so no half-parsed `if` is emitted without its `endif`. Conditional waits round-trip too: `stripComments` PRESERVES the generator's trailing `// wait until` marker (the second such exception, alongside `// disabled — skipped:`), and a marked `expect` becomes a `wait` step instead of an `assert` — without it every conditional wait would silently come back as an assertion, since the two compile to the same call. `.waitFor({ state })` now carries its state back as a `waitUntil` (a wait-for-hidden used to parse as a bare wait and regenerate as wait-for-VISIBLE); `state: "detached"` has no counterpart in the model and is counted as unclassified rather than inverted. Regression coverage: `main/services/__tests__/spec-parser.check.ts` (sections 5–6 cover if/endif, 7–9 cover conditional waits). **Sandbox note:** `npm run check:spec-parser` (tsx) fails under the agent sandbox with `listen EPERM` (unix socket); run it via `npx esbuild main/services/__tests__/spec-parser.check.ts --bundle --platform=node --format=esm --outfile=$TMPDIR/check.mjs && node $TMPDIR/check.mjs` instead.
- `main/services/run-history-store.ts` — Log database for completed runs. `append(run, logText)` writes `userData/recorder/logs/<uuid>.log` + appends a `RunRecord` to `userData/recorder/run-history.json` (capped at 1000, oldest+their logs pruned). `list()` (newest first), `readLog(id)`, `searchLogs(query)` (case-insensitive across all `.log` files → `{runId,testName,status,startedAt,matchCount,snippet}`, cap 200), `resetStats()` (clear index, KEEP `.log` files), `deleteAll()` (clear index + delete all `.log` files, incl. orphans), `deleteRange(fromMs,toMs)` (remove records + logs started in inclusive range), `logsDirPath()`.
- `main/services/playwright-runner.ts` — Resolves `@playwright/test` CLI by scanning candidate node_modules roots; spawns `cli.js test <spec> --config <playwright.config.ts> --headed --browser=<engine> --reporter=line`; installs the chosen engine first if missing; streams output. **Browser selection:** `start({browser?})` resolves explicit → `TestRecord.runBrowser` → `RecorderSettings.defaultRunBrowser`. `isBrowserInstalled(engine)` matches directories by the `<engine>-` prefix, NOT a bare `startsWith` — Playwright also unpacks `chromium_headless_shell-*`, which is not a usable headed browser, so the old `startsWith("chromium")` reported a shell-only install as complete and the run failed at launch. **Awaiting a run:** `start` is fire-and-forget, and the `runs` map can't be used to await one (it holds an entry only while the child process is alive — empty during browser install and after exit but before the `RunRecord` is written), so a separate `inFlight` map holds a per-run promise resolving to the exit code, exposed as `waitFor(runId)` (null when not in flight). This is what batch runs sequence on. `ensureConfig()` writes `playwright.config.ts` next to the specs from `playwright-config-source.ts` since the CLI has no `--slow-mo` flag; **every `ensure*` writer now goes through `writeIfChanged` (compare, then temp-file + atomic rename)** — these are files SHARED by every run, rewritten on every run, while other runs' Playwright processes may be reading them, and truncate-then-write is not atomic. Content is fixed per app build, so after the first run of a session they write nothing at all. **Concurrent browser install** is serialized through an `installs` map keyed by engine: several parallel runs can discover the same missing engine at once, and N `playwright install` processes unpacking into one directory produces a half-written browser that then fails to launch for every later run; the first caller installs and the rest await the same promise (and are told so, since the install's output streams to a different run's Output panel). **`PW_OUTPUT_DIR`** gives each run its own Playwright scratch dir (`<scriptsDir>/test-results/<recordId>`, removed in the `finally`) — the default is derived from the SPEC's path, so two concurrent runs of one spec would share and clean the same folder; the speed→delay table and the per-test timeout rule now live in `run-pacing.ts` and are passed via the `PW_SLOWMO_MS` env var and `--timeout` per run. **Crawl speed:** a `crawl` run of an app-generated test also joins `captureArtifacts || healing || a11y || recordLogs` as a reason to redirect the spec's `@playwright/test` import to the capture fixture, writes `glaze-settle.mjs`, and sets `GLAZE_SETTLE=1` (see `settle-fixture-source.ts`). Settling alone does NOT make the run an artifact run — `artifactRun` gates the prune/`ensureRunDir`/`writeSteps` bookkeeping separately, so a crawl run with healing off doesn't prune the artifact history to create an empty dir. An imported test can't be redirected at all, so it gets the step delay and an explicit "page-settling is skipped for imported tests" line rather than silently slower-but-identical behaviour. **Run persistence:** accumulates visible output per run in `logBuffers` (via `emitOutput`) and on `finally` calls `runHistoryStore.append(...)` (status = exitCode===0?passed:failed) then pushes `runs:changed` before `runner:done`. **Visual-testing capture (Phase 1):** mints a fresh `recordId` uuid per run (used for BOTH the artifacts dir and the `RunRecord` id, so a test's runs stop overwriting each other); when `captureArtifacts && !rec.sourceDir`, calls `ensureCaptureFixture` + `prepareCaptureSpec` (temp `<recordId>.capture.spec.ts` with line-1 `@playwright/test`→`./glaze-capture.mjs`), prunes old run dirs, creates the run dir, and runs the temp spec with env `GLAZE_ARTIFACT_DIR`/`GLAZE_TEST_ID`/`GLAZE_RUN_ID` (`GLAZE_CAPTURE_ARTIFACTS`=1); deletes the temp spec in `finally`; step line map built from the spec actually run. `buildStepLineMap` unchanged (line-preserving redirect). **Phase 2:** accumulates per-step pass/fail in `stepStatusMaps` (via `emitStep`, keyed by the reporter's step index) and, in `finally` when capturing, writes `replay.json` via `buildReplay(...)` — the single place that correlates the reporter statuses + the capture manifest against `Step[]`. **Reporter-attribution gotcha:** the capture fixture WRAPS action methods, so Playwright attributes wrapped actions' step location to `glaze-capture.mjs` and the step-reporter's file guard drops them → wrapped actions (goto/click/fill/…) get NO reporter status on a capture run. So `buildReplay` combines two signals: reporter statuses are authoritative for asserts/waits/page-level steps; a screenshot's presence ⇒ that action ran and passed; and the failing step is the first reported failure, else (for a failed run) the first uncaptured non-control step after the last screenshot. `captureMethod(step)` mirrors the fixture's PAGE_ACTIONS/LOCATOR_ACTIONS to match manifest entries to steps by method (so a misclassification can't cascade-desync the timeline).
- `main/services/capture-fixture-source.ts` — `captureFixtureSource`: the `glaze-capture.mjs` fixture as a raw JS string (bare `"` inside the template literal — escaped quotes trip `no-useless-escape`). Extends Playwright's `test` so its `page` fixture patches page-level (`goto`/`reload`/`setViewportSize`/…) and Locator-prototype (`click`/`fill`/`check`/`selectOption`/…) action methods to screenshot AFTER each action into `GLAZE_ARTIFACT_DIR` as `<index>.png` (index = 0-based action order), then writes `manifest.json` on teardown. Env-gated: exports plain `base` when `GLAZE_CAPTURE_ARTIFACTS!=="1"` (zero overhead, no patching). Every screenshot is `try/catch`-wrapped + `screenshot({timeout:5000})` so a failure is logged to stderr and skipped, never failing/altering the test.
- `main/services/page-actions.ts` — `PAGE_ACTIONS` (`goto`/`goBack`/`goForward`/`reload`/`setViewportSize`/`setContent`) and `LOCATOR_ACTIONS` (`click`/`fill`/`check`/`selectOption`/…): the canonical set of page-mutating Playwright methods, plus `actionsLiteral()` to embed them in a fixture source string. **Two** fixtures patch these now (capture screenshots after each; settle waits after each), and they are separate source strings — a second hand-maintained copy would drift the first time an action was added to one, and the failure is silent (the step still runs and still screenshots, it just never settles). One list, interpolated into both. Pinned by `check:crawl-speed`.
- `main/services/settle-fixture-source.ts` — `settleFixtureSource`: the `glaze-settle.mjs` fixture as a raw JS string, written next to the specs like the capture and heal fixtures. `installSettle(page)` patches the `page-actions.ts` methods so that after each action resolves — and **before control returns to the spec** — it awaits `waitForLoadState("load")` (15s cap), `waitForLoadState("networkidle")` (5s cap, expected to time out on a page with an open connection; reported once per run, not per step), then `document.fonts.ready` + a double `requestAnimationFrame` (2s cap). Env-gated on `GLAZE_SETTLE`, set by the runner only for a `crawl`-speed run of an app-generated test. **Never fails a test:** every wait is individually bounded and swallowed, and `withTimeout` attaches a terminal `.catch` — an abandoned wait whose page later navigates would otherwise become an unhandled rejection and fail an otherwise-fine run. The paint timer is deliberately NOT `unref()`d: an unref'd timer doesn't hold the event loop open, so when it is the only pending work the process exits instead of the fallback firing. `onSettled(fn)` is the extension seam page indexing will hang off — post-settle is the one moment the DOM is known stable. Why a fixture and not generated code: a spec is generated once and lives on disk while speed is changed afterwards from the sidebar slider, so emitted `waitForLoadState` calls would silently disagree with the setting.
- `main/services/run-pacing.ts` — pure run-pacing policy, split out of `playwright-runner.ts` so a timeout rule can be tested without bundling the visual pipeline. `SLOW_MO_MS` maps `TestRecord.speed` (`crawl`/`slow`/`medium`/`fast`) → `2500`/`1200`/`400`/`0` ms. `resolveTestTimeoutMs(perTest, settingsDefault, speed)` resolves explicit per-test → Settings default → 60s, then raises a `crawl` run to a `CRAWL_MIN_TEST_TIMEOUT_MS` (5 min) **floor**, returning `{timeoutMs, raised}`. The floor exists because crawl multiplies run time: against the 60s default, choosing the resilient speed would make tests fail. It is a floor, not an override — a longer timeout is left alone — and `raised` is what lets the runner say so in the output rather than changing a timeout silently.
- `main/services/artifact-store.ts` — `artifactStore` owns `<userData>/recorder/artifacts/<testId>/<runId>/`. `runDir`/`ensureRunDir`, `pruneRuns(testId, keep=DEFAULT_RETAINED_RUNS=10)` (delete all but newest `keep` run dirs by mtime), `listRuns`/`readManifest`, `deleteTest` (called from `tests:delete`). **Retention default kept at 10** (Phase 5 revisit): real usage measured ~0.6 MB per captured run for a small test (page PNGs ~0.1–0.4 MB each), so 10 runs ≈ 6 MB small / tens of MB large — recent history without waste. **`RESERVED_DIRS = {"baseline"}`:** both `pruneRuns` and `listRuns` now exclude the sibling `baseline/` dir — a Phase-5 bug fix, since it previously counted as a prunable "run" and retention could silently DELETE the pinned baseline (breaking the Phase 3/4 "baseline survives pruning" premise). The e2e regression check locks this. `ArtifactManifest`/`ArtifactStepEntry` = the per-step capture model (screenshot success). **Phase 2 replay model:** `RunReplay`/`ReplayStep`/`ReplayStepStatus` (`passed|failed|skipped|unknown`) + `RunReplaySummary`; `writeReplay`/`readReplay` (per-run `replay.json`), `listReplays()` (scans the artifacts tree for all `replay.json`, newest first — naturally reflects retention), `readShot(testId,runId,file)` (returns PNG bytes; `file` validated to `^\d+\.png$` so it can't escape the run dir).
- `main/services/replay-builder.ts` — the runner's replay-correlation brain, **extracted from `playwright-runner.ts` in Phase 5** so it's regression-testable without spawning Playwright: `captureMethod(step)`, `buildReplay(...)` (correlates reporter statuses + capture manifest → `RunReplay`), `enrichWithVisualDiffs(replay, threshold)` (Phase 3 diff pass). Depends only on artifact/baseline stores + `diffPngBuffers` + `describeStep` — no `child_process`/IPC — so a standalone check can drive it. `playwright-runner.ts` now imports these two functions instead of defining them (behavior identical).
- **`runStep` is the single replay dispatch point** (`recorder-service.ts`). All four replay paths route through it. `cookie` steps CANNOT go through `buildReplayScript` — an httpOnly cookie is invisible to `document.cookie` — so they branch to `applyCookieStep`. Added deliberately as one dispatch point after the Auto-Heal bug, where a capability was wired into one replay path and silently missing from the other three: a new step kind now cannot be handled in some paths and missed in others. `withCaptureSuspended` is the same pattern one level up — one place that decides what a replay does to the SESSION, for the same reason.
- **Testing (two systems, one command).** `npm run test:all` = the 15 standalone `check:*` scripts, then Vitest. `npm test` runs Vitest alone; `npm run test:watch` for watch mode.
  - **Vitest** was added because Vite 8 was already a devDependency, so it reuses the toolchain rather than adding a second bundler. Config in `vitest.config.ts`, two projects: **`node`** (backend + pure renderer logic; `main/**/*.test.ts`, `mcp/**/*.test.ts`, `renderer/lib/**/*.test.ts`) and **`dom`** (jsdom; `renderer/**/*.test.tsx` + `main/**/*.dom.test.ts`).
  - **The hard part is `@glaze/core/*`**, which resolves through the Glaze runtime's ESM loader hooks + tsconfig paths, neither of which exists under a runner. `backend` → the test stub (NEVER the real module — it talks to the native host and would touch real userData); `components`/`hooks`/`ipc` → the SDK's REAL prebuilt ESM bundles, so component tests exercise the actual design system. Those bundles sit outside the project root, so their bare imports (`react`, `react-dom`, `@tanstack/react-query`) are pinned to this project's copies — which also guarantees ONE React instance, since two produce "invalid hook call" errors that look like component bugs. To find the set if the SDK is upgraded: `grep -ohE 'from"[^".][^"]*"' <sdk>/components.js | sort -u`. `sonner` is STUBBED, not installed (it's the SDK's dependency, not this app's); the stub also makes toasts assertable.
  - **`.dom.test.ts` vs `.test.ts` matters:** the node project explicitly excludes `**/*.dom.test.ts`, or DOM tests match both globs and run a second time with no document, failing for reasons unrelated to the code.
  - **jsdom has no layout engine** — `getBoundingClientRect()` returns zeros, so the replayer's `visible()` (correct for a real browser) treats everything as hidden. `step-replayer.dom.test.ts` installs a nominal box; without it, visibility tests fail AND "hidden → passes" silently becomes a test that proves nothing.

- **Cross-copy parity checks are a house pattern.** Five places duplicate logic that can't be shared, each pinned by a test: app↔MCP batch summary and app↔MCP concurrency clamp (`check:batch-runner`), app↔MCP `playwright.config.ts` (`check:runner-config`), backend↔renderer `describeStep` (`describe-step-parity.test.ts`), and the capture-script↔replayer locator contract (`step-replayer.dom.test.ts`). Two of them caught real drift.
- **Regression checks** (`main/services/__tests__/*.check.ts`, run via `npm run check:*`). There is **no test runner** in this project — each check is a standalone script using plain assertions + a non-zero exit code, and adding one alongside a behavioral change is the house convention. Eighteen exist: `spec-parser`, `visual-pipeline`, `ai-debug-scroll`, `capture-overhead`, `retention`, `auto-heal-wiring`, `run-filters`, `batch-runner`, `runner-config`, `batch-history`, `test-tags`, `mcp-select`, `alerts`, `cookie-steps`, `batch-order`, `paginate`. `glaze-backend-stub.ts` now also stubs `safeStorage` — it reports encryption as UNAVAILABLE so a check can never write a real secret to disk. **The esbuild-bundled checks do NOT type-check** — `npm run type-check` is the real gate for them (a spread overwriting an explicit property slipped past a green `check:batch-history` once). Three styles: pure-logic checks run under `tsx` directly; the MCP checks are plain `.mjs` run by `node`; anything importing `@glaze/core/backend` must be bundled with esbuild + `--alias:@glaze/core/backend=./main/services/__tests__/glaze-backend-stub.ts` (plain tsx/node can't resolve that specifier). `check:auto-heal-wiring` is a *source-level* check — it slices each replay method out of `recorder-service.ts` and asserts it calls `healAndRetry`, guarding against a path silently losing Auto-Heal again. `check:replay-suspend` is its sibling and works the same way: it slices out each replay method and asserts it runs inside `withCaptureSuspended` and never touches `session.paused` directly — a replay path that skips it RECORDS WHAT IT REPLAYS, appending a duplicate step every time the user previews one, which is silent and looks like a test that grew on its own.
- `main/services/__tests__/visual-pipeline.check.ts` — **Phase 5 end-to-end regression check** covering the whole visual pipeline in one path: seed artifacts → `buildReplay` correlates → seed baselines → intentional change flagged `changed` (+ diff overlay) → `acceptStep`/`acceptRunBaseline` clears the flag → annotation upsert/list round-trip → `pruneRuns` retention (baseline survives). Drives the REAL stores against a temp `userData` dir; `@glaze/core/backend` is aliased to `__tests__/glaze-backend-stub.ts` (lazy `app.getPath`→`GLAZE_TEST_USERDATA`, no-op `logger`). Run via `npm run check:visual-pipeline` (esbuild bundle `--format=cjs` with the alias, then `node` — plain tsx/node can't resolve `@glaze/core/backend`, and pngjs is CJS so esm output breaks on dynamic `require`; sandbox-safe, no listen socket).
- `main/services/app-window.ts` — Holds main-window ref; `sendToMain(channel, payload)` for backend→renderer push. **Also fans out to registered auxiliary windows** (`registerAuxWindow`/`unregisterAuxWindow`), which is how the trainer panel receives every existing channel without touching the ~50 call sites. The fan-out lives INSIDE `sendToMain` on purpose: a panel that receives most pushes but not all would leave two trainers disagreeing about the step list, which reads as a step-ordering bug in the recorder rather than a missing subscription.
- `main/services/panel-dock.ts` — **Pure** dock geometry for the trainer panel. `computeDock` (dock-time: splits the browser's footprint into browser + panel, total-preserving, `null` when the display can't hold both at their minimums — unless `DockOptions.preserveBrowserWidth`, for a session recording at a **window-size preset**, where the browser's width is the size the test replays at rather than a footprint the user dragged: the pair's total grows instead of splitting, `BROWSER_MIN_WIDTH` does not apply because a 390-wide mobile preset is deliberately below it, and not fitting the display returns `null` so the panel opens undocked rather than resizing a browser it was told not to), `computePanelFollow` (every move/resize thereafter: places the panel against the browser's edge and does NOT touch the browser — flips to the other side when the preferred one runs out of display, `null` when neither fits so the caller undocks), `computeUndock`, `boundsEqual`, `isDuplicateApply`. ### Settings window

Redesigned 2026-08-07 from one flat scroll into a sidebar of eight panes with search. See DECISIONS.md for why this shape.

- `renderer/lib/settings-schema.ts` — the window's shape **as data**, pure and DOM-free so it runs in the node project. `PANES` (id/title/subtitle/group) and `paneSegments()`, which returns RUNS of consecutive panes sharing a group rather than one bucket per group — two separate stretches are ungrouped (Appearance at the top, Advanced at the bottom), and bucketing by value would render Advanced directly under Appearance. `SETTING_INDEX` maps every row to its pane, its label, its search keywords and the `RecorderSettings` key it writes (absent for credential-backed and action rows, which is what keeps "reset section" away from the API key and the webhook URL). `searchSettings(query)` is case-insensitive substring over label + keywords + the owning pane's title, every term required — substring rather than fuzzy, because a settings search that returns near-misses is worse than one that returns nothing. `SETTINGS_DEFAULTS` mirrors `recorder-settings-store.ts` (which stays the authority) so the window can say "3 settings differ from the default" without asking the backend; `modifiedKeys`/`resetPatch` build on it, with a `sameValue` that compares arrays and `{width,height}` structurally — reference equality would report an untouched `disabledAestheticEnhancements` as modified on every load. Also the five **clamps** (`clampTestTimeoutSec`, `clampRetainedRuns`, `clampRetentionDays`, `clampHealRetries`, `clampHealTimeoutMs`), lifted out of the old async handlers where the only way to test "9999 runs is refused" was to render a window and fire a change event, plus `formatBytes`. Covered by `settings-schema.test.ts` (118 tests), whose load-bearing assertion is that **every persisted default is surfaced in exactly one pane** — a key in the store with no row is unreachable, a key claimed by two panes shows two different modified-counts for one value, and both are invisible on screen.
- `renderer/settings/settings-controller.tsx` — every piece of state and every handler, lifted wholesale out of the old view. One controller rather than per-pane state because two loads have side effects that must fire when the WINDOW opens, not when a section is looked at: the LLM auto-probe rewrites the configured model when the stored one is no longer installed, and the settings load feeds every pane's modified-count. The ~20 `useState`s for `RecorderSettings` fields collapse into one object plus `save(patch)`; the patch shape is unchanged (one key per `recorder:setSettings` call, merged backend-side), so nothing crossing IPC moved. `save` is **optimistic and does not roll back** on failure — the toast reports it, and a rollback would fight the user's next keystroke. Each load goes through a local `load()` helper whose `try` matters as much as its `.catch`: the calls are made synchronously inside the effect, so a surface that THROWS (a preload that didn't expose it) would abort the effect and skip every load after it. A **resolved** `null` from `recorder:getSettings` is coerced to `{}` for the same reason — it doesn't reach the catch, and the first pane to read a key off null took the whole window down. `SettingsControllerProvider` is the test seam.
- `renderer/settings/settings-view.tsx` — the shell only: `SplitView` + nav + the active pane, search wiring, the reset footer, Escape-to-close (unchanged — a field's own Escape and a Select's must win over closing the window). A search that empties the selected pane moves to the first pane that still has a hit; staying put would show an empty pane beside a sidebar advertising matches elsewhere.
- `renderer/settings/settings-nav.tsx` — the sidebar. The row accessory does double duty: match count while searching, modified count otherwise. Panes with no match **leave the list** rather than greying, because greying keeps the list the same length and hides that search narrowed anything. Adds `aria-current="page"` itself — the SDK's `selected` only applies a background class, so nothing was announced.
- `renderer/settings/setting-row.tsx` — one row. `summary` is always visible; `details` goes behind a disclosure (descriptions were ~2/3 of the old window's vertical space). **`danger` suppresses `details` outright** rather than trusting callers to leave it unset: the two rows that carry it warn about storing credentials and about sending data off the Mac, and a warning behind a click is a warning nobody reads. `nested` indents a dependent row and draws the dependency rule. `stacked` moves the control to its own full-width line below the label, for rows whose control is a cluster rather than one switch — in the horizontal layout the two columns compete for the same width and the wide one wins. Search filtering happens HERE via `RowFilterProvider`, so a pane's JSX is the same whether or not a search is running — there is no second, filtered rendering path to drift.
- `renderer/settings/pane-section.tsx` — a titled group that removes itself when a search filters away every row it holds. Reads the `id` prop off its children rather than taking a second list of ids, which would drift.
- `renderer/settings/panes/*.tsx` — Appearance (theme + flourishes), Recording (trainer window), Test defaults, Auto-Heal, Storage, AI, Alerts, Advanced. **Test defaults is the pane the redesign is built around**: a third of the window's settings answer "what should a NEW test do", they map one-to-one onto `test-detail-view.tsx`'s six run controls, and they are ordered to match it — so the two read as the same panel at two scopes. The pane subtitle now carries the "each test can override this" fact that used to be repeated in half the row descriptions. Dependent rows are **unmounted, not greyed** (`record-all-headers` under `default-record-logs`; the Auto-Heal parameters under the Auto-Heal switch) — the old greyed-out siblings had nothing on screen saying which setting controlled them, and the Auto-Heal parameters were editable while writing settings nothing would read. Storage promotes the usage figure out of the middle of a description string into the pane's first element; it is the only live number in the window, and both its retention controls are `NumberInput` with the unit (`days`) rendered INSIDE the control — a sibling `<span>` displaced the right-aligned field by its own width and knocked the two inputs out of line with each other. Auto-Heal's two parameter controls are the same shape for the same reason (`ms`), and keep an explicit `aria-label` because `NumberInput`'s unit is `aria-hidden`. Alerts is the one place a toggle **confirms before turning on** (`AlertDialog`, ON only), because it starts sending data off the Mac on a schedule the user no longer intervenes in; its Webhook URL row is `stacked` so the field-plus-three-buttons cluster doesn't crush the label column.
- Descriptions use the SDK's `FieldDescription`. The old view's `<p className="text-sm text-muted-foreground">` was a **dead class** — no `muted-foreground` token exists in the design system, so every description rendered at full-strength primary text, which is a large part of why the window read as an undifferentiated wall.
- `main/windows/settings-window.ts` — 760×560, min 620×420 (was 560×480, min 440×320). The sidebar only pays for itself if the pane beside it is wide enough for a label, its description and a control on one row.

### Build, test and preview tooling
- `scripts/bootstrap-worktree.mjs` — `npm run bootstrap`. Symlinks a git worktree's `node_modules` at the main checkout's, so a fresh worktree can run lint/type-check/`test:all` immediately instead of paying a multi-minute install (or, as was the case before this, running none of them: a fresh worktree has no dependency tree at all). **Refuses when the two `package-lock.json` files differ** — a shared tree across branches with different dependencies means an install on one silently rewrites the other's, which surfaces days later as an unexplained version error on a branch nobody touched. `.gitignore` spells `node_modules` without a trailing slash so the symlinked form is still ignored.
- **`shell/electron` branch** — the de-Glazed tree: stock Electron + Vite + esbuild, nothing outside `node_modules`, so `npm ci && lint && type-check && test:all && build` all run on a hosted CI runner, which this branch structurally cannot do. Branched from `a61598c` (the port's real merge base, established by comparing all 199 shared source files against each candidate), so `git diff main..shell/electron` is the port itself and the 12 commits of drift arrive by cherry-pick. It carries `.github/workflows/gate.yml` (the real gate on ubuntu; end-to-end + `electron-builder` on macOS), an `e2e/` suite that drives the actual app through Playwright's `_electron` support, and `renderer/dev/` — a `window.glazeAPI` stand-in over fixtures that runs the whole UI in an ordinary browser tab (`npm run dev:web`, `npm run build:preview`). See `docs/plans/testing-pipeline-and-preview-environments.md` for the phased plan and `docs/DECISIONS.md` (2026-08-07) for why.

### Data & storage
- `userData/recorder/tests.json` — array of `TestRecord`.
- `userData/recorder/scripts/<id>.spec.ts` — generated specs. A `node_modules` symlink → app node_modules is created here so specs resolve `@playwright/test`.
- `userData/recorder/browsers/` — Playwright browser install (`PLAYWRIGHT_BROWSERS_PATH`).
- `userData/recorder/run-history.json` — array of `RunRecord` (run stats index; capped 1000). `userData/recorder/logs/<runId>.log` — raw console output per run. These two are deleted independently (see the Stats feature): reset-stats keeps the `.log` files. `RunRecord.id` is now minted at run START by the runner (passed into `append`) so it equals the artifacts `runId`.
- `userData/recorder/artifacts/<testId>/<runId>/` — **visual-testing screenshots (Phase 1)**: `<stepIndex>.png` (0-based page-action order) + `manifest.json` (`{testId,runId,title,status,startedAt,finishedAt,steps:[{index,action,target,value,ok,ts}]}`). `runId` === `RunRecord.id`. Written by the `glaze-capture.mjs` fixture inside the Playwright worker; NOT inlined into tests.json (binary blobs kept out of the JSON store). Retention: newest 10 run dirs per test (`artifact-store.ts`). Deleted with the test via `tests:delete`. **Phase 2:** the run dir also holds `replay.json` — the canonical per-step replay model (`{testId,runId,testName,url,status,startedAt,finishedAt,failedIndex,visualThreshold?,steps:[{index,stepId,label,type,status,screenshot,diff?}]}`, aligned to `Step[]` index, `screenshot` a filename or null). Written by the runner (`buildReplay`), read by the Visual tab. Runs captured before Phase 2 lack `replay.json` so they don't appear in the replay list. **Phase 3 (visual diffing):** each `ReplayStep` also carries `diff?: {state:"new-baseline"|"match"|"changed"|"unable", ratio?, threshold?, reason?, diffFile?}` and the run dir holds `<stepIndex>.diff.png` overlays for `changed` steps. **Pinned baselines** live at `userData/recorder/artifacts/<testId>/baseline/<stepId>.png` + `baseline.json` (`{testId,updatedAt,steps:{[stepId]:{stepId,runId,at,label}}}`) — keyed by `Step.id` (NOT URL: a test is a deterministic script and Step.id survives reorder/insert; only screenshot-producing steps get a baseline). Managed by `baseline-store.ts`; deleted with the test via `tests:delete`. The first captured run seeds baselines; later runs diff against the PINNED baseline (never the previous run). Diffing is pure-JS (`visual-diff.ts` → pixelmatch + pngjs, no native bindings); size mismatch (viewport/responsive change) or a decode error degrades to `state:"unable"`, never a false flag. Per-test threshold on `TestRecord.visualThreshold` (percent of pixels, default `DEFAULT_VISUAL_THRESHOLD` = 0.1 in `recorder/types.ts`).
- `userData/recorder/alert-webhook.bin` — the outgoing-alert webhook URL, **encrypted via `safeStorage`** (atomic `.tmp` rename), managed by `webhook-url-store.ts`. Same treatment as the Anthropic key: backend-only, never returned to the renderer — only `{hasUrl, host}` crosses IPC.
- `userData/recorder/batch-history.json` — array of `BatchRecord` (batch id, per-test results, summary; capped 50, newest first). Written **write-through** by the batch runner after every per-test transition, and by the MCP server's `run_batch` in the same shape — so a batch driven from an MCP client appears in the app's Batch view. Joined to individual runs by `RunRecord.batchId`.
- `userData/recorder/annotations.json` — **Phase 4 step notes**: flat array of `Annotation` (`{id,testId,runId,stepId,text,createdAt,updatedAt}`), one per `(runId, stepId)`. Deliberately its own index file (mirrors `tests.json`'s pattern) rather than embedded in `replay.json`, since `replay.json` is a runner-owned model fully regenerated every run — annotations must survive that regeneration and outlive artifact retention pruning. Managed by `annotation-store.ts` (`list/upsert/deleteTest`); blank text in `upsert` deletes the note. Deleted with the test via `tests:delete`.
- `userData/recorder/llm-config.json` — `{ provider, model, baseUrls }` for the LLM integration. `provider` is now `"ollama" | "lmstudio" | "anthropic"`.
- `userData/recorder/anthropic-key.bin` — the user's Anthropic API key, **encrypted via `safeStorage`** (written atomically via a `.tmp` rename). Managed by `anthropic-key-store.ts`; the key stays backend-only (decrypted in-process cache, never returned to the renderer). Only `hasKey` booleans cross IPC.
- `userData/recorder/recorder-settings.json` — global preferences: `{ showUrlBar: boolean (default true), defaultRunSpeed, defaultWindowSize: {width,height} | null (default null = the trainer's own window size; normalized on read/write via `normalizeViewport`), autoHealEnabled: boolean (default true), autoHealRetries: number (default 3, clamp 1–10), autoHealAttemptTimeoutMs: number (default 4000, clamp 1000–30000), defaultRunBrowser: "chromium"|"firefox"|"webkit" (default "chromium", validated on read/write via `isRunBrowser` — an unknown engine name would otherwise be handed straight to the Playwright CLI and fail the run), defaultCaptureArtifacts: boolean (default false), defaultRunHeadless: boolean (default false), disabledAestheticEnhancements: string[] }`. Backed by `recorder-settings-store.ts` (validates/clamps on load and set). Snapshotted into the session at `recorder:start`. `defaultRunHeadless` is the fallback for the per-test "Run headless" toggle (test runs only — does NOT affect the trainer). Per-test override persisted on `TestRecord.runHeadless` via `tests:setHeadless`, mirroring `captureArtifacts`.

### IPC channels
- Invoke: `recorder:start {url,name,testId?,viewport?}` (testId seeds the session from an existing `TestRecord` — its steps/url/name/createdAt win over the passed url/name, and so does its recorded viewport; `viewport` is the New Recording dialog's window-size preset, normalized by `normalizeViewport` and recorded as the session's first `viewport` step) / `recorder:pause` / `recorder:resume` / `recorder:setAssert {mode,soft?}` / `recorder:deleteStep {stepId}` / `recorder:insertStep {step,index?}` / `recorder:reorderStep {stepId,toIndex}` / `recorder:updateStep {stepId,patch}` / `recorder:setCursor {index}` / `recorder:replayStep {stepId}` → `{ok,error?}` / `recorder:startRefine` / `recorder:endRefine` (Refine Selector picker: startRefine pauses + enters pick mode, endRefine resumes; both take no args — the target step is tracked renderer-side in `refiningStepId`, and a pick updates that step's locator rather than inserting a new step) / `recorder:stop` / `recorder:getState` → `RecorderState` (now includes `editing`, `assertSoft`, `cursor`, `refineMode`). Push: `recorder:steps` (full `Step[]`, after every mutation — replaces the old per-step `recorder:step`) and `recorder:picked` (`PickedElement` — an element captured via Refine Selector).
- Invoke: `trainerPanel:dock` / `trainerPanel:undock` → `{docked}`. Push: `trainerPanel:docked {width}` / `trainerPanel:undocked {reason}` / `trainerPanel:viewportNarrowed {width}`. Dock state lives in the BACKEND (it moves real windows) and the panel's button follows the push rather than flipping optimistically — a dock can legitimately be refused on a display too small to hold both windows, and an inverted label makes the control look dead. `viewportNarrowed` fires once per session because docking shrinks the training browser, so a responsive site may render a layout the user did not choose.
- Invoke: `recorder:getSteps` → `Step[]` — the session's current steps, for a window that opened AFTER the initial `recorder:steps` push (that push fires inside `recorder:start`, so the docked panel never sees it). The store calls this on mount alongside `getState` and sets `stepsLoaded`; both trainers gate `controlsDisabled` on it, because acting on a step list you have not received yet inserts at the wrong position. The insert cursor opens at `initialCursor(editing, stepCount)` — index 1 when continuing an existing test, since opening a session executes only the initial navigation.
- Invoke: `recorder:getSettings` → `RecorderSettings` (includes `defaultTestTimeoutMs`, default 60000) / `recorder:setSettings {…}` → `RecorderSettings`, backed by `recorder-settings-store.ts`. Snapshotted into the session at `recorder:start` (a mid-session toggle doesn't affect an already-open trainer window; it takes effect next time a trainer window opens). Per-test Playwright timeout override: `tests:setTestTimeout {id, testTimeoutMs: number|null}` (null clears); runner resolves override → Settings default → 60s and passes `--timeout=` + `PW_TEST_TIMEOUT_MS`.
- Invoke (Auto-Heal): `recorder:applyHeal {stepId, locator}` → applies a chosen heal candidate's `Locator` to the step (thin wrapper over `updateStep`, then broadcasts `recorder:steps`). Push: `recorder:healSuggestion` (a `HealResult` with `autoApplied`) — fired by `tryHeal` when the engine finds candidates during **any** replay path; also carried on the `recorder:replayLog` `step` event's `heal` field so the Console can render candidates/badge inline. **Auto-Heal replay flow (`tryHeal` + `healAndRetry` in `recorder-service.ts`):** Auto-Heal runs in **all four** replay paths — `replayStep` (single-step preview), `replayFromStart`, `replayAll` (Edit-in-Trainer auto-run), and `replayFromCurrent`. It was originally wired into `replayFromCurrent` only; the shared re-run wiring now lives in `healAndRetry(wc, step, index, error)`, which every path calls, and structural `if` steps are excluded in the loop paths (no healable target). Guarded by `check:auto-heal-wiring`. When a step fails with an element-not-found error AND `autoHealEnabled`, it runs `healStep`, and if candidates are found it re-runs the step with the best candidate; on success it sets `heal.ok=true`, `heal.autoApplied=true`, `heal.appliedLocator`, auto-applies the locator to the step, and treats the step as passed. Otherwise the (un-applied) candidates stream to the Console for the user to pick manually.
- Invoke: `tests:list` / `tests:get {id}` / `tests:getScript {id}` / `tests:delete {id}` / `tests:rename {id,name}` (skips script regen if `scriptEdited`) / `tests:updateScript {id,source}` (writes the spec file, sets `scriptEdited: true`; for non-imported tests also resyncs `steps` via `parseSpecDetailed` and sets `stepsDiverged` when any statement couldn't be classified — surfaced as a `Callout` in `test-detail-view.tsx`) / `tests:setSpeed {id,speed}` → `TestRecord` (`speed` is `"slow"|"medium"|"fast"`, validated in the handler) / `tests:setHidden {id,hidden}` → `TestRecord | null` (toggles sidebar visibility; no file deletion).
- Invoke: `tests:importFiles` (opens native folder picker) / `tests:importGit {url}` → `{ imported: number; names: string[]; ids: string[] }` (ids for post-import navigation). Both handled by `import-service.ts`. `tests:repairImports {id}` → `{ copied: string[] }` re-copies an imported test's sibling modules from its `sourceDir`.
- Invoke (LLM): `llm:getConfig` → `LlmConfig` / `llm:setConfig {provider?,model?,baseUrls?}` → `LlmConfig` / `llm:status {provider}` → `LlmProviderStatus` (for `anthropic`, `reachable` = valid key that lists models; adds `hasKey`) / `llm:detect` → `LlmProviderStatus[]` (local providers only; Claude probed on demand via `status`) / `llm:listModels {provider}` → `LlmModel[]` / `llm:chat {messages,provider?,model?,temperature?}` → `{requestId}` (streams) / `llm:cancel {requestId}`. **Anthropic key channels:** `llm:setApiKey {key}` → `{hasKey:true}` / `llm:clearApiKey` → `{hasKey:false}` / `llm:hasApiKey` → `{hasKey}` (never returns the key). Renderer wrappers under `api.llm.*` in `renderer/lib/api.ts`; renderer type mirror in `renderer/lib/llm-types.ts`. No new preload wiring — reuses the existing `glaze.ipc` bridge.
- Push (LLM, via `sendToMain`): `llm:chunk {requestId,delta}`, `llm:done {requestId,cancelled?}`, `llm:error {requestId,message}`. Consumed by `renderer/lib/use-llm-chat.ts` (phase 2's `AiDebugDialog`).
- Invoke: `runner:run {id,headed,captureArtifacts?}` → `{runId}` (runId === testId); `runner:stop {runId}`. **`captureArtifacts` (default off)** is the per-run visual-testing gate (Phase 0 of the visual-testing roadmap) — NOT on `TestRecord` (that's a permanent property; this is a per-run choice) and distinct from the DOM-action training recorder. `playwrightRunner.start` threads it to the Playwright subprocess as env `GLAZE_CAPTURE_ARTIFACTS` ("1"/"0", alongside `PW_SLOWMO_MS`) and records it on the `RunRecord`. (That gate is now fully implemented — capture/storage/diffing all shipped in later phases; earlier notes saying it "carries no capture logic yet" are stale.) UI: a "Capture screenshots" `Checkbox` in `test-detail-view.tsx`'s `ToolbarActions` next to Run test (local state, default off, disabled while running) → `run(id, captureArtifacts, headless)`. **`headed`** is now driven by a per-test **"Run headless"** `Checkbox` (also in `ToolbarActions`, next to Capture screenshots; init from `test.runHeadless ?? defaultRunHeadless`, persisted via `tests:setHeadless`): `run()` in `recorder-store.tsx` invokes `api.runner.run(id, !headless, captureArtifacts)` — headed = not headless. `playwrightRunner.start` appends `--headed` only when `headed` is true, so omitting it runs Playwright headless. Runs only — trainer (`recorder:*`) is unaffected. Invoke: `tests:setHeadless {id,runHeadless}` → `TestRecord`.
- Invoke (visual replay, Phase 2): `artifacts:list` → `RunReplaySummary[]` (all captured runs with a `replay.json`, newest first; each carries `changedSteps` count for the run list's visual-change marker) / `artifacts:getReplay {testId,runId}` → `RunReplay | null` / `artifacts:readShot {testId,runId,file}` → data-URL string | null (base64 PNG; `file` validated to `<n>.png` or `<n>.diff.png`). Under `api.artifacts.*` in `renderer/lib/api.ts`; type mirrors in `renderer/lib/recorder-types.ts`; reuses the `glaze.ipc` bridge (no preload change).
- Invoke (visual diffing, Phase 3): `visual:getThreshold {testId}` → number / `visual:setThreshold {testId,threshold}` → number (clamped 0–100, saved on `TestRecord`) / `visual:acceptRun {testId,runId}` → `RunReplay | null` (pin every captured step of a run as new baselines) / `visual:acceptStep {testId,runId,stepId}` → `RunReplay | null` (pin one step) / `visual:baselineShot {testId,stepId}` → data-URL | null. Accept ops (`visual-baseline-ops.ts`) re-pin the baseline AND patch the run's `replay.json` so the accepted step flips to `match` (ratio 0) immediately. Under `api.visual.*` in `renderer/lib/api.ts`.
- Invoke (batch runs): `batch:run {testIds, captureArtifacts?, runHeadless?, browser?}` → `{batchId, alreadyRunning}` (throws if `testIds` is empty; an unknown `browser` falls back rather than failing the run) / `batch:stop` / `batch:status` → `BatchState | null` (includes a finished batch's results, so the view can restore them). Push: `batch:progress` and `batch:done`, both carrying the whole `BatchState` + `summary`. Batch state is **persisted** (see `batch-history-store.ts`) and survives restarts; `RunRecord.batchId` joins runs back to their batch.
- Invoke: `tests:setBrowser {id, runBrowser}` → `TestRecord` (per-test browser engine; validated backend-side).
- Invoke: `tests:setTags {id, tags}` → `TestRecord`. `tags` is typed `unknown` and passed through `normalizeTags` (trim, collapse inner whitespace, dedupe case-insensitively with first spelling winning, sort, cap 20 tags × 32 chars) — it sits directly behind IPC, so a non-array or non-string entries normalize to `[]` rather than throwing or persisting junk into `tests.json`. Idempotent, so repeated saves don't churn the record.
- Invoke: `tests:deleteTag {tag}` → `{tag, removed}`. Removes the tag from every record carrying it (case-insensitive, hidden tests included). `tag` is typed `unknown` and goes through `normalizeTags` too, so canonical form has exactly one definition; anything that normalizes away throws "A tag is required" rather than touching the library. `removed` is the true count and can exceed what the renderer previewed, since `tests:list` excludes hidden tests.
- Invoke (trainer cookies): `recorder:listCookies` → `LiveCookie[]` / `recorder:setCookie {cookie}` / `recorder:deleteCookie {cookie}` / `recorder:clearCookies` — each mutation returns the FRESH list so the panel can't drift from the session. These act on the training browser immediately; recording a change as a step is separate (`recorder:insertStep` with a `cookie` step).
- Invoke (alerts): `alerts:setWebhookUrl {url}` → `{hasUrl, host}` (validates http(s), stores encrypted) / `alerts:clearWebhookUrl` / `alerts:status` → `{hasUrl, host}` / `alerts:test` → `{ok}` (posts a canned payload and **rethrows on failure**, unlike `sendAlert` — the point of a test button is to find out that it doesn't work). The URL only ever travels renderer→backend.
- Invoke (batch history): `batch:list` → `BatchRecord[]` (newest first) / `batch:get {batchId}` / `batch:delete {batchId}` → `{removed}` / `batch:clearHistory` → `{removed}`.
- Invoke (run history): `runs:list` → `RunRecord[]` / `runs:getLog {id}` → raw log string / `runs:searchLogs {query}` → `LogSearchResult[]` / `runs:resetStats` → `{removed}` (keeps logs) / `runs:deleteAll` → `{removed}` / `runs:deleteRange {fromMs,toMs}` → `{removed}` / `runs:logsDir` → absolute logs dir. Push: `runs:changed` (fired after a run is persisted; StatsView invalidates `["runs"]`). All under `api.runs.*` in `renderer/lib/api.ts`; reuses the `glaze.ipc` bridge (no new preload).

### Conventions & constraints
- **External Claude Code collaboration:** `CLAUDE.md` (repo root, tracked in git) is a handoff doc for a Claude Code CLI session run directly in this folder — architecture, directory map, hard constraints (forbidden imports, protected dirs, npmrc rules), SDK reference paths, and npm commands. External sessions can edit + `npm run lint`/`type-check`/`build`, but can't launch or live-preview the native app — that still requires the Glaze app. Both share the same local-only git repo (no remote); commits from either show up interleaved in `git log`.
- **Sidebar `actions` cannot host a React dropdown menu.** `Sidebar` runs `applyButtonDefaults` over its `actions`, which breaks any `*DropdownMenuTrigger asChild` wrapper — both the native `DropdownMenu` and `CustomDropdownMenu` render an empty actions wrapper (no trigger button, no error thrown). Verified: only the plain `<Button>` renders there. For a header action menu, keep a plain `<Button>` in `actions` and open a native menu from its `onClick` via `window.glazeAPI.Menu.popup({ items, x, y, coordinateSpace: "view" })` (already exposed in `preload.ts`), switching on the returned `commandId`. Anchor with the button's `getBoundingClientRect()` (left/bottom); leave `positioningItem` unset (a harmless "ignoring invalid positioningItem" debug warning is logged). **`coordinateSpace: "view"` is required** — `Menu.popup`'s `x`/`y` are documented as absolute screen-space coordinates, but `getBoundingClientRect()` gives coordinates relative to the window's content view. Without `coordinateSpace: "view"`, those small view-local numbers get treated as virtual-desktop coordinates and the menu always opens near the primary display's origin (i.e. on the laptop screen) even when the app window is on a different display. All four renderer popup call sites (`recording-view.tsx` ×2, `library-sidebar.tsx`, `stats-view.tsx`) now pass it. The backend context menu in `recorder-service.ts` (`menu.popup({ window: recWindow, ... })`) is unaffected — it passes an explicit `window`, which anchors it correctly regardless of coordinate space.
- **Glaze `webContents.executeJavaScript` runs each call in a fresh ephemeral content world** — JS globals do NOT persist between calls, and the backend `console-message` event does NOT fire for page logs. The recorder therefore stores all state + the step queue on shared `<html>` DOM attributes (which persist for the document lifetime and are readable from any world) and the backend polls to drain them. Do not switch back to console/global-based capture.
- Recording window loads the external URL directly with `titleBarStyle: "default"` and NO app preload (external/untrusted page). Popups are denied and loaded in-place via `setWindowOpenHandler`.
- **No custom in-window address bar is possible:** the recorder window's content IS the externally-loaded page (no app-owned HTML wrapper, no `<webview>`/`WebContentsView` embedding in this SDK), so a real editable URL bar can't be overlaid on the page. The "URL bar" is the native title bar instead — `recorder-service.ts`'s `updateTitle()` sets `recWindow.setTitle("Recording/Editing — <current URL>")` on every `did-navigate` when `session.showUrlBar` is true (the global default), so it tracks navigation live; when the setting is off, the title is left at its static initial value (set once at window creation) and never updated.
- **All navigation stays in the trainer window (3 layers):** Glaze routes navigations out to the system browser in ways that broke recording. Fixes, in `recorder-service.ts` `start()` + capture script:
  1. **Plain cross-origin `<a href>` links (the main culprit):** Glaze hands cross-origin main-frame navigations to the default browser. `wc.on("will-navigate")` calls `details.preventDefault()` then `loadNavInWindow(url)` (re-issues via `loadURL`) for main-frame, non-same-document http(s) navigations. A `selfLoad` guard prevents the programmatic `loadURL` from being re-intercepted (loop). `did-navigate` no longer needs to be prevented.
  2. **`target="_blank"` anchors:** capture script `keepInWindow()` rewrites the clicked anchor/form `target` to `_self` in the capture-phase click/keydown, plus injects `<base target="_self">`.
  3. **`window.open`:** `setWindowOpenHandler` returns `{action:"deny"}` and calls `loadNavInWindow`; `did-create-window` closes any stray child as a backstop.
  - NOTE: an external browser window is NOT a Glaze window, so it never appears in `LiveAppInspectionStatus`. Verify in-window navigation by reading the recorder window's own `location.href`, not by counting app windows.
- The navigating click is caught by draining on `will-navigate`/`did-navigate` in addition to the 250ms poll.
- Runner spawns with `process.execPath` + `ELECTRON_RUN_AS_NODE=1`, `cwd` = scripts dir, `NODE_PATH` = app node_modules.
- Built backend runs from `.glaze/build/main`, so runtime deps must be resolved against `.glaze-sources/node_modules` (see `resolvePlaywright` candidate scan).
- **`Slider`'s `onValueCommit` is unreliable for a plain click (no drag) — commit on `onValueChange` instead.** `TestSpeedSlider` in `library-sidebar.tsx` originally persisted on `onValueCommit`; the thumb's local value visibly updated on click but the backend write never happened (no `tests:setSpeed` call, no `testStore.save` log line) because a single click never produces the drag gesture Radix's slide-end/pointerup handling expects. Fixed by calling the commit logic directly from `onValueChange`, guarded by a `useRef` so repeated same-value events don't re-fire — fine for a low-cardinality (3-stop) slider; a continuous-value slider would need a debounce instead.
- App logs (`~/Library/Logs/app.glaze.macos.<appId>/glaze-*.log`, tail the most-recently-modified one) are the fastest way to confirm an IPC handler actually ran — `testStore.save()` logs `"Saved test record"` (not the channel name), so grep the log message text, not the IPC channel/handler name.
