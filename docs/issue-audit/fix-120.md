# Fix plan — #120: "Generate steps with AI" reports *No steps parsed*

**Status:** partially addressed since filing; **not reproducible from the issue
as written**. Needs one piece of information from the reporter before code is
written.
**Verified:** 2026-08-17, by reading the parser and its history.

## What has already changed since the issue was filed

`renderer/lib/parse-llm-response.ts` carried three hand-transcribed kind lists,
and the assert one had drifted — it omitted `urlEndsWith`, `urlIs` and `css`
while the prompt actively told the model to emit `urlEndsWith`. `validateStep`
drops an assert step with no recognised kind, so those steps vanished silently.
That was fixed (the lists are now derived from `recorder-types`, see the comment
at `parse-llm-response.ts:96-103`; landed in `f8037c4`, "The AI features believed
things about this app that stopped being true", #146).

If the reporter's prompt produced URL assertions, that fix plausibly *is* this
issue, and it should be re-tested before anything else is done.

## What is still fragile, if it recurs

`extractStepsJson` (`parse-llm-response.ts:170-201`) accepts a step list two
ways: a closed ```` ``` ```` fence whose content starts with `[`, or the widest
`[`…`]` span in the raw text. Three realistic failure modes survive:

1. **An inline reasoning block.** Local models (Ollama, LM Studio — both first
   class here) often emit `<think>…</think>` in the content stream. Any `[` in
   that prose moves the start of the "widest span" and `JSON.parse` fails, with
   no further candidate to try. `use-llm-chat` accumulates *streamed* reasoning
   separately (`renderer/lib/use-llm-chat.ts:14`), which does not help a model
   that puts the tags in the answer body.
2. **An object wrapper.** `{"steps":[…]}` happens to survive on the widest-span
   fallback, but only when nothing else in the response contains brackets.
3. **Everything dropped by `validateStep`.** If the model emits a step type
   outside the deliberately narrow `STEP_TYPES` set (`parse-llm-response.ts:85-96`
   — `if`/`endif`/`cookie`/`capture`/`runFlow`/`state` are not the model's to
   emit), the array parses and every entry is discarded. The user sees the same
   "No steps parsed" as a total parse failure.

The third one is the worst, because the message is actively misleading: the
steps *were* parsed and then thrown away, and nothing says which or why.

## Before writing code — ask the reporter

Reproduce or get: **which provider and model**, **the prompt**, and **the raw
response** (the dialog already streams it into a scrollable block below the
status, `generate-steps-dialog.tsx:333+`, so it can be copied). Without the raw
response this is guesswork, and three of the four candidate fixes are wrong for
any given cause.

## The fix, once a cause is known

Ordered by value, not by size:

1. **Say why.** Replace the bare "No steps parsed" (`generate-steps-dialog.tsx:313`)
   with a reason: *no JSON array found* vs *found N entries, kept 0*. Have
   `extractStepsJson` return the discard count alongside the steps rather than
   `null`. This is the fix that matters regardless of cause — it turns every
   future instance of this issue into a report that can be acted on.
2. **Strip inline reasoning** before scanning: remove `<think>…</think>` and the
   equivalent tags from the text `extractStepsJson` searches.
3. **Accept an object wrapper**: if the parsed candidate is an object with a
   single array property, use that array.
4. **Do not widen `STEP_TYPES`.** The narrowness is deliberate and documented;
   if the model is emitting composed step types, the prompt is what is wrong.

## The test

`renderer/lib/parse-llm-response.test.ts` (node project). One case per failure
mode above, each pinning the *reason* as well as the result. Add the reporter's
real response verbatim as a fixture once it is available — a synthetic
reproduction of a model quirk is a guess about the quirk.

**Verify it can fail:** for each new case, revert its guard and confirm that
case alone goes red.
