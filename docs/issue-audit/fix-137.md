# Fix plan — #137: the New recording dialog stays open after the test is created

**Status:** confirmed valid. Reproduced in the browser preview 2026-08-17.
**Correction:** an earlier pass on this audit read the *native window* teardown
(`stop()` → `finalize()`), found it correct, and called the issue likely fixed.
That was the wrong window. The thing that persists is the **modal inside the
main window**, and it is still broken.

## What actually happens

`Dialog`'s confirm button calls `onConfirm()` and nothing else:

```tsx
// renderer/ui/overlays.tsx:222
<Button variant={confirmVariant} disabled={confirmDisabled} onClick={() => void onConfirm()}>
```

It is not a `DialogPrimitive.Close`, and `Dialog` never calls
`onOpenChange(false)` itself. `NewRecordingDialog`'s `onConfirm`
(`renderer/main/new-recording-dialog.tsx:86-95`) starts the recording and clears
its fields, but nothing closes it.

Reproduced in the preview — Home → "Record a test" → type a URL → "Start recording":

```
stillOpenAfterConfirm: true
title:                 "New recording"
urlFieldNowEmpty:      true     ← setUrl("") ran, so onConfirm completed fine
```

The handler succeeded and the dialog stayed.

## Why it looks intermittent

Which owner mounted the dialog decides whether you ever see it, and that is why
this was hard to pin down. `RootShell` swaps only the **outlet** while recording:

```tsx
// renderer/main/root-view.tsx:29-35
header={<AppStrip … />}
sidebar={<LibrarySidebar />}          // ← outside the swap
…
{state.recording ? <RecordingView /> : <Outlet />}
```

| Started from | Owner | Mounted during recording? | Symptom |
| --- | --- | --- | --- |
| Home → "Record a test" | `HomeView` (`home-view.tsx:219`) | **No** — it's in the outlet | Dialog unmounts with the view. No bug |
| Sidebar `+` → Record | `LibrarySidebar` (`library-sidebar.tsx:775`) | **Yes** — it's the `sidebar` slot | Dialog survives the whole session |
| ⌘K → Record a test | `CommandPalette` (`command-palette.tsx:371`) | **Yes** — it wraps everything (`root-view.tsx:176`) | Same |

In the two broken paths the modal sits in the main window for the entire
recording. The user does not notice, because the training browser is a separate
`BrowserWindow` and has focus. When recording ends, `finalize()` closes the
training window, `onFinished` navigates the main window to `/test/$id`, the main
window comes forward — and the modal is sitting on top of the step view that was
supposed to be the reward. Which is exactly the report: *"Currently have to
dismiss the window after test creation."*

## The same bug, unreported: Git import

`ImportGitDialog` has it too. Its `onConfirm` imports, navigates to the new test
and calls `reset()` — but never `onOpenChange(false)`
(`renderer/main/import-git-dialog.tsx:37-57`). Import succeeds, the app navigates,
the dialog stays on top of it.

And it names the contract it is relying on:

```ts
// import-git-dialog.tsx:53
// Re-throw keeps the dialog open for retry (see Dialog semantics).
```

**Those semantics do not exist in this tree.** The composed `Dialog` was
evidently meant to close on a resolved `onConfirm` and stay open on a thrown
one — call sites are written against that — but the implementation never does
it. Most likely lost in the SDK port, which kept symbol names and prop contracts
so consuming views were not rewritten (`PORTING.md`). Nothing caught it:
`renderer/ui/dialog-actions.test.tsx` pins that Close calls `onOpenChange(false)`
and that each action fires its handler, and never asserts what happens to `open`
after a successful confirm.

`GenerateTestDialog` is unaffected — it uses its own `Button` and closes itself
(`generate-test-dialog.tsx:237`). `GroupNameDialog` calls `onOpenChange(false)`
by hand (`group-name-dialog.tsx:64`).

## The fix

**Do the local fix now; file the contract separately.** Two reasons, and the
second is not obvious:

### Now — close the two dialogs that don't

In `renderer/main/new-recording-dialog.tsx`, after `start()` resolves:

```tsx
onConfirm={async () => {
  await start(url.trim(), name.trim() || "Recorded test", undefined, viewportForPresetId(windowSize));
  setUrl("");
  setName("");
  // Closed HERE, not by `Dialog`: the composed dialog does not close on a
  // resolved confirm (see #137). Two of the three owners of this dialog —
  // the sidebar and the command palette — stay mounted for the whole
  // recording, so without this the modal is waiting on top of the step view
  // when the session ends.
  onOpenChange(false);
}}
```

Same in `renderer/main/import-git-dialog.tsx`, after the navigate: `onOpenChange(false)`.

Two lines, no blast radius.

### Separately — restore or delete the `Dialog` contract

A latent mismatch between a documented contract and the implementation will be
tripped over again. But **restoring auto-close globally is not a safe blanket
change**, which is why it must not be bundled into this fix.

`IssueComposeDialog` is the counter-example. Its `onSend` catches its own error,
sets `sendError` and **returns normally** (`issue-compose-dialog.tsx:276-278`).
Under a restored "close on resolved confirm" rule, a *failed* send would close
the dialog and discard the typed report — the precise thing that file's header
is written to prevent: *"closing over a long typed description on a transient
network blip is how you lose it."*

So restoring the contract means auditing all ~35 `onConfirm` call sites and
making every one that swallows an error re-throw. That is its own piece of work
with its own review. The alternative — delete the comment in
`import-git-dialog.tsx` and accept that every caller closes itself — is smaller
and equally honest.

## The test that would have caught it

`renderer/main/new-recording-dialog.test.tsx`: render with `open`, fill the URL,
click "Start recording", assert `onOpenChange` was called with `false`. Same for
`import-git-dialog`.

Add the missing contract assertion to `renderer/ui/dialog-actions.test.tsx` too
— whichever way the contract question is answered, that file should state it:
either "a resolved `onConfirm` closes the dialog" or "`Dialog` never closes
itself; callers do".

**Verify it can fail:** remove the `onOpenChange(false)` and confirm the new test
goes red. It will — the preview measurement above is the same assertion by hand.

## Gate

`npm run lint && npm run type-check && npm run test:all && npm run build`, then
**record a test from the sidebar `+` in `npm run dev`** — not from Home, which
is the one path that hides this bug.
