# Fix plan — #134: show `https://` on URL entry instead of implying it

**Status:** the functional half is already done; the issue is now UI-only.
**Verified:** 2026-08-17, by reading the normalizer and the URL inputs.

## What is already true

The backend already prepends the scheme for a recording's start URL:

```
main/services/recorder-service.ts:825-829
function normalizeUrl(input: string): string {
  const trimmed = input.trim();
  if (/^https?:\/\//i.test(trimmed)) return trimmed;
  return "https://" + trimmed;
}
```

Called at `recorder-service.ts:1205`. So typing `example.com` in the New
recording dialog already works — it records against `https://example.com`. The
issue is not a broken flow, it is that nothing on screen says so: the field
shows a placeholder (`renderer/main/new-recording-dialog.tsx:100`) that vanishes
the moment you type, so the user cannot tell what will be loaded.

Note also that the trainer's URL bar (`renderer/recorder-chrome/`) is **read-only
by design** — a navigation the user types is one the recorder does not record —
so "the Test Trainer URL bar" in the issue title cannot take input at all. The
input the screenshot shows is the New recording dialog's.

## The fix

Two independent pieces; the first is the issue, the second is the "+ Elsewhere".

**1. A fixed scheme prefix on the input.** Render `https://` as a non-editable
prefix inside the URL field in `renderer/main/new-recording-dialog.tsx`, with
the input holding only the host and path. Then:

- Paste handling is the whole risk. A user pasting `https://example.com/x` into
  a field that already shows `https://` must not end up with
  `https://https://example.com/x`. Strip a leading `https?://` on change, not
  only on paste — typing it character by character reaches the same state.
- `http://` must stay reachable. Some internal test targets are not on TLS. Do
  not hard-block it: either keep the prefix a *display* affordance over a field
  that still accepts a full URL, or offer a scheme toggle. A dialog that cannot
  express `http://localhost:3000` is a worse bug than the one being fixed.

The lower-risk version, and the one to prefer unless the user wants the split
field specifically: keep one input, and render the resolved URL under it as
help text (`https://example.com` updating live as they type), reusing
`normalizeUrl`'s rule. It says the same thing, cannot corrupt a paste, and does
not need a second control.

**2. Share the rule.** If the renderer starts normalizing URLs, it must not
transcribe the regex. `normalizeUrl` is currently a private function in a
compiled main-process module and the renderer cannot import it. Two copies of
"what counts as already having a scheme" is exactly the drift `shared/` exists
to prevent (see CLAUDE.md on `shared/`, and `heal-key.mjs` / `step-semantics.mjs`
as the precedents). Move it to `shared/url-normalize.mjs` + `.d.mts` and have
both sides import it.

That is the part of this issue with real value. The prefix is cosmetic; one
spelling of the scheme rule is structural.

## Other URL entry points to cover under "+ Elsewhere"

Audit before implementing — this list is from a grep, not from driving each
screen:

- `renderer/main/new-recording-dialog.tsx` — the one in the screenshot.
- `renderer/main/generate-test-dialog.tsx` and `import-git-dialog.tsx` — check
  whether either takes a URL and whether it is normalized at all.
- Any `goto` step composed in the trainer (`step-composer.tsx`) — a `goto` step's
  URL reaches the generator, so it is on the capture-boundary path and is
  quoted by `q()`; the scheme question there is about usability, not safety.

## The test

`start()` receives. Add a paste case (`https://example.com`) and an
`http://localhost:3000` case. Move the node-side test for the shared rule beside
whatever `shared/` module it lands in.

**Verify it can fail:** revert the paste-stripping and confirm the double-scheme
test goes red.
