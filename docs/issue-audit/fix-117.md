# Fix plan — #117: the sidebar's AI row opens Settings on the wrong pane

**Status:** confirmed valid, one-line cause, not fixed.
**Verified:** 2026-08-17, by reading the call site against the deep-link API.
**Severity:** low. Cosmetic, but the code comment above it claims the fixed
behaviour, so it also reads as a lie to the next person.

## What the user sees

Clicking the AI provider row in the sidebar footer opens Settings on
**Appearance** (the first pane) instead of **AI**.

## Root cause

The deep-link mechanism already exists and is already used elsewhere. The
sidebar simply does not pass the pane:

```
renderer/main/library-sidebar.tsx:170-174
function openSettingsWindow(): void {
  (window as ...).glazeAPI.glaze.ipc.invoke("window:openSettings")   // ← no pane
    .catch(() => {});
}
```

Compare the working caller:

```
renderer/main/cost-panel.tsx:84
void window.glazeAPI.glaze.ipc.invoke("window:openSettings", "cost");
```

The handler accepts and validates the argument (`main/handlers/index.ts:156`,
`main/windows/settings-window.ts:27` `paneFragment`), and `"ai"` is a real pane
id (`renderer/lib/settings-schema.ts:113`).

The doc comment at `library-sidebar.tsx:186-188` already states the intended
behaviour — "Clicking opens Settings on the AI provider section" — so this is a
comment that has never been true rather than a deliberate choice.

## The fix

In `renderer/main/library-sidebar.tsx`, widen the local helper's type to take a
pane and pass `"ai"`:

```ts
function openSettingsWindow(pane?: string): void {
  (window as unknown as {
    glazeAPI: { glaze: { ipc: { invoke: (c: string, pane?: string) => Promise<void> } } };
  }).glazeAPI.glaze.ipc.invoke("window:openSettings", pane).catch(() => {});
}
```

and at line 239: `onClick={() => openSettingsWindow("ai")}`.

## The one caveat worth knowing before calling it done

`openSettingsWindow` deliberately does **not** apply a pane to an already-open
Settings window (`main/windows/settings-window.ts:39-43` — re-loading it would
discard unsaved edits, and pushing the pane across needs a channel aimed at
this window that `check:ipc-egress` scans for). So with Settings already open on
Appearance, this click still lands on Appearance.

That is a defensible product decision and matches the Cost panel's behaviour, so
the fix above is complete as-is. But it is the thing that will make someone
re-file this issue. Either accept it and say so in the comment, or treat
"deep-link an already-open Settings window" as its own follow-up — it is a
larger change than this fix and should not be bundled into it.

## The test that would have caught it

`renderer/main/library-sidebar.test.tsx` — the pattern already exists at
`renderer/main/cost-panel.test.tsx:113`:

```ts
expect(invoke).toHaveBeenCalledWith("window:openSettings", "ai");
```

Note `RailRow` may activate on `mouseDown` like `SidebarListItem` does — check
which, and use the matching event. `fireEvent.click` against a `mouseDown`
handler reports "0 calls", which reads as a broken handler rather than a wrong
event (CLAUDE.md, Environment gotchas).

**Verify it can fail:** drop the `"ai"` argument and confirm the test goes red.

## Gate

`npm run lint && npm run type-check && npm run test:all && npm run build`, then
open the real app (`npm run dev`) and click the row — Settings is a separate
`BrowserWindow`, so no preview or jsdom test proves the window actually lands on
the AI pane.
