# Fix plan — #121: the issue-compose dialog resets whenever a run finishes

> **Implemented 2026-08-25.** Keyed on `defectSourceKey(source)` with the object read through a ref; `issue-compose-dialog.test.tsx` pins both directions (an equal-but-new object does not reload, a different defect does). See DECISIONS 2026-08-25.

**Status:** confirmed valid, root cause identified, not fixed.
**Verified:** 2026-08-17, by reading all three call sites.
**Severity:** high for the feature it breaks — it discards typed text.

## What the user sees

The "Send to Linear" (now "send to issue tracker") form flashes and reloads
every time a test starts or finishes in the background. Most visible during a
Routine/Batch run, because those finish a run every few seconds. Anything the
user has typed into Title or Description is lost each time, as is their choice
of destination and labels.

## Root cause

`IssueComposeDialog`'s load effect is keyed on the `source` **object**:

```
renderer/components/issue-compose-dialog.tsx:109-178
useEffect(() => { ... }, [open, source]);
```

The effect's first act is to blank the form — `setDraft(null)`, `setExisting(null)`,
`setLoading(true)` — and then re-fetch the draft, the vocabulary, the defaults
and the existing links. That is correct behaviour *for a different defect*. It
is wrong for the same defect re-identified.

All three call sites build `source` as a **fresh object literal during render**,
so its identity changes on every parent re-render even when every field is
identical:

| Call site | Line |
| --- | --- |
| `renderer/main/test-detail-view.tsx` | 1008-1012 (`kind: "failure"`) |
| `renderer/main/a11y-panel.tsx` | 319-329 (`kind: "a11y"`) |
| `renderer/main/visual-view.tsx` | 2153-2161 (`kind: "visual"`) |

And those parents re-render on exactly the event in the bug report: a finished
run invalidates `["runs"]`, `["replays"]`, `["a11y-rollup"]` and the rest via
`invalidateRunDerived` (`renderer/lib/run-derived-cache.ts`), every one of which
these views read. `test-detail-view` also re-renders on live run output, so a
*starting* run resets it too — which is the "flashes every time a test kicks
off" half of the report.

Every field of `DefectSource` is a scalar (`renderer/lib/issue-types.ts:140-150`),
so identity is the only thing that changes.

## The fix

Fix it in the dialog, not in the three callers. A caller that forgets to
memoize is invisible — the form still works, it just quietly resets — and the
next call site added will forget again.

In `renderer/components/issue-compose-dialog.tsx`:

1. Derive a stable identity for the defect and depend on that:

   ```ts
   // WHY A KEY AND NOT `source`: callers build this object inline, so its
   // identity changes on every parent render. The parents re-render whenever a
   // run finishes (see run-derived-cache), and this effect BLANKS THE FORM —
   // so a background Routine run used to wipe a half-typed report.
   const sourceKey = source
     ? `${source.kind}|${source.testId}|${source.runId}|${source.stepId ?? ""}|${
         source.kind === "a11y" ? source.ruleId : ""
       }`
     : null;
   ```

2. Change the load effect's deps from `[open, source]` to `[open, sourceKey]`,
   and read `source` through a ref inside the effect so the lint rule stays
   satisfied without reintroducing the identity dependency.

3. Leave the second effect (`[open, draft, containerId]`) alone — it is keyed on
   the user's own choice and is not affected.

## The test that would have caught it

`renderer/components/issue-compose-dialog.test.tsx`. Render with a `source`
object, assert the draft loaded, then re-render with a **new object of equal
value** and assert `api.issues.buildDraft` was called exactly once and any typed
title survived.

**Verify it can fail:** revert to `[open, source]` and confirm that test goes
red. Without that check the test passes vacuously — React Query mocks in this
repo often make the push bridge inert (`on: () => () => {}`), which is the trap
noted in CLAUDE.md that hid the original stale-cache bug.

## Gate

`npm run lint && npm run type-check && npm run test:all && npm run build`.

No check script covers "a prop object is rebuilt every render" and none should
be added for it — this is one component's contract, and the test above pins it.
