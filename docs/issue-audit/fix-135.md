# Fix plan — #135: vertical form fields right-align their controls

**Status:** confirmed valid, root cause identified, not fixed. One shared cause
behind every example in the issue.
**Verified:** 2026-08-17, measured in the running browser preview
(`npm run dev:web`, Home → "Record a test").
**Severity:** low individually, wide in reach — it is one class in one file, and
it is wrong on every vertical field in the app.

## What the user sees

In the New recording dialog, "URL" and "Test name" fill the width and read
left-aligned, but **Window size** and **Run speed** sit hard against the right
edge under left-aligned labels. Same shape in the trainer's Add Assertion /
Target Element rows, and anywhere else a `Field` has a control narrower than
the dialog.

## Root cause

`Field` puts its children in a control slot that is **unconditionally
`justify-end`**, regardless of orientation:

```
renderer/ui/layout.tsx:386
<div className="flex shrink-0 flex-wrap items-center justify-end gap-2 [&>*]:min-w-0">
```

In `orientation="horizontal"` that is correct — label left, control right. In
`orientation="vertical"` (the default, `layout.tsx:332`) the wrapper stretches
to full width and `justify-end` pushes a narrow control to the right, under a
left-aligned label.

Measured in the preview, the New recording dialog's "Run speed" field:

```
field:   flex min-w-0 gap-2 py-2.5 flex-col items-stretch   (column, stretch)
slot:    flex shrink-0 flex-wrap items-center justify-end   width 414, left 513
```

The label starts at x=513; the segmented control is right-aligned inside the
same 414px box.

The comment at `layout.tsx:381-385` already names this exact behaviour and
records it as the status quo: *"in a vertical field the wrapper stretches, so
`justify-end` only affects children narrower than the field, which is the
existing arrangement across ~50 call sites."* So this is a known trade-off being
revisited, not an undiscovered bug — and that sentence is also the warning about
blast radius.

## The fix

Make the slot's justification follow the orientation, in `renderer/ui/layout.tsx`.
Because the field root already stamps `data-orientation`
(`layout.tsx:395`, `layout.tsx:416`), the cheapest correct version is a `cva`
variant on the slot driven by `effectiveOrientation` — not a descendant
selector, which would be one more rule that can silently stop matching.

```ts
const fieldControlVariants = cva(
  "flex shrink-0 flex-wrap items-center gap-2 [&>*]:min-w-0",
  {
    variants: {
      // `justify-end` is what pins controls to the right of a horizontal
      // field's label. In a vertical field the wrapper is full width, so the
      // same class right-aligns a narrow control UNDER a left-aligned label —
      // see #135.
      orientation: {
        horizontal: "justify-end",
        vertical: "justify-start",
        responsive: "justify-start sm:justify-end",
      },
    },
    defaultVariants: { orientation: "vertical" },
  },
);
```

Keep `shrink-0` and `[&>*]:min-w-0` exactly as they are — the comment above them
records a measured overflow bug in the 360pt trainer panel where controls
rendered with their first characters sliced off. Do not "simplify" them away.

## Blast radius, and how to check it

This changes every vertical `Field` in the app at once — the ~50 call sites the
comment names. That is the intent of the issue ("Anywhere the 'legacy styled'
modal exists"), but it must be looked at, not just type-checked:

1. `npm run dev:web` → `?view=specimen` — every primitive in every state.
2. `?view=settings` — the densest concentration of `Field`, and the only way to
   see the Settings window outside a packaged build.
3. `?view=recorder` and `?view=recorder-editing` — the trainer rows the issue
   names by hand.
4. Home → "Record a test" — the dialog in the issue's screenshot.

`responsive` is the case to think about rather than copy: it is a horizontal
field below `sm`, so it should end up left-aligned narrow and right-aligned wide.
The mapping above does that; confirm it against a real `responsive` call site
before shipping.

## The test that would have caught it

Nothing in this repo can catch it. jsdom has no layout engine, so a rendered
assertion sees zeros, and `check:renderer-classes` proves a class *resolves*,
not that it resolves to the right value. Add a class-list assertion in
`renderer/ui/label-gap.test.tsx` (the nearest existing home) pinning that a
vertical `Field`'s control slot does **not** carry `justify-end` and a
horizontal one does. That is a weak test, and it is the strongest one available
here — the real verification is the four preview screens above.
