## Bugs

### #153 — Minimized run output drawer pushes the console below the window — **fixed**

Measured live with a failing run open (`?test=t-login`):

```
window height  900
run panel      top 676 → bottom 900   flex: 0 0 224px
console scroll clientH 89, scrollH 146, overflow-y: scroll, scrollTop 0…57
```

The panel ends exactly at the window's bottom edge and its console scrolls
through its full height. The layout was rebuilt during the B5a reskin
(`.gl-run-panel` in `renderer/theme/screens.css:2653`), which is what fixed it —
`min-height: 0` on the panel and `min-h-0 flex-1` on the `ScrollArea`
(`renderer/main/run-output.tsx:213`), the pattern `check:scroll-layout` exists
to enforce.

**Close.** Optionally add `run-output.tsx` to the `VIEWS` list in
`main/services/__tests__/scroll-layout.check.ts` so it cannot regress.

### #139 — AI Debug output cropped at bottom — **fixed**, one nit left

### #137 — Record-new-test window persists after recording — **valid**

**Corrected after the reporter confirmed it still reproduces.** The first pass
checked the *native window* teardown (`stop()` → `finalize()`), found it correct,
and called the issue likely fixed. Wrong window: what persists is the **modal
inside the main window**.

`Dialog`'s confirm button calls `onConfirm()` and nothing else
(`renderer/ui/overlays.tsx:222`) — it is not a `DialogPrimitive.Close` and
`Dialog` never calls `onOpenChange(false)`. Reproduced in the preview: after
"Start recording", the dialog is still mounted and its fields have been cleared,
so the handler ran to completion and simply did not close it.

It looks intermittent because `RootShell` swaps only the **outlet** while
recording (`root-view.tsx:29-35`). Started from Home the dialog unmounts with the
view and there is no bug; started from the sidebar `+` or ⌘K — both mounted
outside the swap — it survives the whole session and is waiting on top of the
step view when the recording ends.

`ImportGitDialog` has the same defect, unreported. It also names a `Dialog`
contract that does not exist in this tree ("Re-throw keeps the dialog open for
retry (see Dialog semantics)", `import-git-dialog.tsx:53`) — the composed
`Dialog` was meant to close on a resolved `onConfirm`, several call sites are
written against that, and `dialog-actions.test.tsx` never asserts it.

→ **[fix-137.md](fix-137.md)**. Two lines now; the contract question filed
separately, because restoring auto-close globally would break
`IssueComposeDialog`'s deliberate stay-open-on-failure behaviour.

### #135 — Left-align form controls — **valid**

One cause behind every example. `Field`'s control slot is `justify-end`
regardless of orientation (`renderer/ui/layout.tsx:386`), so a narrow control in
a vertical field is right-aligned under a left-aligned label. Measured in the New
recording dialog: label at x=513, control right-aligned in the same 414px box.

The comment above that line already documents the behaviour and warns it reaches
~50 call sites. → **[fix-135.md](fix-135.md)**

Separate finding from the same screen, filed as its own thing rather than folded
in: the New recording and missed-runs dialogs still render in the **old SDK look**
while everything around them is the theme layer.

### #122 — Stats aren't refreshing — **fixed, both causes**

The report was "Total Runs # remains 991 after multiple runs". Two separate
defects produced that, and both have landed:

1. **Nothing invalidated the caches a run writes.** Views subscribed to
   `runs:changed` from inside route components, so refreshing only happened if
   you were standing on the screen. Fixed by `renderer/lib/run-derived-cache.ts`
   — one list, invalidated from the session-long provider, guarded by
   `check:derived-cache` (`4f0bad6`, #133).
2. **The totals were computed over a capped run list.** 991 is the tell — the cap
   was 1000. Fixed by a separate `["run-totals"]` key that counts every run
   (`890d5d2`, #158). Its comment in `run-derived-cache.ts:49-53` names exactly
   this: *"that list is capped, this count is not"*.

The preview now reads "276 runs recorded, 30 kept in history" — a lifetime count
alongside a retained count, which is the shape the fix introduced. **Close.**

### #121 — Send-to-tracker form reloads on background runs — **valid**

The dialog's load effect blanks the form and re-fetches, and it is keyed on the
`source` **object** — which all three call sites rebuild inline on every render.
A finished run invalidates the caches those views read, so every run in a Batch
resets the form and discards typed text. → **[fix-121.md](fix-121.md)**

This is the same family as #122's root cause: a run's side effects reaching a
component that did not expect to be re-rendered by them.

### #120 — "No steps parsed" — **needs the raw response**

and the message is the same for all of them — including the case where steps
parsed fine and were then all discarded. → **[fix-120.md](fix-120.md)**

The fix worth doing regardless of cause is making the message say *why*.

### #117 — AI model row opens the wrong settings pane — **valid, one line**

### #124 — GitHub / Jira in Integrations — **half done, narrow to Jira**

**Already built:** the whole tracker abstraction, plus GitHub Issues end to end
(`fe041de`/#154). `main/services/issue-tracker/` has a provider registry, a
config store, a link store, and Linear + GitHub providers. The registry's own
header states the shape: *"adding a provider is a row here plus its two files"*.

**Still necessary:** yes, for Jira — that is a real gap for anyone not on Linear
or GitHub.

**Lift:** small-to-moderate, and almost all of it is Jira's API rather than this
app. One row in `provider-registry.ts:37`, a `jira-provider.ts`, a
`jira-token-store.ts`, `"jira"` added to the `ProviderId` union in
`renderer/lib/issue-types.ts`, and the credential fields in
`renderer/settings/panes/integrations-pane.tsx`. Call it 1–2 days.

**Complexity added:** low structurally — the seam already exists and was built
for exactly this. The real complexity is Jira-shaped: its auth (Atlassian OAuth
or an API token plus a site URL, not a single opaque key like Linear and GitHub)
does not fit the current `EncryptedSecretStore` `get/set/clear/has` interface,
which stores one secret per provider. That interface is the thing this work
would bend. Jira's project/issue-type/field model is also richer than
`container` / `sub-container` / `label`.

**Dependencies:** none blocking.

**Unblocks:** nothing else in the tree; it is a leaf.

**Existing plan?** Not for Jira specifically. `docs/plans/mcp-and-test-intelligence.md:607`
argues the opposite position — *"rather than building a Jira integration, emit a
ticket-shaped payload and let the customer's existing Jira MCP file it"*. That
argument was overtaken when GitHub was built natively, but it is worth a
deliberate answer in `DECISIONS.md` rather than a silent reversal.

**Design:** none new. The Integrations pane already renders a provider picker
and credential rows.

**Surface:** grows by one row in one settings pane. Every other screen already
asks "which provider?" rather than naming one.

### #136 — Tags/labels at creation time — **valid, small, good value**

**Still necessary:** yes. Tags exist (`tags-dialog.tsx`, `tag-cluster.tsx`) and
drive real behaviour — Batch/Routines filter by them — but they are reachable
only by right-clicking a test in the sidebar. A feature you have to discover by
right-clicking is one most users never find.

**Already done:** no. None of the four creation paths offers tags: New recording
(`new-recording-dialog.tsx`), Prompt (`generate-test-dialog.tsx`), Git import
(`import-git-dialog.tsx`), local import.

**Lift:** small, ~1–2 days for all four. `TestRecord` already carries tags, and
`finalize()` in `recorder-service.ts:2640` explicitly spreads the existing record
first *so that tags survive a re-record* — so the storage side is solved. The
work is a tag input in four dialogs and passing the value through to the record.

**Complexity:** low, with one wrinkle. `start()` currently takes
`(url, name, ?, viewport)` and finalize builds the record when the *window
closes*, so a tag chosen at start must be carried on the session and applied at
finalize, not written at start (there is no record yet).

**Dependencies:** the issue says tags are also "planned for test settings". Build
the tag input as one reusable component and both land together; build it four
times inline and the settings version becomes a fifth.

**Unblocks:** Routines. Tag-filtered routines are only as useful as the tagging
rate, and tagging at creation is what raises it.

**Design:** existing components. `TagCluster` is a picker already; whether it can
be reused directly for *entry* (rather than filtering) needs a look.

**Surface:** grows — one field in four dialogs. Mitigated by the shared component.

### #80 — Cherry-pick / edit AI debug suggestions — **valid, the largest UI item here**

**Still necessary:** yes, and the reasoning holds. `extractCorrectedScript`
(`renderer/lib/parse-llm-response.ts:63-77`) returns a whole replacement file or
nothing, so applying is all-or-nothing. Its guard (require a closed fence
containing both `import` and `test(`) exists to avoid overwriting a script with
an illustrative snippet — which is the same problem stated from the other side.

**Already done, partly, elsewhere:** yes, and it changes the plan. `88b4a02`/#118
put script changes in the Heals view with **a diff and an undo**. So there is
already a reviewed-change surface, and undo already makes a bad apply
recoverable. That weakens the urgency and suggests the right shape is a diff
*before* apply reusing that surface, rather than a new inline editor.

**Lift:** moderate to large — 3–5 days for hunk-level selection. A per-hunk apply
means computing a diff against the current script, letting the user stage hunks,
and reassembling — plus the case where the model's output does not apply cleanly
because the script changed underneath.

**Complexity:** the highest of any feature here, and it lands on a security-
adjacent path. The AI's output becomes a `.spec.ts` that Playwright executes in
Node. Today one guarded gate decides whether to overwrite the file; hunk-level
apply multiplies the paths by which model output reaches executable source.
Anything built here must keep the generator's own guards intact — CLAUDE.md is
explicit that a boundary fix is not enough on its own.

**Dependencies:** the Heals diff/undo surface (already exists).

**Unblocks:** nothing directly. It raises trust in AI debug, which is the feature
everything AI-shaped in this app is judged by.

**Design:** needs new design for hunk staging. A diff view exists to borrow from.

**Surface:** grows meaningfully — a new interaction mode in a panel that is
already the densest in the app.

**Recommendation:** split. Ship "show a diff before applying" first, reusing the
Heals diff; treat hunk selection as a follow-up decided by whether the diff alone
is enough.

### #73 — Index commonly-used URLs — **valid, but the issue body is wrong about its pre-work**

**The premise is stale, and this is the most important finding in the audit.**
The issue says *"this is what the 'Crawl' test setting speed was originally
designed for; that was scoped in as pre-work."* In the code as it stands, `crawl`
is a **run speed** — the slowest of four, which additionally waits for the page
to settle after every step (`main/recorder/types.ts:368-379`,
`main/services/settle-fixture-source.ts`,
`main/services/playwright-runner.ts:996-1160`, including its own timeout floor
and user-facing log lines). It is fully built, documented and shipped, and it has
nothing to do with crawling a site.

There is **no site crawler, no local index and no stored site model anywhere in
the tree.** This is greenfield. Anyone picking it up expecting pre-work will not
find any.

**Still necessary:** the goal is sound — a local model of the site under test
would help auto-heal, a11y, visual diff and step execution alike. But it is a
research-shaped bet, not a scoped feature.

**Lift:** the largest item in the backlog by a wide margin. Weeks, not days. It
needs a crawler (queue, scope rules, robots, auth, rate limiting), a storage
format, retention and invalidation (a site changes; a stale index is worse than
none), a settings surface, and then separate integration work into each of the
four consumers.

**Complexity:** very high, and it introduces a class this app does not currently
have — **background network activity against a third-party site outside a
recording session**, with everything that implies for consent, credentials and
rate limits. Note the existing capture boundary treats page content as untrusted
input compiled toward executed code; an index of crawled content feeding
auto-heal puts untrusted content on a new path into locator selection.
`docs/DECISIONS.md` would need an entry before a line is written.

**Dependencies:** none technically. Storage would sit beside `metrics.db` and
should follow its rule — a **derived shadow**, droppable and rebuildable, never a
store of record.

**Unblocks:** potentially a lot (better healing, better a11y baselines,
site-aware generation). All of it speculative until the index exists.

**Existing plan?** No. `docs/plans/` has nothing on it.

**Design:** substantial new design — crawl configuration, progress, scope, and a
way to see and clear what was stored.

**Surface:** grows significantly on both sides.

**Recommendation:** rewrite the issue body to drop the Crawl claim, then split
into (a) a spike answering "what would auto-heal actually do with an index, and
is it better than what it does now", and (b) implementation, gated on (a).
Building the crawler first risks weeks of work for a consumer that turns out not
to want it.

## Method note

#137 is the cautionary tale for this audit and for the skill that generalises
it. It was first marked "likely fixed" from a clean reading of the window
teardown code — which was correct, and was not what the issue was about. A
verdict of "fixed" reached without driving the thing the user actually touched
is a guess wearing a citation. Where a claim is about something on screen,
**drive it**; where it cannot be driven, say the verdict is unverified rather
than picking the optimistic reading.
